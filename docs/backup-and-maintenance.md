## 1 已确定的第一版方案

| 事项 | 确定方案 |
| --- | --- |
| 备份单位 | 整个项目的完整归档；第一版不做增量、差异或仅数据库恢复 |
| 数据库副本 | 使用 SQLite Backup API 创建一致性副本 |
| 普通备份 | 只在生成不可变副本期间短暂冻结业务接口，之后自动恢复 |
| AI 维护 | 显式进入、显式结束，维护期间网页不能操作业务数据 |
| 维护前备份 | 进入维护后先生成完整基线备份，成功才允许管理端修改 |
| 恢复 | 验证候选项目，保留原项目现场，按持久操作日志完成整目录替换 |
| 旧页面 | 维护结束后必须重新加载，旧文档的请求不能直接恢复写入 |
| 任务协议 | 复用既有任务 ID、等待和日志，不新增任务状态枚举 |
| 备份保留 | 手动备份不自动清理；普通自动备份保留最近 10 份，保护正在使用的基线 |

普通页面改动和一般业务数据操作不强制进入维护，也不为每次 SQL 自动备份。改表可能使旧页面失效、大批量数据修正或整项目恢复时，使用维护流程。平台不尝试自动判断任意 SQL 的业务破坏性。

## 2 归档内容与位置

完整项目备份携带当前业务数据，不等于用于公开分享的应用包。两者的目录、清单、Schema 和状态见[《项目与应用包格式 v1》](project-and-app-format-v1.md)；外部包的 seed/初始化是候选设计，不反向收紧本文坏库现场保全、恢复及 WAL/SHM 保护规则，恢复也不重新播种。

使用支持大文件的 ZIP 归档，内部保留清晰目录，名称为 `<backupId>.zip`。归档结构如下：

```text
backup.zip
├── backup.json             归档版本、项目 ID、时间、来源及文件校验清单
└── project/
    ├── project.json
    ├── README.md
    ├── docs/
    ├── meta/               可选 icon.png 及其他持久项目资料
    ├── app/                源码、依赖声明、锁文件、vendor 中的 SDK 包
    ├── dist/               备份时正在使用的完整网页产物
    └── data/
        ├── main.sqlite     通过 SQLite Backup API 生成的独立数据库副本
        └── attachments/
```

以上展示标准目录，实际按已校验的项目清单保存相对路径。项目下其他持久文件也纳入清单，不能只备份固定文件名而遗漏补充文档或自定义源码。排除范围只认已识别的 `sourceDir/node_modules`、项目根 `.platform/`、工程版本控制内部目录及白名单构建缓存；不得按目录名递归排除附件中的 `node_modules`、`.git` 或用户文件夹，也不将任意隐藏文件一概视为缓存。备份范围在结果中可查看，与空间清理的路径归属规则一致。

上述排除针对现有源码构建依赖，不是未来 Node 运行依赖的归档规则。Node 应用必须携带明确声明、可归档的完整运行产物和依赖；不得将唯一运行依赖放进会被排除的源码 `node_modules` 后宣称可恢复。应用自有持久目录、数据库/附件归属及目标系统原生依赖的格式仍须按新方案定稿；不改变当前 `main.sqlite` 和附件的所有权。恢复验证仍不执行应用代码、npm 或安装脚本，也不自动启动后端。

**Node 配置归档候选策略：** 声明及虚构示例属于程序资料，实际普通配置属于本实例受管私有数据、不默认发送业务网页，随新类型私有完整归档保存；同机原实例恢复时恢复普通配置的快照值，并按恢复后的声明重新校验，不把配置文件复制成功当作已可启动。此规则必须由新类型格式明确实现，不改现有项目的归档行为；分享默认去掉本机实际配置值。

秘密值拟保存在 OS 凭据库，不写 `.env`、源码、项目数据库或日志；任何项目 ZIP（含完整备份、导出和分享）均不携带秘密值或可直接使用的绑定。同机恢复原实例时，保留当前本机凭据绑定而不恢复旧 Key；当前绑定缺失、格式不兼容或 OS 凭据库不可用时提示重新配置，不从归档猜测或补造。复制/导入的新 ID 不继承源实例的可用绑定，重新填写；源实例绑定继续保留，控制令牌与用户配置分别管理。归档中不携带可用绑定不等于删除固定本机控制记录；未知、未解决的控制现场继续保留。以上策略和具体绑定校验在[配置契约](node-app-configuration.md)定稿后验收。

`project.json` 中的 `name`、`description`、可选 `icon` 及其引用的 `meta/` 图标文件随项目保存。标准图标路径为 `meta/icon.png`，属于“源码与项目资料”，不属于可清理缓存。恢复时这些信息回到所选快照，不用平台列表缓存、恢复前名称或本机图标缓存覆盖；快照没有图标时使用默认图标，不从旧项目补回。

不纳入本机管理凭据、会话、服务发现文件、Node 路径和运行控制状态。数据库副本完成并关闭句柄后应可独立打开，不依赖源库的 WAL/SHM；不能把源库的伴随文件拼进副本。尚未构建的项目可备份，元数据标记无可运行产物，恢复后仍显示尚未构建。

空间统计是可重建缓存：`workspace/.platform/cache/storage/projects/<projectId>.json` 及汇总 `workspace/.platform/cache/storage/workspace.json` 不纳入单项目归档，也不作为项目资料的权威来源。平台自身安装信息和 `appLocalDataDir/cache/storage/platform.json` 同样不随项目备份、恢复或工作区迁移；它们按当前运行的安装包重新读取或扫描。恢复提交后使该项目及工作区汇总缓存失效，按恢复后的文件重新统计，不能沿用同 ID 的旧空间结果。

`backup.json` 至少包含：`formatVersion`、`backupId`、`projectId`、`createdAt`（UTC）、`kind`、备注、平台与 SQLite 版本、接口主版本、是否存在网页产物，以及各文件的相对路径、字节数和 SHA-256。该校验用于检测遗漏和损坏，不冒充归档来源的数字签名，也不证明业务数据正确。

按[已确认生命周期契约](project-lifecycle-and-workspace.md)，归档增加可选 `snapshotState`（`ready`、`maintenance`、`unknown`），缺失按 `unknown` 处理；保存平台已知的未完成构建提示，信息不足时明确需要检查。这些是可移植提示，不是本机维护 ID、凭据或完整控制状态。导入维护快照重新建立本机维护与基线，不能借新基线消除原先未完成的构建要求。

可选 `buildProvenance` 保存当前产物的成功构建来源：完成时间、输入摘要、摘要规则版本、产物摘要及工具版本，不含本机绝对路径、凭据或必须可查询的原任务 ID。备份时核对记录是否对应所复制的产物；缺少或无法关联时记录来源未知，不伪造匹配。导入与恢复据此重建本机来源，并重新核对源码；已知待构建要求独立保存，不能因来源字段缺失而丢掉。根 README、项目身份、名称、简介、图标字段、`meta/` 项目资料和运行时声明不属于构建输入；业务网页中的 `app/public/` 图片仍按源码资源处理，具体范围按主约定第 7.4 节。

本机目录：

```text
workspace/
├── backups/<projectId>/<backupId>.zip
└── .platform/
    ├── project-state/<projectId>.json    持久维护、页面代次、基线及构建来源
    ├── tasks/<taskId>/                  任务元数据和日志
    └── operations/<taskId>/
        ├── journal.json                操作进度与恢复依据
        ├── snapshot/                   备份暂存副本
        ├── candidate/                  已验证的恢复候选目录
        └── original/                   恢复前完整现场
```

控制状态和操作日志放在被恢复项目目录外，不能被旧备份覆盖。它们不是可任意清理的缓存；清理器必须识别未结束维护、未提交操作和受保护的现场。该目录是对主约定工作区布局的确定细化。

项目删除、旧回收站和迁移按生命周期契约执行：当前删除直接永久执行、不产生回收项，旧回收站继续保护原维护基线，新删除和旧项永久清除均不连带删除历史备份；迁移完整保留持久控制、历史备份与恢复现场，受保护现场内部不套用缓存排除规则。

归档解包到暂存目录，先检查格式版本、路径越界、重复路径、大小和文件校验值，不向正式项目目录直接解包。第一版归档只保存普通文件和目录；遇到需要打包的符号链接时明确报错，不静默漏掉文件或跟随到项目外部。

图标是可选展示资料：`project.json.icon` 未设置时正常使用默认图标；已声明引用的文件原本缺失，或已归档文件并非可解码的静态 PNG 时，使用默认图标并报告图标问题，不单因此阻断业务或要求构建。该容错不放宽归档完整性：凡 `backup.json` 文件清单已列出的文件，解包后缺失、字节数不符或校验失败，仍须拒绝该归档；路径越界等归档安全错误也不能按图标警告放行。

## 3 普通备份流程

1. 提交任务，校验项目和预计空间，取得同项目操作互斥；有构建、恢复或其他备份时返回 `PROJECT_BUSY`。
2. 关闭新的业务操作入口，排空已经接受的数据库、附件和资源替换操作。为简化首版，冻结期间暂停全部业务 SQL 和附件接口，不尝试只靠 SQL 字符串判断读写。
3. AI 暂停直接改源码、项目元数据、数据库和附件。平台通过 SQLite Backup API 生成数据库副本，并复制源码、文档、`project.json` 与 `meta/`、SDK 包、当前网页产物及附件到暂存目录。
4. 暂存副本完整且不再变化后释放业务冻结。原项目可继续使用；压缩和校验只处理暂存副本，不再读取正在变化的原项目。
5. 生成文件清单、校验数据库副本和归档，先写临时归档，完成后发布为正式备份并登记。只有此时任务才是 `succeeded`。
6. 失败时不登记可恢复备份，清理可安全删除的临时产物并返回原因；原项目未被修改。任务结束后释放操作互斥。

SQLite Backup API 提供数据库一致性副本，但不能同时替附件和源码加锁；全项目一致性需要上述协调。外部进程任意写文件时，平台不能宣称获得跨文件原子快照。参见 [SQLite Backup API](https://www.sqlite.org/backup.html) 及其[接口约束](https://www.sqlite.org/c3ref/backup_finish.html)。

冻结时网页可继续显示已经加载的内容，平台静态提示、项目状态和 SSE 保持可用。SDK 告知“正在备份，暂时无法保存”，不把用户未提交表单当作已保存数据，也不在解冻后偷偷重放失败的写入。普通备份成功或失败后恢复原有模式；它不会让正常项目长期停在维护状态。

数据库或复制任务没有真正停止前不能因客户端超时释放冻结。程序崩溃后，未完成备份任务标为 `interrupted`，未发布归档不列为有效备份；普通备份本身不留下持久维护模式。

## 4 备份触发与保留

| 类型 | 触发 | 保留规则 |
| --- | --- | --- |
| 手动备份 | 用户或 AI 明确调用 | 不自动清理，可明确删除 |
| 维护基线 | AI 进入需要修改项目的维护流程 | 当前维护引用期间保护，结束后进入自动备份保留规则 |
| 恢复前备份 | 当前项目健康且可创建完整归档时 | 归入自动备份，但恢复操作未结束前保护 |
| 恢复前现场 | 每次恢复替换前都必须保留 | 在恢复确认完成、存在适当保留依据或用户明确清理前，不按缓存删除 |

自动备份每项目保留最近 10 份可清理归档，当前维护基线、正在恢复的来源、未解决恢复关联备份及最后一份有效备份不参与自动删除。先成功产生新备份，再清理超额旧备份；不先删旧备份赌新任务会成功。保护项和手动备份可能使数量超过 10，界面展示实际占用。

恢复前现场若已有内容等价且校验完成的恢复前归档，可在操作完成后释放其重复目录；原库损坏而无法形成有效归档时保留现场并提示手动处理。不要把损坏现场冒充正常备份，也不要无限隐形积累目录。

第一版不做定时备份、云同步和自动加密归档。默认保存在工作区，允许用户另存到其他磁盘；同盘备份用于撤销项目改动，不能替代磁盘损坏后的恢复来源。估算空间要包含暂存副本、归档和恢复原目录的保留需要；空间不足则停止本次操作，既有数据和备份继续保留。

## 5 维护状态模型

持久模式只使用两个值，避免把所有任务阶段都变成项目状态：

| 字段 | 含义 |
| --- | --- |
| `mode: ready` | 项目未处于持久维护；不代表一定已构建 |
| `mode: maintenance` | 项目处于明确维护，业务网页被阻断 |
| `maintenanceId`、原因、开始时间 | 标识本次维护，用于交接和避免管理工具误结束另一轮维护 |
| `baselineBackupId`、`readyForChanges` | 本轮基线是否已成功，可以开始管理修改 |
| `activeTask`、任务 `phase` | 当前构建、备份、恢复等临时操作，独立于持久模式 |
| `recoveryRequired` | 目录替换结果尚不明确，必须先处理操作日志，不能结束维护 |
| `documentEpoch` | 本次项目运行上下文的代次，不能随项目恢复倒退 |

`maintenanceId` 是操作关联标识，不是新的管理密钥，不限制已经授权的外部 AI 读写业务数据。平台管理入口仍按现有凭据鉴权。

## 6 进入与结束维护

### 进入

1. 取得操作互斥并记录维护意图。已有构建等任务时返回忙碌，不强行打断。
2. 持久化 `mode: maintenance`，关闭网页业务入口，通知已打开页面并排空已有操作。
3. 创建整项目基线备份；此阶段管理 SQL 写入和构建也暂不接收，外部 AI 应停止直接文件修改。
4. 备份成功后记录基线 ID，设置 `readyForChanges: true`，进入任务返回成功及 `maintenanceId`。
5. AI 才开始调整源码、SQL 和说明，并调用构建。维护中的管理修改携带当前维护 ID；网页继续停用，不开放用于绕过维护的浏览器特权模式。

进入任务失败则保留维护和失败原因，不能假装基线已经存在。允许在同一维护 ID 下重试准备步骤，或在确认尚未开始改动后明确结束维护；不通过反复进入生成多个看似成功的基线。

### 结束

结束请求显式指定维护 ID。平台确认没有进行中的项目操作、恢复日志已处理、数据库可打开且机械检查通过、清单及声明的网页资源有效。维护准备时记录构建输入基准，结束时按主约定第 7.4 节复核；期间改变构建输入时，应有与当前输入对应的成功构建。仅改根 README、业务文档、项目名称、简介、图标字段或 `meta/` 资料不强制重建，不要求安装 Node；这些修改也不能解除原先已存在的待构建要求或维护状态。可选展示图标的问题按第 2 节降级展示，不等同于业务入口产物损坏。

合法 `unbuilt` 项目例外：本就没有已发布产物时，包括导入、复制或恢复得到的这种状态，其他维护检查通过后可以结束为 `ready + unbuilt`；即使初始源码已改或首次构建失败，也保留待构建信息且不开放业务网页、不伪造构建成功。已登记产物丢失或损坏、原先可运行项目的修改不能使用此例外。

整项目恢复按归档原有状态判断：已验证且原本可复用的产物不因恢复了不同源码就要求 Node 或补造原任务记录。`ready` 快照中源码已修改、仍运行旧产物的情况可以保留，并继续显示差异；这不自动等于必须构建。恢复 `maintenance` 或 `unknown` 快照时，仍保留已知未完成构建并检查不明状态；缺少摘要不自动使网页无效，也不能当作已完成构建的证据，无法确认可复用时保持维护并明确要求修复或构建。恢复后再改构建输入需要重新构建。建立新基线不能清除这些要求。

平台检查目录和数据库完整性，不能证明页面业务逻辑正确。AI 需要完成结构和结果检查；真正浏览器交互在结束维护后验证，破坏性改动可先在项目副本测试。平台不自动运行项目自定义的“验收脚本”来代替这些判断。

检查通过后，在持久状态中推进页面代次并切换为 `ready`，通知页面重新加载。失败保持维护并返回具体问题；没有自动超时解锁。CLI 退出、AI 关闭或平台重启都不会自动结束维护。

独立桌面项目窗口的复用不绕过该检查：结束维护或恢复后再次打开同项目，仍只聚焦容器并提示明确重载，不把旧脚本的代次改成新值；未保存内容由项目处理。

“结束维护”不回滚任何修改。需要撤销时恢复基线；恢复成功后仍要明确结束维护。平台界面可用“恢复并打开”一次动作编排恢复、结束维护和打开项目，只有前一步成功才继续，不要求用户手动执行命令。

## 7 旧标签怎样停止操作

仅让旧 Cookie 失效不够：同一浏览器的新旧标签会共享更新后的 Cookie，旧 JavaScript 仍可能继续请求。每次服务提供项目入口 HTML 时，必须附上当前 `documentEpoch`，由该文档的 SDK 在内存中固定持有。

- SDK 的业务请求通过 `X-Platform-Document-Epoch` 请求头携带文档代次；服务在接收请求和真正执行前都核对模式与代次。
- 结束维护、完成恢复并重新开放项目时推进代次。旧文档返回 `PROJECT_RELOAD_REQUIRED`，必须重新加载当前网页。
- SDK 不在后台取到新代次后让旧 JavaScript 继续操作，不在共享 localStorage 中保存可自动替换的代次。
- 图片、附件 URL 和 SSE 等不能加自定义请求头的入口，通过 `documentEpoch` 查询参数携带代次；Cookie 仍负责身份验证，代次不是密码。
- `context`、控制状态查询和维护通知允许旧文档获取必要提示，但不能更新该文档内固定的代次，不能借此自动恢复业务权限。
- 普通备份不推进代次；普通兼容页面更新继续沿用已有的更新提示策略。
- 工作区迁移提交后在目标位置推进活跃登记项目的代次，并在开放业务前持久化；新会话不能让迁移前的旧文档恢复写入。

这是阻止旧代码误操作的机制，不是对恶意项目的安全沙箱。首个 SDK/API v1 实现必须包含代次约定，不能在已有 v1 项目发布后悄悄强制新增请求字段，破坏已经确认的兼容政策。

## 8 整项目恢复流程

1. **明确目标。** 输入项目 ID 和备份 ID，核对它们匹配；恢复不猜“最新备份”，也不把其他项目的数据当成本项目恢复。
2. **准备候选目录。** 在正式项目外解包，验证归档、清单版本、接口兼容性、文件校验和数据库。无效归档在改动正式项目前失败；恢复不需要 Node，也不执行 npm 或构建脚本。
3. **进入独占维护。** 若尚未维护，建立带恢复原因的维护记录；已在维护则沿用该维护 ID。停止新业务请求、等待已接受操作及文件读取结束，关闭平台数据库和文件句柄；无法安全排空时报告忙碌，不强制替换。外部 SQLite 工具、编辑器及 AI 必须停止访问和修改待替换项目。
4. **保留原现场。** 健康项目可额外生成恢复前归档，但原库已损坏时不能要求先成功创建有效备份。必须完整保留原项目目录及其 WAL/SHM 等伴随文件，称作恢复前现场，不称作已验证备份。
5. **记录并切换。** 在项目目录外持久记录操作意图，使用同一文件系统上的候选目录和保留目录；完整移开原目录，再安置候选目录。每一步可根据日志和实际目录核对。目录切换期间业务访问始终关闭，不承诺两次重命名构成单个跨平台原子操作。
6. **验证并提交。** 重新打开恢复后的数据库、检查入口和元数据，记录提交完成。将已验证的恢复来源归档记录为可用恢复基线，设置 `readyForChanges: true`，允许 AI 在维护中继续修复或检查；原维护基线若存在则同时保留引用。提交日志记录这些状态更新，重启时据此核对补齐；切换失败或结果待处理时不放开管理修改。任务返回恢复后的项目状态、来源备份和原现场位置；只有完成这些步骤才是 `succeeded`。
7. **恢复使用。** 项目继续处于维护，明确结束后推进代次并打开网页。不会自动混入恢复时点之后的记录，也不会自动把旧依赖升级为最新版本。

恢复必须等待外部程序停止访问。SQLite 锁和平台互斥不能证明所有外部文件句柄都已关闭，尤其不能以一次锁探测成功代替外部工具的协作。不能删除旧 WAL/SHM 后强行覆盖使用中的数据库，参见 [SQLite 文件替换与损坏说明](https://www.sqlite.org/howtocorrupt.html)。

数据库检查区分物理完整性与约束：`integrity_check` 不检查外键，需要另外执行 `foreign_key_check`。备份可保存并报告原有外键违规，不悄悄改数据；恢复后的项目有违规时保持维护，允许 AI 修复后再结束。检查通过也不等于附件引用及业务规则全部正确。参见 [SQLite PRAGMA 文档](https://www.sqlite.org/pragma.html#pragma_integrity_check)。

## 9 失败与重启恢复

| 发生位置 | 处理 |
| --- | --- |
| 普通备份暂存或压缩失败 | 不发布备份，安全结束任务后释放短期冻结，原项目内容不变 |
| 进入维护的基线备份失败 | 保持维护，标记未允许修改，支持重试或明确结束 |
| 恢复预检查失败，尚未进入维护 | 原项目保持原模式，不替换任何文件 |
| 已进入恢复，尚未提交切换 | 能确认原目录完整时回退原目录；保持维护，不自动开放网页 |
| 恢复已持久提交 | 保留恢复后的项目，不因任务响应丢失就回退；仍保持维护 |
| 无法确认哪份目录完整 | 保留原目录、候选和日志，设置 `recoveryRequired`，禁止继续业务操作或结束维护 |

平台启动时先处理操作日志和实际目录，再允许打开对应项目。不能仅信任最后一个阶段字符串；文件移动可能成功但日志还未更新。记录写入和目录变化需要实施时验证落盘顺序与异常恢复。

崩溃遗留任务仍按既有协议标记 `interrupted`，结果额外说明 `rolled_back`、`restored` 或 `needs_attention`；这是结果信息，不是新任务状态。不得因上次请求中断而自动重放 SQL、重新恢复一遍或重新构建。

失败不是清除恢复现场的理由。尚未完成恢复判断、回退失败或用户未处理的损坏现场，不进入普通缓存清理。

## 10 操作互斥与访问规则

| 操作期间 | 项目网页 | 管理 SQL/附件操作 | 构建、其他备份或恢复 |
| --- | --- | --- | --- |
| 正常运行 | 可读写 | 可操作 | 可提交一个任务 |
| 普通构建 | 使用原有产物 | 按正常模式；AI 不同时改构建源码 | 同项目互斥 |
| 备份生成暂存副本 | 数据与附件暂不可用，显示提示 | 暂停业务操作 | 同项目互斥 |
| 备份压缩归档 | 按原有模式恢复 | 按原有模式恢复 | 保持任务互斥至归档完成 |
| 维护准备/基线备份 | 不可操作业务数据 | 暂停修改，状态与日志可读 | 内部基线任务运行，不接受另一个任务 |
| 已就绪的 AI 维护 | 不可操作业务数据 | 带维护 ID 可操作 | 可依次构建或备份 |
| 恢复替换与提交 | 不可操作业务数据 | 暂停，状态与日志可读 | 独占 |
| 结果待处理 | 只展示恢复提示 | 仅诊断和明确的恢复处理 | 不自动执行普通任务 |

数据库串行队列、项目任务互斥和持久维护各自承担不同职责。不同项目互不阻断；全局资源限额在实施时设置。互斥只能约束平台操作，外部 AI 直接写文件仍依赖协作约定。

平台提交名称、简介和图标修改也取得同项目操作互斥，与备份、恢复、构建和生命周期操作协调。正常模式不必为这些展示资料进入维护；已处于维护时，修改必须携带当前 `maintenanceId` 且 `readyForChanges: true`。维护准备、恢复切换或 `recoveryRequired` 未解决时禁止这类写入。概览只读取平台识别的元数据和状态，不执行项目脚本，不以业务数据库可打开为前提；仍可显示诊断和恢复入口。AI 直接修改文件继续遵守暂停与交接约定，不能由平台互斥替代外部协作。

## 11 已确定的接口扩展

本节为已确认接口，与既有路由共同构成第一版契约。已有 `backup create`、`backup restore` 与 `task get/wait/logs` 继续复用；后台操作均使用 `queued → running → succeeded | failed | interrupted`，通过 `type`、`phase`、结果字段表达细节。

| CLI 入口 | HTTP 入口 | 用途 |
| --- | --- | --- |
| `platform backup list --project ID --json` | `GET /api/v1/projects/{id}/backups` | 时间、类型、大小、校验结果和保护原因 |
| `platform backup info --project ID --backup ID --json` | `GET /api/v1/projects/{id}/backups/{backupId}` | 查看备份内容、版本及诊断 |
| `platform maintenance status --project ID --json` | `GET /api/v1/projects/{id}/maintenance` | 模式、维护 ID、关联任务、是否可修改 |
| `platform maintenance begin --project ID --input request.json --json` | `POST /api/v1/projects/{id}/maintenance` | 说明原因，提交进入与基线备份任务 |
| `platform maintenance end --project ID --input request.json --json` | `POST /api/v1/projects/{id}/maintenance/end` | 指定维护 ID，检查并结束维护 |

进入请求包含原因；准备失败后的重试包含原 `maintenanceId`。结束请求包含 `maintenanceId`。进入、结束和恢复继续使用 `--input` 传递结构化输入；恢复请求要求明确的 `backupId`，处于既有维护时同时提供 `maintenanceId`。

维护期间的管理修改使用 HTTP JSON body 的 `maintenanceId` 字段。相应 CLI 管理命令可通过 `--maintenance ID` 传入，CLI 将其归一化为同一字段；已有 `--input` 的命令也可在输入 JSON 中提供 `maintenanceId`。两处同时提供时必须一致，冲突则按参数错误拒绝，不静默覆盖。正常模式下的命令继续沿用原有形式。

进入维护、结束维护和恢复均可返回任务 ID。内部基线备份是进入任务的阶段，不能把它当外部第二个任务再申请同一互斥锁。AI 等待最终结果，确认 `readyForChanges` 和基线 ID 后再修改文件；返回任务 ID 本身不代表可以修改。

补充 `PROJECT_MAINTENANCE`、`PROJECT_RELOAD_REQUIRED`、`BACKUP_INVALID`、`BACKUP_SOURCE_CHANGED`、`SPACE_INSUFFICIENT`、`RECOVERY_REQUIRED` 等错误原因。可观测到源文件变化时不宣称成功获得稳定备份；无法观测的外部写入仍不能得到一致性承诺。错误、超时和断线都不意味着写操作可以自动重试。

项目状态通知使用 SSE 事件 `project.state.changed`，提供本项目的 `mode`、是否暂时忙碌及是否需要重新加载。事件不暴露 `maintenanceId`、管理任务详情、备份路径或管理凭据；网页通过允许读取的控制状态获取必要提示。服务端访问检查才是实际约束，页面漏掉事件也不能继续执行旧请求。

## 12 界面与 AI 操作流程

平台首页显示正常、维护中或恢复待处理。项目菜单提供备份列表、创建备份、恢复和维护入口；普通用户不接触事务、WAL 或目录替换细节。恢复入口展示备份时间和回到该时点的含义，CLI 使用明确项目及备份 ID 表达同一意图，不增加逐条 SQL 确认流程。

AI 的改表流程为：阅读源码与实际结构 → 进入维护并等基线成功 → 修改 SQL、源码及文档 → 构建并检查 → 结束维护 → 获取浏览器入口并验证。如果需要撤销，则恢复基线后再结束维护；如果 AI 中途离开，平台保留原因、基线和日志，供下一次继续。

维护后重新打开只保证项目整体来自一个明确版本，不合并用户未提交的表单。SDK 尽量保留页面内尚未提交的输入并明确提示，不强制静默刷新；用户确认重新加载后再进入新文档。

## 13 已确认的取舍与验收要求

- 每份归档包含源码、产物和全部附件，首版简单可移植，但大附件项目的时间和空间开销明显；不承诺固定几秒完成。
- 维护前基线默认必须成功。数据库已损坏的恢复场景走“保留完整现场”的例外，不被无效数据库的备份失败卡住。
- 普通备份冻结全部业务 SQL/附件接口，压缩时解冻；比持续可写的跨文件快照更容易保证一致性。
- 维护退出不自动回滚，失败和重启不自动解锁；普通用户可通过平台提供的恢复并打开流程完成收尾。
- 自动备份保留最近 10 份可清理归档，手动和受保护备份除外。

首版验收应覆盖：WAL 中已提交记录被备份、附件与数据库协调、无 Node 的恢复、名称与图标恢复到快照、图标展示容错与归档校验失败的区分、空间缓存失效重算、损坏原库恢复、不同阶段中断后的目录判断、旧标签拿到新 Cookie 后仍不能继续写，以及维护中重启不会自动解锁。
