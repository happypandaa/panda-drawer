### 2.1 平台名称、图标、版本与关于页面

平台自身的名称、图标和版本属于发行内容。平台开发工程中的发行配置及品牌资源是唯一权威来源；构建发布包时由同一份配置生成平台界面、CLI 和 `.app` 所需的元数据，禁止在几个界面分别维护不同的版本字符串。此处确定数据规则，不选择正式产品名、固定应用标识、图标作品或首个正式版本号。

| 信息 | 权威来源与读取方式 | 展示规则 |
| --- | --- | --- |
| 平台名称 `name` | 当前安装包内的发行元数据 | 管理窗口、“关于”、CLI 显示同一产品名；区别于各项目的 `project.json.name` |
| 固定应用标识 `identifier` | 发布前确定并固定的发行配置，写入安装包 | 用于应用身份与本机数据位置；放在“关于”的详细信息中，不用它代替用户可读名称 |
| 平台图标 | 随签名包发布的只读品牌资源 | Mac 原生图标和界面使用的位图由同一品牌源生成；不读取某个项目的 `meta/icon.png` 充当平台图标 |
| 已安装版本 `version` | 当前运行程序对应的包内版本信息 | “关于”和 CLI 均标明“已安装版本”；不读取项目源码、业务数据库或网上最新版本作为当前版本 |
| 构建编号 `buildNumber` | 当前包实际携带的可选发行元数据 | 有实际值才显示；未设置时省略，不用时间或随机数伪造 |
| 架构和支持线 | 当前包的目标架构与发行支持信息 | 首版显示 Apple Silicon / arm64、macOS 15+；它们与运行机器当前系统版本分别标注 |
| 程序位置 | 从当前运行程序解析出的实际 `.app` 根目录 | 可查看或在 Finder 中显示；不假定必定位于 `/Applications` |

“关于”页至少展示平台名称、图标、已安装版本、可选构建编号、架构、系统支持线，以及程序位置和程序文件大小的最近统计时间。提供“检查更新”“版本说明”“空间总览”入口；空间总览另列工作区及其他本地数据。工作区位置可以在此查看或跳转管理，Node 等构建环境信息放入环境详情，不能让缺少 Node 阻止打开“关于”。

网上可下载的新版本使用独立的发行信息字段与展示区域，不能覆盖已安装版本。平台版本、SDK 包版本、SDK API 版本、项目最近成功构建记录分别表达不同信息；不从平台版本推导各项目的版本，也不为没有版本声明的项目虚构版本号。

后续产品改名可以改变显示名称，但不更换既有固定应用标识或据此迁移、重建本机数据目录。“关于”是查看与跳转入口，不直接修改已签名 `.app` 内的名称、图标或版本。用户的工作区指向等可变设置存于本机设置，项目的名称、简介和图标仍存于各自项目目录。

## 3 安装目录与数据目录

默认工作区为 `appLocalDataDir/workspace`，程序、本机设置和数据按以下结构分开：

```text
/Applications/<产品>.app/                     平台程序与只读资源

~/Library/Application Support/<bundle-id>/   固定的本机应用数据位置
├── settings.json                            工作区指向、Node 路径等本机设置
├── runtime/
│   ├── connection.json                      当前服务发现信息
│   └── control-token                        本次实例管理凭据
├── migrations/                              固定位置的工作区迁移日志
├── cache/
│   └── storage/
│       └── platform.json                    当前安装程序的可重建空间统计缓存
└── workspace/                               默认工作区，可以后续迁移
    ├── projects/
    ├── backups/
    └── .platform/                           控制状态、恢复现场与可重建缓存
        └── cache/storage/
            ├── projects/<projectId>.json              各项目的空间统计缓存
            └── workspace.json               当前工作区的空间统计缓存
```

实际路径由系统目录 API 与固定应用标识解析，不拼接假定的用户名。上图是 Mac 默认位置；用户变更安装位置或工作区后，程序与 CLI 仍通过实际安装信息和固定发现位置工作。Tauri 的 `appLocalDataDir` 使用本机数据目录及应用标识，参见[路径 API](https://v2.tauri.app/reference/javascript/api/namespacepath/#applocaldatadir)。

工作区迁移现已按[生命周期契约](project-lifecycle-and-workspace.md)确定：迁移日志在固定 `appLocalDataDir/migrations/`，提交新位置后不自动回源；上图仅展示默认布局，回收站与恢复现场等完整目录见该契约。

项目数据不写进 `.app`。更新时只替换应用；卸载默认只移除程序，不顺便删除工作区、备份或恢复现场。清除数据使用独立且明确的操作。固定应用标识在首次分发前稳定下来，后续改名不随意换标识，否则可能表现为“项目突然消失”。

初次运行引导用户完成：确认数据位置 → 创建或打开项目 → 复制给外部 AI 的项目说明。新增 Node 应用拟增加配置检查：按作者声明显示名称、用途、获取方式和必填项，用户在平台管理页填写 API 地址与 Key，无需编辑文件或设置全局环境。秘密输入时受信管理页会短暂持有明文；草案建议保存后只展示已设置状态，不回读明文，保存不自动重启，提示用户明确重启后生效。

开发 Node/npm 在环境检查或构建时校验；缺少构建工具不阻止进入平台和运行现有成品。带配套资源的服务在没有显式选择时使用受管工具；已有显式路径保持优先，两种来源失效均明确报告，不暗中回退。可修复配套资源或明确选择兼容的本机工具，不静默安装全局工具。固定应用运行 Node 与构建选择分开，其缺失或损坏使依赖它的应用后端不可用。Node 后端是本机程序，会读取被注入的 Key；内置运行时及签名不构成权限沙箱。当前配置与本机凭据文件的实际范围见[本机配置与运行](node-native-configuration.md)。

配置保护草案建议：秘密存入目标系统凭据库，普通配置存入受管私有数据；Mac 与 Windows 分别验收，凭据库不可用则明确失败，不回落明文。用户配置只注入目标应用新建进程，拒绝未声明与 Node／系统控制变量。默认备份、导出和复制不携带秘密值或可用秘密绑定；原实例同机恢复保留当前绑定，不回滚 Key，新副本及导入重新填写，重装后若绑定丢失也重新填写。用户填写值不进入安装资源、清单、源码、`.env`、日志或分享 ZIP。具体规则按配置草案定稿后实施，不改变现有静态 v1 或通用云连接器范围。

### 3.1 程序占用与统计存储

平台程序占用由 Rust 对当前运行的 `.app` 进行只读扫描，显示其文件逻辑大小及统计时间。扫描真实安装位置，而非固定扫描 `/Applications/<产品>.app`；DMG 的下载大小、压缩大小或另一份旧安装包均不代表正在运行的程序大小。程序包内的 CLI、内置 SDK、模板和资源已包含在 `.app` 总量中；新增内部随包私有 Node 亦按此口径计入，不在程序占用之外再累加一次。用户应用后端及依赖按其实际存放位置计入项目或相应受管范围，不能因共享运行时而遗漏。

空间总览将以下范围分开：当前安装程序、当前工作区、其他已知本地数据位置。默认工作区位于固定应用数据目录内时，统计“其他本地数据”必须排除已独立统计的当前工作区；迁移保留的旧工作区也按独立范围计数，同一目录不能重复加入总量。程序安装位置和数据位置意外重叠时不直接相加，须明确标出重叠并按空间管理契约划分范围。

系统 Node、系统 WebKit、用户全局 npm 缓存和任意下载目录不计入“平台程序”。项目自己的依赖及 SDK 副本按它们在项目中实际占用的文件另计；平台管理的缓存按其真实位置计入本机数据或工作区。逻辑字节数不等同于磁盘分配量，也不承诺删除后一定释放相同物理空间。无法读取的范围显示不完整或不可用状态，不把失败视作 0 B。

程序统计缓存固定写入 `appLocalDataDir/cache/storage/platform.json`，不得写回只读 `.app` 或任何项目业务数据库。该文件包含缓存格式版本、已安装版本、程序根目录身份、扫描时间、统计结果与完整性状态，可随时删除并重建；它是展示缓存，不是安装包元数据、迁移日志或恢复状态的权威记录。缓存失效或缺失不影响平台和项目正常运行。

覆盖更新、程序实际路径或根目录身份变化时，旧程序统计标为过期并重新扫描；即使版本字符串相同，也不能据此永远复用旧结果。“关于”和空间总览复用同一份扫描结果，提供刷新操作，避免显示两个互相矛盾的程序大小。

此缓存属于固定本机应用数据，不随工作区迁移，也不进入项目导出或备份；工作区和项目空间统计缓存分别位于 `workspace/.platform/cache/storage/workspace.json` 与 `workspace/.platform/cache/storage/projects/<projectId>.json`，按[空间管理契约](project-storage-and-assets.md)失效和重建。平台及项目运行控制信息遵守既有控制文件约定，均不存入项目业务数据库。

## 4 第一版手动更新

本节记录原首版方案及仍需保留的手动兜底流程；2026-10-24 已将应用内升级纳入后续实施顺序，当前目标见第6节。本节较早的“第一版不后台下载”不再限制新的已授权范围。

第一版提供“检查更新”和版本说明入口，通过 HTTPS 获取当前发行信息，再打开官方下载安装页。检查失败只显示网络状态，不影响本地项目。第一版不后台下载、覆盖程序或自动重启，也不要求为检查版本建立用户账号。

确定流程：

1. 展示新版本、适用系统/CPU、最低系统要求和更新说明。
2. 用户下载对应 DMG，尚未替换时可继续使用当前平台。
3. 准备覆盖前，平台等待构建、备份、恢复及其他活动操作结束，完成数据库与文件操作的关闭流程，再明确退出整个程序。
4. 用户先通过菜单“退出”／Cmd+Q 正常退出，确认全部业务窗口、受管 Node／普通后代和平台服务结束后，再把新 `.app` 替换到原安装位置。macOS 管理窗口 X 只隐藏窗口并保留 Dock、业务窗口及服务，不能作为已退出或可安全覆盖的依据；点击 Dock／Reopen／重复启动会恢复同一个管理窗口。非 macOS 管理窗口 X 维持正常退出。只关闭业务窗口也不等于已退出平台，清理失败不能视为可安全覆盖。
5. 启动新版，校验本机设置和工作区控制格式，检查遗留操作日志，重新启动服务并发布新的实例及凭据。
6. 项目仍使用原来的源码、SDK、构建产物和数据；CLI 重新发现服务，浏览器重新获得有效会话后打开。

存在正在执行的恢复切换时，更新必须等待其安全结束，不能以强杀进程完成退出。仅有已暂停、没有活动操作的持久维护状态，不要求强行结束维护；记录应保留到新版，避免更新被“必须先解除维护”永久卡住。准备更新后停止接收新任务，避免一直有新任务进入而无法退出。

手动覆盖不是无缝更新，浏览器在程序退出期间会断开。安装器或应用应对运行中覆盖提供明确提示；具体 Mac 文件替换和进程检测行为需要实施验证，不宣称框架自动完成全部保护。

## 5 软件更新与数据兼容

更新对象包括平台程序、原生 CLI、供新建项目使用的 SDK 和模板。既有项目内的 SDK 包、依赖锁文件、源码和业务数据库按已确认政策保留。

项目备份不能替代平台控制状态的兼容检查：维护记录、文档代次、操作日志属于工作区级状态，不在整项目归档内。平台设置和控制文件使用明确格式版本；需要变更时，先保留本次转换涉及的原设置、完整控制状态及操作日志，记录可验证的转换步骤，不能把未知格式当空目录初始化。

更新不得覆盖正在等待处理的恢复现场或自动解除维护。新版不能理解遗留操作日志时，保留现场并阻止相关项目继续读写，提供可理解的状态，不猜测哪个目录应该删除。

第一版不承诺自动回退软件。保留旧安装包可以帮助排障，但旧程序是否能读取新设置和控制状态仍需检查；不能把“装回旧版本”当成自动恢复项目数据。软件降级、平台设置恢复和项目备份恢复是分别执行的操作。

## 6 后续接入应用内更新

2026-10-24 已授权在前述核心流程、数据版本及旧备份退役完成后实施本节。默认自动检查及后台下载，用户明确选择安装并重启；不在用户编辑或任务运行时静默重启。以下技术细节继续以实际集成、签名产物及目标系统验收为准。

后续可采用 Tauri updater，加一个静态 HTTPS 更新清单和产物存储，无需先建立动态更新后端。按系统和 CPU 区分产物，校验版本、目标平台、签名和最低环境，再提供“下载”与“安装并重启”。不在用户编辑或任务运行时静默重启。

两个签名用途不同：操作系统代码签名、公证用于分发和运行校验；updater 签名用于校验更新产物来源，不能相互替代。更新私钥作为发行凭据保存，不放入用户安装包或项目。

macOS 首次及手动安装使用 DMG；Tauri updater 使用其生成的 `.app.tar.gz` 等更新产物及签名，不直接把 DMG 当作更新归档。具体文件名和目标映射随实际打包验证。官方插件支持静态 JSON 并要求更新签名，参见 [Tauri updater](https://v2.tauri.app/plugin/updater/)。

自动检查与后台下载已纳入2026-10-24确认的目标；具体频率、网络偏好及安装失败处理随实施落实。当前代码仍未接入更新服务，不把已授权目标写成已经实现的功能。

## 7 Windows 支持目标与待定发行细节

Windows 10 22H2 x64 与 Windows 11 x64 均已确认为产品支持目标。适配范围、数据保护、W1–W4 阶段和分平台验收见[Windows 规划](windows-support-plan.md)。当前已开始 W1.1 开发工具准备和只读诊断，没有平台 Windows 可运行或安装通过结果，证据见 [W1 记录](windows-w1-verification.md)。初期范围已确认为本机内置 NTFS、由系统 API 解析的固定默认工作区；程序与数据分离，普通更新保留数据。外置盘、网络/映射盘、同步目录及迁移目标后续评估，私有 ACL 和安全路径仍需实现。

以下仍为工程与发行建议，尚未因系统目标确认而定稿：

- 使用 NSIS `setup.exe`，优先当前用户安装，争取两个系统共用同一 x64 包，实际依赖及兼容性分别验证。
- 安装器检测 WebView2 Evergreen 运行环境，缺失时用内嵌 bootstrapper 下载并安装；需要离线分发时另提供包含 Evergreen 离线安装器的包。
- 不默认使用固定版本 WebView2，不跳过运行环境检查。Windows 11 通常已有运行环境，也仍需处理缺失和最低版本。
- 程序、CLI 与安装器安排代码签名；不承诺签名后所有机器都没有系统信誉提示。

Tauri 提供 [NSIS 与 WebView2 安装选项](https://v2.tauri.app/distribute/windows-installer/)，微软解释了 [Evergreen 在线及离线分发](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)。离线运行环境安装不代表首次 npm 依赖下载也能离线完成。Windows 10 目标仅为 22H2 x64，不自动覆盖更早版本、32 位、LTSC 或特殊精简环境。

Windows 的代码签名、WebView2 缺失/版本不足、普通用户安装、覆盖更新、维护和恢复日志保留、卸载默认保留数据及重装发现均需真实验收。Mac 已定的 DMG、公证和 APFS 条件不直接套用到 Windows，也不因新增 Windows 目标而改变现有 Mac 开发身份或资料。

## 8 实现验收与发布准备

Mac 首发至少覆盖：macOS 15 与发布时的当前目标系统、真实 Apple Silicon 设备、从下载产物安装、签名公证与离线启动、系统 WebView 和普通浏览器、从桌面启动时发现 Node、无 Node 运行与恢复、旧版本覆盖更新、维护中更新、恢复日志遗留后的新版启动、卸载后数据保留。

Mac 项目使用系统 WebKit。浏览器调试通过不代表桌面 WebView 通过，媒体和设备权限按实际支持范围分别验证，参见 [Tauri WebView 版本说明](https://v2.tauri.app/reference/webview-versions/)。开发与发布构建优先使用对应平台的构建环境；能生成安装包不代替目标设备验收。

窗口验收包括独立项目顶层页面、同项目重复打开聚焦不刷新、管理窗口恢复、多个项目窗口并存、关闭与明确退出的区别、外链及下载适配、旧代次重载、设备释放，以及项目无法调用管理原生命令。重启不自动恢复全部项目窗口。

发布前验证以下确定行为；这些是实现验收，不是重新决定首发范围：

1. DMG 中的平台与 CLI 均为原生 arm64，在 macOS 15 上通过实际安装与完整项目流程；包内元数据与下载页一致标注最低系统和 CPU。
2. 下载、公证票据、签名及首次启动验证通过；从应用程序目录启动后能使用默认工作区，并保留用户后续选择的工作区。
3. 手动更新前停止接收新任务、安全结束活动操作并完整退出；覆盖后重新发现服务、恢复持久维护记录，已有项目源码、SDK、构建产物和数据保持原样。
4. 平台界面、CLI 与当前 `.app` 的名称和已安装版本一致；有更新可下载时仍保留清楚的当前版本。平台图标与项目图标相互独立，项目损坏或缺少 Node 不影响“关于”页面。
5. 从自定义位置启动程序时，“关于”显示该实际安装位置和对应统计；覆盖更新或移动程序后使旧缓存失效。空间总览对默认工作区嵌套位置及迁移保留目录不重复计数，统计失败不显示为零。

产品名、固定应用标识、正式图标资源、首个正式版本号、正式下载地址、签名账号和发行存储供应方在发布前落实；不在这里虚构可用的品牌资源、下载站点或安装包。已确认的是本文件中的存储、读取与展示规则，资源限额及历史管理接口草案继续保持各自的待确认状态。
