# 停止并删除：第二阶段第 1 批

2026-10-28，按用户确认的[第二阶段设计及补充规则](stop-and-delete-phase2-design.md)实施。本批是实例准入、运行归属及两层锁拆分；持久删除任务、改名恢复和放弃接口在第 2 批，任务界面完整对接在第 3 批。本批不能当作整个第二阶段已经完成。

## 实际变化

- `NodeApps` 的全局表保存稳定的实例 `RuntimeEntry`。实例在启动前入表，进程／代理归属保存在实例资源锁中。启动、失败启动清理、停止、重启、健康检查和全平台停止均不持全局 `Inner` 锁等待资源。
- 启动／停止／重启由后台 owner 持有。调用者丢失等待者不会丢掉实例、真实进程、reader 或文件工作；启动中退出仍能等到迟到 owner 并收尾。状态读取使用快照，不因另一个应用停止耗时而等待全局运行锁。
- 桌面使用实例操作锁。删除先封住新准入、等待已接纳操作，再共用内部 teardown；不调用会重新获取同一锁的公开关闭入口。窗口销毁依赖精确 generation 的 `Destroyed` 回执，回调先记录回执再等待后续 session 清理。
- 原生窗口实际创建仍使用短共享锁，并将 guard 放进排队的主线程闭包；退出快照因此能等到已预约创建完成。启动／停止进程、窗口销毁回执、Git 和复制等等待不持这把全局锁。
- source lease、构建及安装任务、源码发布的真实后台 owner 保留实例准入。旧操作可凭原 token 安全结束；新启动、构建、更新、Git、绑定、配置写入及迟到开窗在删除期间被拒绝。只读删除预览不再因为已有开发操作而直接失败。
- Git／恢复、源码发布、安装准备／构建和已进入的安装提交都先等待已接纳 owner 自然结束；保留原有手动取消入口。本批没有加入“删除自动取消开发任务”，以免在半次事务中截断恢复证据。
- 删除线程持有实例 reservation，不再持有全局 `Inner` guard。已排空旧操作后，配置读取不能在递归删除中重新创建配置目录。
- 确认弹窗注明会关闭窗口及丢失未保存内容，提交期间显示等待具体操作、正在停止或正在删除。迟到状态读取不能覆盖最终失败／成功，也不能污染另一应用弹窗。

## 本批边界

第 1 批仍使用请求归属的临时删除 reservation 和既有实际删除范围；失败后保留已有运行／恢复门禁，没有声称提供持久任务或改名恢复。待第 2 批取得可证明的不可逆边界后，再接入“改名前可放弃，任一目录已改名后只能继续或重试”。本批没有删除完整实例槽、独立可编辑源码或共享来源／安装根，也没有扩大既有范围。

网页项目仍沿用自己的 lifecycle journal、删除门禁、数据库关闭和原地删除。它尚未复用 Node 的新任务／暂存恢复器，差异和后续接入安排见设计说明；本批未改变网页删除协议。

## 验证

只使用临时目录、明确命名的临时项目及人工协议进程；外部源码使用哨兵，另一个实例保持运行或核对登记完整。没有向 Radio Bob 或其他真实项目提交删除，没有为测试手动移除真实标记。

实际验证覆盖：停止的文件工作阻塞时仍能读取状态及启动／停止另一实例；丢失停止或启动等待者仍保留 owner；启动中平台退出；删除等待 source lease 和实际 worker keepalive；旧 lease 仍可完成校验；新修改入口被封；外部源码及另一实例不变；窗口回执和排队清理不互等；退出快照不漏排队创建；删除阶段及迟到 UI 读取。
