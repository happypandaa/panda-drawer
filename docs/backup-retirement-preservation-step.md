# 旧备份退役：先停止自动裁剪

日期：2026-10-24（Asia/Shanghai）。本步仅停止按保留份数自动删除旧 ZIP，独立备份体系整体退役尚未完成。路线依据见[技术实施计划](technical-implementation-plan.md#6-旧代码退役的准确边界)。

## 当前改动

`MaintenanceManager` 不再在准备维护基线或结束维护后执行旧“最近十份”裁剪，原裁剪包装已移除。旧 ZIP、损坏归档、维护控制及恢复现场继续保留；没有扫描或修改真实项目、固定开发数据根、工作区位置、旧备份或恢复记录。

旧格式读取、状态检查、结束维护、恢复及启动中断核对保持原有行为。`backups.rs` 中的归档工具与显式保留策略函数本步没有删除；平台运行路径已无该裁剪函数调用。

## 验证

新增两项真实临时文件测试，均通过：

- 显式构造十二份旧 `maintenanceBaseline`／`preRestore` ZIP 和一份损坏归档，恢复一个已存在的维护状态；通过生产入口结束维护并重新创建服务对象后，十三份文件逐字节保持，旧列表仍可识别。
- 使用同样的旧档案 fixture，在目前尚未退役的维护准备入口成功生成基线后，全部旧文件继续逐字节保持；总计十四个归档条目，没有删减旧历史。

`node scripts/rust.mjs test --locked -p platform-core --lib maintenance::` 共二十二项通过，覆盖新增保护、旧 ZIP 恢复、维护门槛和中断重启核对。本人两份 Rust 文件的格式检查及差异检查通过。

首次新增测试使用未规范化的系统临时路径，被现有符号链接检查拒绝；已只修正 fixture 为真实规范化路径，未放松生产安全检查，随后通过。此前共享源码缺少并行开发中的 Node 测试模块时，编译未进入测试；该并行引用修正后完成上述检查。

## 后续边界

本步没有封闭 `backup`／`maintenanceBegin` 生产入口，也没有改变恢复前 `preRestore` 或导入／复制的隐含 ZIP 基线。既有自动化在维护、重启、历史清理和生命周期等多个模块中依赖这些入口创建遗留状态，需先改成明确的历史 fixture，再在任务、租约及控制写入前统一返回退役错误；不能增加测试模式下的生产放行开关。

数据 Git 不得重新使用这些入口建立 ZIP 基线。SQLite 一致性文件与附件准备、当前操作停写及未完成现场保护继续作为独立能力保留。

没有进行原生界面、真实安装包或真实项目数据验证，本步结果仅覆盖上述源码与隔离临时文件测试。
