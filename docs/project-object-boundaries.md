# 项目对象、目录与 Git 边界

更新：2026-10-21。对应[技术实施计划](technical-implementation-plan.md)第1项，按本轮实施授权落实规则。以下区分本步已实现的只读诊断和后续 Git／安装步骤的约束；不把目录约定写成已交付能力。

## 当前对象与目录

| 对象 | project-v1 网页项目 | 已登记的本机 Node 应用 |
| --- | --- | --- |
| 身份 | 工作区 `projects/<已登记目录>/project.json` 中的完整 ID 与本机登记 | 固定数据根 `node-apps/<UUID>/registration.json` |
| 开发源码 | 清单 `sourceDir`，默认 `app/`；目录存在不证明能重建 | `sourcePath` 仅指外部程序目录；当前清单未声明开发源码，不能据此推断可构建 |
| 当前运行文件 | 清单 `outputDir`（默认 `dist/`）是产物镜像；正常构建发布使用 `.platform/artifacts/<buildId>/dist`，已打开窗口可能保留旧代；来源由 `buildInfo` 表达 | 外部目录下声明的 `web.root`、`backend.root` 及就绪依赖；尚非脱离作者目录的安装副本 |
| 活跃业务数据 | 清单 `database`、`attachmentsDir`，受限于 `data/` | 本机槽 `data/`；具体数据库与附件结构由应用负责，平台未声明或接管 SQLite 路径 |
| 用户配置、秘密 | 沿用现有能力，不虚构配置目录 | 本机槽 `configuration/`；凭据在其 `credentials/` 私有文件，不归作者目录所有 |
| 本机控制与操作现场 | 项目 `.platform/` 及工作区登记、任务、维护记录 | 本机槽登记、`active.json`、`runs/` 等；不进入作者仓库或分享包 |
| 成品包 | 尚未实现标准外部包安装；格式检查不等于安装成功 | 本机登记不等于自包含安装；标准安装另按第7项交付 |

上述角色允许通过明确声明关联，但不能互相冒充。静态网页的构建使用 Node，不会因此变成 Node 服务；运行目录里存在 JavaScript，不会因此获得开发构建能力。没有源码的成品使用 `不适用／未提供` 状态，不伪造 `sourceState: matched`、构建成功记录或 Git 历史。现有 `project.json` 的必填开发字段不为接收成品而放宽；未来安装对象单独建模。

2026-10-23 起，新分配的用户项目根按[可读目录命名](project-directory-names.md)使用转写名与短码，旧目录保留原样。完整 ID、实际 `projectRoot` 与角色分别核对，不靠目录名推断身份；Node 私有槽仍按实例 ID，用户选定外部目录不改名。

本步新增管理接口 `project info`／桌面项目详情及 Node 详情中的 `objectLayout`。其中 `runtime.webRoot` 对 project-v1 表示清单产物目录，对本机 Node 表示外部网页运行目录；不将静态产物镜像称为所有窗口当前运行的代次。其内容是路径和能力边界的只读报告，不能作为对这些路径执行写入、checkout、清理或迁移的授权。project-v1 必须通过清单、路径及登记校验才生成报告，失败返回 `null`；Node 来源失联或声明变化也返回 `null`，保留原错误及停止流程。私有路径仅随受认证管理接口或原生管理命令返回，不新增网页访问权限。

`build.state: platform-build` 只表示安全的源码目录及 `package.json`、`package-lock.json` 材料存在，可交给现有构建入口；不证明脚本、锁文件、依赖、工具环境或最终构建成功。缺材料时报告 `unavailable`，已有运行文件仍按原运行校验使用。Node 暂无平台构建入口，报告 `unavailable`。

2026-10-22 新增[受管 Node 安装](node-managed-installation.md)：v2 登记指向固定数据根内 `generations/<代次>` 的独立程序，`runtime.external` 为 false；原 v1 外部目录登记保持不变。受管程序不是开发源码，`source` 仍标未核实且路径为空，构建能力不伪造为可用。新安装和更新保留来源摘要，不把安装副本当成 Git 仓库。

## Git 根和数据保存规则

当前报告只浅查项目根、声明源码目录及父目录的 `.git` 标记，不执行 Git、不读取配置、私钥或标记文件内容。目录／普通文件／不安全标记分别呈现；普通文件可能是 worktree 或 submodule 指向，存在标记不证明有效仓库、干净状态或任何数据已受跟踪。多标记全部保留，不自动选根；路径不安全和读取错误单列，不能当作“没有 Git”。诊断失败不改变原有运行状态。

后续第4项按以下规则实现：

- 只使用用户项目的标准 Git。新 project-v1 的版本范围以项目根为目标，包含清单、源码、固定 SDK、文档等开发材料；实际初始化是明确的版本操作，读取详情和普通打开不初始化仓库。
- 现有 Git 根仅覆盖 `app/`、位于外部父目录或有多个候选时，先用真实 Git 校验并明确范围。不得悄悄搬根、包裹第二层仓库或创建私有恢复仓库；不能纳管数据库时说明未包含数据库，源码版本能力可独立呈现。
- 纳入数据库时使用一致性 SQLite 快照及所需附件；新建此能力时使用仓库内 `version-data/database.sqlite`、`version-data/attachments/` 保存**当前受跟踪快照**。目录碰撞须拒绝覆盖并报告，不将已有同名目录当平台所有。2026-10-24 已接入明确的数据保存入口，支持范围见[Git 数据版本](project-data-git.md)。
- 活库 `data/`、WAL、SHM、凭据、本机配置、控制现场、缓存及依赖目录不作为版本提交对象。提交前临时文件与受跟踪快照分开；成功后只收尾本次临时文件，不删除受跟踪快照。历史仅由标准 Git 保存。
- 源码分支切换不覆盖活库；取回数据库是明确的独立选择，需停写、校验和失败保留。Node 自有数据尚无一致性快照契约，不能复制目录便声称数据库已纳管。
- 数据库及附件可能含个人资料；本地保存不自动推送，尤其不推向原作者仓库。已知秘密默认排除，不承诺通用数据库脱敏。含私人内容的历史不能直接作为公开分享包。
- `dist` 是否进入开发 Git 待受管构建的实际重建验证；成品必须独立带齐运行文件。运行 Node、开发 Node/npm 和 Git 分别诊断，成品下载、安装、运行不依赖 Git/SSH。

目录报告的 `versioning.state` 仍为 `not-integrated`，表示该报告未执行真实 Git 检查，project-v1 数据库版本状态为 `not-inspected`，Node 自有数据仍为 `not-supported`。2026-10-22 新增独立 Git 状态／初始化／源码保存、历史列表及新建定制分支入口，实际范围与可用性以其新鲜响应为准，不凭目录标记判断；新分支仅改变当前提交的分支引用，不替换项目文件。旧源码取回另有显式预览／应用及中断处理，只改变允许的开发文件，留下待保存改动；HEAD、索引、活库和当前产物不随之回退。恢复现场独立保护开发操作，不触发旧维护停写，也不生成替代ZIP。2026-10-24 新增明确的“保存源码和数据”，为项目根 Git 保存一致性 SQLite 与完整附件快照；普通源码保存保留此前数据子树。数据库取回尚待后续实现，不能把保存能力视为活库恢复已交付。持久日志、明确收尾和实际验证见[Git 数据版本](project-data-git.md)。

## 旧流程退役与兼容

独立本地备份产品和另一套私有 Git 恢复仓库均已取消。2026-10-24 已[封闭新建备份／维护基线并解除新实例 ZIP 基线依赖](backup-retirement-admission-step.md)，不再自动裁剪旧归档。历史读取、同实例恢复、已有维护结束及中断处理继续保留；这不等于将旧兼容代码全部删除或任意历史状态均可安装为新实例。

正常持久化、候选校验、必要停写、失败保留当前程序、中断核对继续存在。已有项目、源码、SDK、数据库、附件、配置、维护状态、旧备份、回收与恢复证据不删除、不移动；固定开发身份及数据根不变，工作区变更仍走公开迁移。旧 ZIP 读取按兼容导入保留，不恢复为新备份产品。

## Node 声明式开发补充（2026-10-24）

[源码开发流程](node-development-workflow.md)新增作者目录的明确关联、Git 状态／保存／历史／新分支和隔离构建。只有明确展开开发入口才建立或核对关联；受管程序代次和来源候选继续是不可变运行材料，不充当第二份 Git 仓库。对象报告在核验关联后可返回 `source-git` 与实际构建能力，不能再将所有 Node 源码一概标为不可开发。Node 业务数据库、附件与配置秘密仍不纳入此源码 Git；更新继续受数据契约门禁保护，工作区迁移不搬动 Node 槽。
