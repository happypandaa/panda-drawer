# Git 备份与现有逻辑精简评估

**状态：历史评估，路线已被取代。** 用户随后明确“仅保留 Git，其他本地备份去掉”。本页提出的私有 Git 恢复仓库、独立恢复点管理和备份功能扩展已取消；当前执行范围以[技术实施计划](technical-implementation-plan.md)为准。以下保留当时代码盘点、技术依据和方案比较，不作为新增实现要求，旧资料仍须保全。

日期：2026-10-21。范围：应用项目的备份与恢复，不是把用户数据库提交到熊猫小抽屉的平台开发仓库。

当时讨论方向：**新备份以 Git 可用为前提，尽量由 Git 管理历史；数据库应纳入提交；`dist` 是否提交重新评估。** 本文盘点当时实现并提出替换方案；未删除运行代码，也未迁移、修改或清理任何项目及旧备份。下述替换方案已由后续决定收敛为标准项目 Git 版本管理。

建议先替换“历史如何存储”，保留已有 SQLite 快照和安全恢复能力。内置 Node/npm 可以帮助重建，但不能单独证明旧版本可恢复，因此目前不能据此删除运行产物。

## 1. 当前究竟保存了什么

| 内容 | 当前做法 | Git 路线的建议 |
| --- | --- | --- |
| 源码、说明、清单、图标、固定 SDK、锁文件 | 复制进每份完整 ZIP；项目根和源码根 `.git` 排除 | 用 Git 保存恢复点中的文件内容；开发仓库本身的分支、暂存区和历史继续由 Git 管理，不为备份改写它们 |
| 正在使用的网页 `dist` | 随 ZIP 保存，并记录来源与产物摘要 | 待决：可重建的开发项目考虑不提交；无源码成品和不能保证重建的版本必须另有受保护的运行包 |
| SQLite 数据库 | 已使用 SQLite Backup API 生成关闭、独立可打开的一致性副本 | **直接复用该快照能力，再把快照提交到 Git**；不提交正在写入的活库及其 WAL/SHM |
| 数据库引用的附件 | 与数据库协调生成副本，随 ZIP 保存 | 恢复点必须覆盖附件内容，或引用另有持久保全的内容对象；只提交数据库会留下失效的文件引用 |
| 普通项目资料和配置 | project-v1 持久资料随 ZIP；Node 实际配置已有独立本机槽，尚无完整归档 | 按归属纳入私有恢复点；Node 配置规则另行接入，不声称已有完整支持 |
| API Key、SSH 私钥、访问令牌 | Node 凭据独立放在本机私有文件；现有 project-v1 完整 ZIP 只按固定路径排除，没有通用脱敏保证，源码 `.env` 或数据库内秘密可能被带入 | 新方案排除已知凭据文件；任意源码或数据库中的秘密需先明确处理，不自动删字段，也不能承诺通用脱敏；含业务数据的恢复点按私密资料处理 |
| 安装依赖与构建缓存 | 当前源码 `node_modules` 等精确路径排除 | 开发依赖原则上不提交，但必须能按锁文件重新取得；Node 唯一运行依赖不能当缓存丢弃 |
| 维护状态、任务、恢复日志及原现场 | 保存在项目之外的控制目录 | 保留必要的操作状态；这些记录不能随业务版本一起倒退 |

代码依据：[backups.rs](../crates/platform-core/src/backups.rs) 的 `exclusions`、`sqlite_snapshot`、`prepare_snapshot`、`publish_snapshot`、`capture_provenance`；[maintenance.rs](../crates/platform-core/src/maintenance.rs) 的 `snapshot`、`begin`、`restore`、`recover`；[lifecycle.rs](../crates/platform-core/src/lifecycle.rs) 的导出、复制和回收事务。

当前 Node 源码槽还不具备上述整套保护。新方案可以让它直接接 Git 恢复点，避免先实现一套新的 ZIP 历史；但数据目录归属、停写和恢复校验仍要完成。

## 2. dist 是否可以不提交

**有 Node/npm，说明有执行构建的工具；源码、依赖和目标环境齐备，才说明有重建条件。** npm 锁文件约束依赖选择，不能保证所有依赖永远可下载，也不能保证跨系统/架构、不同工具版本或带外部输入的构建得到相同结果。[npm ci 官方文档](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

| 情况 | 建议 |
| --- | --- |
| 有完整源码、锁文件、固定 SDK，目标环境重建已通过 | 开发仓库的 `dist` 可以不提交；恢复点记录重建条件，恢复先在候选目录完成构建和验证 |
| 当前源码有未发布修改，运行的仍是旧产物 | 分别保存当前工作文件，以及运行版本对应的源码/构建依据；不能拿当前源码重建冒充旧运行版本 |
| 无源码成品，或运行产物找不到对应的完整源码 | 必须保留运行产物；不能因为平台内置 npm 就宣布可重建 |
| 要求断网时立即恢复运行 | 保留经验证的运行包，或者证明依赖、SDK、工具等全部离线可得；普通 npm 缓存不能默认当持久恢复依据 |
| Node 应用包含原生模块或额外二进制 | 验证目标系统、架构和 Node 兼容性；前端 `dist` 的策略不自动适用于完整后端运行依赖 |

需要区分两个决定：**不提交到开发 Git，不等于不保存成品。** 分享给普通用户的标准应用包仍携带运行文件，日常启动不临时执行依赖安装和构建。

建议目标是“源码与数据快照进入 Git，普通开发提交不强制携带 `dist`；已发布运行包独立保留”。这会减少源码仓库噪声，但增加运行包与 Git 恢复点的关联；未必比小应用直接提交 `dist` 更简单。因此本轮不冻结统一策略，先对真实代表性样本比较：仓库体积、断网恢复、恢复耗时、缺包失败和旧版重建成功率。

目前已有来源记录只保存输入/产物摘要等信息，不保证留有可重建每个旧产物的完整源码快照；不能直接把摘要当作可取回的源码版本。旧 ZIP 中的 `dist` 保留。

## 3. 数据库进入 Git 的最小流程

数据库快照优先保留原 SQLite 文件格式，复用现有实现；首轮不新增 SQL 文本导出、行级比较或数据库自动合并系统。

1. 确认可用 Git、目标恢复仓库和足够空间。没有 Git 时不创建新的备份，不悄悄回退到另一套 ZIP 备份。
2. 协调本项目写入和源码修改，生成 SQLite 一致性副本，并捕获与其匹配的附件和项目文件。Node 必须先按数据契约确认停写。
3. 将不可变候选内容写入 Git，包括简短的恢复说明：项目身份、数据格式、工作源码依据、运行版本依据、工具要求和附件范围。
4. 核对对象和文件完整性，成功提交并发布恢复点引用后才显示完成。失败不发布有效恢复点，不改变用户开发分支和暂存区。
5. 恢复时先提取到候选目录，校验数据库和附件；需要重建的版本先构建验证，再暂停应用并安全替换。失败保留旧项目及处理依据。开发仓库元数据必须保全并按经过验证的方式保留在工作项目中；恢复工作文件不默认回退分支或暂存区，可能表现为当前分支上的未提交修改。

现有 `sqlite_snapshot` 已生成独立数据库文件，并处理副本不依赖源库 WAL/SHM 的问题，可直接复用。SQLite Backup API 处理数据库快照；源码、附件和外部写入的协调仍由平台负责。[SQLite 官方说明](https://www.sqlite.org/backup.html)

Git 不自动合并两个 SQLite 数据文件。恢复采用选定的完整快照；不把源码分支合并当作业务数据合并，也不在每次 SQL 保存时自动产生 Git 提交。

恢复点采用明确的文件范围，提交后核对数据库、附件和项目资料是否实际进入 Git；不能照搬源码仓库的 `.gitignore`，把已约定保护的数据悄悄漏掉。恢复 Git 使用受控配置，不继承作者或全局 hooks、内容过滤器、自动签名要求及默认远端；验收要比较提取后的原始字节，防止内容转换。[Git 配置说明](https://git-scm.com/docs/git-config)

开发仓库的 `.git` 可能是目录，也可能是指向外部 worktree 元数据的文件。尚未支持的布局应拒绝原位恢复或另行提供副本恢复，不能直接覆盖、重写指向或把唯一历史当成可清理的原现场。

“Git 可用”建议包含两个条件：工具可调用，且恢复仓库已正确初始化。初始化可以在启用备份时完成；用户不必先注册 GitHub/Gitee 或配置 SSH。本地提交与远端推送分开，远端同步失败不能误报为本地快照失败，也不能把本地成功称为异机备份完成。

## 4. 数据库提交到哪里

数据库纳入 Git，不等于把个人数据推到作者的公开源码仓库。已有项目的 Git 根可能只覆盖 `app/`，数据库则位于项目的 `data/`，不能直接在原仓库里追踪父目录文件。

| 方案 | 优点 | 代价与适用范围 |
| --- | --- | --- |
| 原开发仓库同时保存源码与数据快照 | 表面上只有一个仓库，代码与快照易关联 | 会混入私人历史；影响用户分支/暂存区，仓库根也未必覆盖数据；分享与推送容易带出历史数据。只适合明确私有、自用且结构匹配的项目，不宜作为所有项目默认值 |
| 每项目一个本机私有 Git 恢复仓库 | 保存完整恢复点，不改作者仓库和用户暂存区；源码仓库仍可正常公开分享 | 多一个内部 Git 存储，但可以替代原来的多份 ZIP 历史；默认无远端，远端备份另选明确的私有目标 |
| Git 只保存源码，数据库继续独立快照 | 代码和数据边界简单，数据库容量策略自由 | 仍有两套历史存储，不符合本轮“数据库也提交 Git”的优先方向 |

**建议评估第二种作为统一默认值**：让 Git 管理私有恢复点的文件版本，公开源码仓库继续负责开发与分享。此建议尚未定稿，不能自动创建仓库或将数据库推送远端。

这里的“私有”指本机目录权限及默认没有远端，不等于加密。Git 不保留完整权限和 ACL，创建恢复仓库、提取数据库和配置时须复用现有私有权限处理。[Git 文件模式说明](https://git-scm.com/docs/git-fast-import#_filemodify)

私有恢复仓库保存“恢复点当时的项目文件与数据”，不因此承诺完整复制开发仓库的所有分支、stash、reflog、暂存状态及不可达对象。原开发仓库完整保留；完整开发仓库的异机保护可交给已有 Git 工作流或单独的仓库转移能力，不再把复制整套 Git 内部状态作为公开源码下载的前置。

同仓库单独建一个“数据分支”不能作为隐私隔离：它仍可能被整体推送，历史数据也不会因后来加 `.gitignore` 消失。公开分享必须从明确的干净内容生成。

Git 能保存数据库二进制，但体积和增长需要实测；不能承诺一定比 ZIP 小。GitHub 当前普通 Git 文件超过 100 MiB 会被阻止推送，大型数据库/附件不能默认靠普通远端 Git 承接；Gitee 限制单独核对。首轮不为此自动引入 LFS 或另建云备份系统。[GitHub 文件限制](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)

## 5. 哪些逻辑能精简或退役

| 当前逻辑 | 处理建议 | 前置条件 |
| --- | --- | --- |
| 为每个新备份压缩完整 ZIP、逐份登记和列出历史 | 新路线改为 Git 提交与引用，逐步停止新建日常 ZIP 备份 | Git 恢复点创建、重启识别、恢复完整通过；没有 Git 时明确不可用 |
| 维护基线只能引用 `backup_<id>.zip` | 改成可识别旧 ZIP 或新 Git 恢复点的引用 | `control.rs` 当前直接检查 ZIP 文件，必须先解除这个耦合；不能删除检查后假定有恢复依据 |
| 导入/复制时隐含生成维护基线 ZIP | 同步接入恢复点选择，区分保留旧基线和创建新快照 | `lifecycle.rs::initialize_candidate` 也会写入或复制基线；新快照需要 Git，旧基线兼容保留，不能只修改备份按钮 |
| ZIP“最近 10 份”保留逻辑 | 不直接搬到 Git；新路线先提供容量与历史说明，旧 ZIP 按现行规则保护 | Git 提交有祖先关系，删除一个标签或运行 `gc` 不等于只保留最近十个快照；历史裁剪另行评估，不暗中改写旧提交 |
| 源码比较、版本保存、分支与回退 | 使用 Git 原生能力，平台只做调用和必要协调 | 避免覆盖未提交内容，不伪造 Git 已提交/已推送状态 |
| 为新增 Node 再实现一整套 ZIP 备份历史 | 可以取消该重复建设，直接对接新的恢复点格式 | Node 数据归属、依赖完整性、配置边界、停写和恢复验证仍完成 |
| SQLite 一致性快照和数据库校验 | **保留复用** | Git 接收的是稳定文件，不提供活库一致性 |
| 附件一致性、路径/链接检查、空间检查 | **保留，缩小到必需范围** | Git 不替平台判断数据引用完整性、受管路径或磁盘是否足够 |
| 操作互斥、恢复前停写、原现场保留、持久提交与重启对账 | **保留最小实现** | Git 切换提交不等于原子替换运行实例；应用、数据库、进程及平台控制状态需要协调 |
| 旧 ZIP 读取、校验、导入和恢复 | **兼容保留，调整恢复前备份调用** | 当前恢复健康项目会先创建 `preRestore` ZIP；新路线有 Git 时改建 Git 恢复点，无 Git 时只保全恢复前完整现场，不暗中生成新 ZIP；旧备份仍可恢复 |
| ZIP 写入工具 | 暂不按整个函数删除，先区分日常备份和显式导出 | `lifecycle.rs::export` 也调用 `publish_snapshot`；仍支持原导出时就不能删除共用编码器 |
| 完整带数据复制 | 新路线可以后置；源码定制优先 Git 副本/分支，新实例默认独立数据 | 旧复制能力保留；业务复制需要新平台 ID，Git clone 不会自动完成实例登记 |
| 回收、工作区迁移、历史现场清理 | 不属于 Git 的版本存储替代范围；新增复杂体验可后置 | 现有功能和控制记录继续保全；不得用 Git reset 或删除 `.git` 代替整项目回收/迁移 |

代码耦合重点：

- [control.rs](../crates/platform-core/src/control.rs) 的 `check` 检查维护基线 ZIP；改成新引用前，直接停掉 ZIP 写入会阻断后续维护。
- [maintenance.rs](../crates/platform-core/src/maintenance.rs) 的 `snapshot` 同时承担冻结、来源记录和调用 ZIP 发布。应拆出“准备稳定内容”与“保存恢复点”，而不是删除整个管理器。
- 当前整目录恢复会把原项目连同开发 `.git` 移入 `original`，从旧 ZIP 提取的候选本身不含 `.git`。新路线要明确恢复后的仓库接续；原现场中的唯一 Git 历史在此之前不能退役或清理。
- [backups.rs](../crates/platform-core/src/backups.rs) 同时有 SQLite、文件检查、ZIP 编解码和旧格式校验；按职责拆分后才能退役不再调用的部分。
- [lifecycle.rs](../crates/platform-core/src/lifecycle.rs) 的导出、复制、导入复用快照与校验，`initialize_candidate` 还会处理维护基线 ZIP；回收和恢复另有持久日志。
- [workspace.rs](../crates/platform-core/src/workspace.rs)、[history_cleanup.rs](../crates/platform-core/src/history_cleanup.rs) 保存目录身份和未解决现场保护。历史清理会核对来源 ZIP 和维护引用，须扩展识别 Git 恢复点，不能因为换格式而删除保护；工作区迁移本来会保留开发 `.git`，不得套用项目快照的排除规则。

## 6. 最小替换顺序与验收

| 顺序 | 工作 | 验收 |
| --- | --- | --- |
| 1 | 定稿 Git 工具选择、仓库位置、提交范围和 `dist` 分类策略 | 无 Git 行为明确；数据库去向明确；源码公开分享不携带私人历史；可恢复与仅保存源码状态分开 |
| 2 | 复用 SQLite 快照，用可丢弃网页样本生成 Git 恢复点 | 同时有未提交源码、未 checkpoint 数据、附件和旧运行版本的样本可完整记录；原开发分支/index 不变 |
| 3 | 从 Git 候选恢复，并验证省略 `dist` 的条件 | 断网、依赖缺失、构建失败、源文件变化均不破坏当前项目；数据和附件匹配；不能重建的版本有运行包或明确不能宣称完整恢复 |
| 4 | 将维护、导入/复制的隐含基线、任务和 UI 接到新恢复点，停止新路线的日常 ZIP 生成 | 无 Git 时拒绝新备份及依赖新基线的操作；正常应用使用与旧 ZIP 恢复仍可进行；提交中断后结果可辨识；旧现场清理正确识别新旧引用 |
| 5 | 接受支持的 Node 数据类型，再删真正无调用的旧写入路径 | 服务可靠停写、运行依赖齐备、配置不串用；旧 ZIP/维护/回收/恢复现场兼容；导出等仍需的代码不误删 |

本轮只做源码与文档审查，未运行恢复实验。下一步应先验证“Git 恢复点＋数据库快照”的小闭环；在它证明可替代以前，不删除已有 ZIP、`dist`、控制记录或项目管理能力。
