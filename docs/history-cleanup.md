# 历史资料清理与迁移收尾

2026-10-29 起，迁移原目录不再作为“空间 → 历史资料”的手动勾选对象。新迁移在复制核验、提交新位置，并确认新运行服务与原生管理器成功重新打开、旧访问实际结束后自动删除原目录；失败在“设置 › 存储位置”显示残留路径，按迁移 ID 重试。旧迁移 journal 不自动取得本轮删除权限。

<a id="可清理的历史资料2026-10-26"></a>

本页现役手动历史清理只处理网页项目的源码／数据取回原件。旧备份、回收站、Node 安装现场、程序旧版本与来源副本不提供本页的兼容清理入口；项目内容按[完整删除契约](project-complete-deletion.md)随所属项目处理。[操作记录精简与外部 AI 分工](operation-record-simplification.md)继续约束记录留存，下方链接中的历史验收仅证明当时版本。

## 网页取回原件的显式清理

“空间 → 历史资料”首次打开时自动扫描已登记的 `restoreOriginal` 对象，扫描不会删除文件，也不默认勾选。范围仅为 `.platform/project-state/data-restore/<项目>/<任务>/`、`source-restore/<项目>/<任务>/` 中，已经结束的取回操作所保留的 `original/`。完成、已撤回或未应用的状态须可核对；同一项目有任何未完成或无法核对的取回、数据保存与生命周期操作时，该项目的全部取回现场保留。

结果逐项展示完整路径、项目名称与 ID、逻辑字节、文件数、保留原因及清理范围。用户显式选择对象后，在确认弹窗勾选永久清理并确认外部 AI、编辑器与数据库工具已停止使用所选历史目录；界面发送服务要求的确认词“永久清理所选内容”。修改选择、刷新范围、切换页签、工作区变化或预检过期都会撤销确认。计划自生成起十分钟有效；客户端只提交服务返回的计划和对象 ID，不接受自定义路径或 `force`。

| CLI | 管理 HTTP | 原生命令 |
| --- | --- | --- |
| `workspace cleanup-plan --json` | `POST /api/v1/workspace/cleanup-plans` | `workspace_cleanup_preview` |
| `workspace cleanup --input request.json --json` | `POST /api/v1/workspace/cleanups` | `workspace_cleanup` |

两步均返回任务，HTTP 为 202，使用 `task get/wait` 查询；任务成功才表示该步完成。预览包含 `planId`、`expiresAt`（毫秒）、当前根、候选 `items`、`preserved` 与确认词。提交输入为：

```json
{
  "planId": "服务返回的计划 ID",
  "itemIds": ["服务返回的已选择取回原件 ID"],
  "confirmation": "永久清理所选内容"
}
```

计划绑定当前服务实例、工作区根身份与文件清单。未消费计划在重启后失效；同一已消费计划与相同选择返回原任务。响应未知时先查询原任务，不能盲目重放。原生命令校验管理窗口，HTTP 需要管理授权；项目网页和 SDK 不获得清理能力。旧客户端提交的迁移旧根候选不再接受。

清理只删除核对过的 `original/`，保留恢复 journal、任务和状态证据。仍被未解决操作引用的现场不授权清理；未登记路径、身份替换、路径重叠、嵌套挂载、特殊文件、无法核对的记录及新增或修改文件均阻止删除。迁移后 inode 已变化时，使用已提交迁移证明与内容摘要核对归属，再绑定当次预览的目录和文件身份。

执行与迁移互斥，并再次核对所选对象。当前业务项目不被重载，不清除业务草稿，也不改业务 SQLite 或源码。任务报告实际已删、失败与残留范围；部分删除不会恢复已经移除的文件，重新处理须重新扫描与确认。逻辑字节不等于实际释放的磁盘块。

## 迁移原目录自动收尾

公开工作区迁移仍使用复制、校验与提交新位置的流程，同卷也不直接重命名。平台暂停新工作，等待真实任务与文件 I/O，关闭旧数据库；提交后在新根重建运行服务与原生管理器，确认旧 HTTP、附件、下载、文件保存、受管 Node 后端与代理实际结束。只有取得这些收据后，才按照本次迁移明确登记的原根身份与清单删除原目录；新位置已经发生的正常业务写入不要求重新等于复制时的文件清单。

重新打开成功前中断，原目录保留；提交后不自动回源。旧业务窗口保留文档草稿和持有资源，要求用户明确关闭后重开或主动重新加载，不用自动销毁／刷新窗口来换取删除成功。已登记的外部原始源码若位于旧根内，迁移在复制前拒绝并给出路径，不移动、复制或建立兼容链接绕过保护。

`workspace info` 在迁移记录的 `sourceCleanup` 中返回：

| 字段 | 含义 |
| --- | --- |
| `phase` | `awaitingReopen` 等待成功重新打开；`pending` 尚有残留；`removed` 已删除；`absent` 已核对原路径不存在 |
| `cleanupPending` | 是否需要处理本次已授权的迁移原目录 |
| `completed` | 是否已经完成本次收尾 |
| `sourcePath` | 原目录绝对路径 |
| `error` | 失败原因，存在时展示，不据此改变当前工作区 |

自动启动与手动重试的任务通过独立 `migrationCleanupTask` 返回，类型为 `workspaceMigrationCleanup`；它不占用 `activeTask` 或手动历史清理的 `cleanupTask`。清理失败时新位置继续可用，设置页显示残留路径和“重试删除原目录”。该重试只接收迁移 ID：

| CLI | 管理 HTTP | 原生命令 |
| --- | --- | --- |
| `workspace cleanup-retry MIGRATION_ID --json` | `POST /api/v1/workspace/migrations/{migrationId}/cleanup` | `workspace_migration_cleanup({migrationId})` |

返回任务沿用 `task get/wait` 查询。重试仍核对已提交复制／校验收据、当前目标选择与身份、原根身份和剩余清单；遇到原根新增／修改内容或身份变化保留残留并报告原因，不接受任意路径、旧 journal 收养或通用递归删除。新工作区业务继续使用，后续迁移与冲突的管理操作须等本次收尾处理完毕。

## 历史结果与验证边界

2026-10-16 至 2026-10-27 的旧根、回收站、Node 安装材料和恢复现场清理要求及真实结果保留在[历史清理验证](history-cleanup-verification.md)、[原生 GUI 验证](history-cleanup-gui-verification.md)及对应旧阶段记录中，不作为当前候选或自动清理授权。设置中的[卸载前全量清理](local-data-cleanup.md)仍有独立范围与确认流程，不能用它放宽普通历史清理。

文件系统身份核对依赖外部工具按约定停止写入旧目录，不承诺把同一 macOS 用户的恶意并发篡改隔离成安全沙箱。真实服务、实际删除、重开与剩余资料核对的结果另记；模拟 UI 或编译通过不替代原生及真实删除验收。
