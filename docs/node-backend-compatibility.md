# Node 后端兼容性记录

日期：2026-11-02。适用于当前 `panda.json` Node 应用，现行入口和数据规则见[Node 单目录运行](node-single-directory.md)。本文记录本轮源码修正及尚未覆盖的情况，不扩展 SSR、多服务、其他运行时或旧项目格式支持。

本文的源码行为与用户当前安装的 `.app` 分开核对。修改仓库不等于重新打包、安装或更新正在使用的平台；本轮也不修改已添加的 Readio 项目及其业务数据。实际验证结果在末节填写。

## 本次发现与修正范围

Readio 的两次运行日志均显示：进程启动，应用写出 `Ready` 诊断，平台随即以 `startup-rollback` 原因关闭进程，最后退出码为 0。代码检查发现其健康回复使用 Node `writeHead(...).end(JSON.stringify(...))`，没有显式声明 `Content-Length`；原平台健康探测手工读取 TCP 数据并拒绝 `Transfer-Encoding`，因此不能接受这类正常的 HTTP 分块回复。日志未记录原始回复和具体失败原因，单凭这些日志不能声称已动态复现。

原实现还以连接关闭作为回复完成条件，即使已经收到声明长度的完整正文，也继续等待 EOF；健康 JSON 则要求整个对象完全相同，附带 `uptime` 等信息也会被拒绝。启动错误只对外保留通用文案，运行中健康检查也把具体错误压成了“异常”。这些限制和诊断缺失会增加应用接入及排查成本。

本轮源码调整集中在[运行管理器](../crates/platform-core/src/node_runtime_trial.rs)及[应用启停管理](../crates/platform-core/src/node_apps.rs)：

- 健康探测改用 Hyper 的标准 HTTP/1 解码，支持分块回复、按 `Content-Length` 完成的回复和以连接关闭结束的回复。收到完整的声明长度正文后即可判断结果，不必等待后端关闭连接。截断、不完整或无效 HTTP 仍拒绝。
- 健康检查要求 HTTP 状态为 `200`，JSON 中 `protocolVersion` 为整数 `1`、`instanceId` 为本次实例标识、`status` 为字符串 `"ok"`；允许对象附带其他元数据，但这些字段不能替代或改变必要字段。
- 启动失败记录所处阶段；启动及运行中健康检查失败保留固定原因码，以及已收到回复时的 HTTP 状态。诊断不记录健康正文、认证头或令牌，不直接转发应用返回的任意错误文字。启动失败的界面及 AI 求助文案使用固定的中文原因，不再只剩通用启动失败提示。

## 健康检查保持的边界

| 项目 | 当前约定 |
| --- | --- |
| 连接目标 | 本次应用报告且已验证的 `127.0.0.1` 端口，直接连接 |
| 外部代理与跳转 | 不读取系统 HTTP 代理，不跟随重定向，不将认证转发给其他地址 |
| 路径和认证 | 固定 `GET /_platform/health`，携带本次实例 Bearer 认证 |
| HTTP 状态和实例 | 必须为 `200`，必要 JSON 字段的类型、值和实例身份必须正确 |
| 响应头预算 | 16 KiB |
| 解码后正文预算 | 16 KiB；分块传输同样按解码后的正文累计 |
| 整次请求预算 | 3 秒，包含连接、回复头和正文接收 |

支持标准 HTTP 传输格式不等于接受任意回复或任意目标。身份不符、认证失败、跳转、非成功状态、无效 JSON、超时、超量和截断回复仍属失败。健康检查只检查本机服务，不访问 AI、TTS 等上游，不把第三方服务故障等同于本机进程故障。

stdout 仍只允许平台协议消息，stderr 才是普通日志。控制消息的版本、实例身份、字段和大小检查，以及停止时对真实进程和受管后代的核对继续保留；允许健康 JSON 的额外元数据不会放宽 stdout 控制协议。

## 当前接入限制与后续工作

下列事项不随本次健康 HTTP 修正一并改变。它们应在[作者说明](../skills/local-projects-app/SKILL.md)中明确，不能因为应用通过健康检查就推断所有业务接口都兼容。

| 情况 | 当前行为及影响 | 后续处理方向 |
| --- | --- | --- |
| API 路径 | [网页代理](../crates/platform-core/src/node_app_proxy.rs)仅转发首段为 `/api` 或 `/tts` 的地址。其他 GET/HEAD 走静态文件逻辑，其他方法拒绝。Readio 的后端业务接口使用 `/v1`，因此健康修好后仍需单独检查网页请求路径 | 明确支持的代理入口；新增通用入口或声明路由需要统一设计，不能把所有缺失静态文件都自动交给后端 |
| 请求正文 | 业务代理当前最多接收 64 KiB，读取预算 15 秒；长文章、批量 JSON、上传可能在到达应用前被拒绝 | 保留预算并写明适用范围；更大上传或按路由配置预算另行设计 |
| HTTP 请求头 | 代理当前仅转发 `Accept`、`Content-Type`、`Range`、`If-Range`，自行设置后端认证；条件请求、SSE 恢复、幂等键等不能假定透明传递 | 按用途补充明确的头部列表，继续隔离平台认证、浏览器 Cookie 和管理头 |
| HTTP 响应头 | 代理仅保留现有列表中的内容类型、长度、Range、ETag 和修改时间；下载文件名、压缩正文等语义可能受影响 | 单独验证 `Content-Disposition`、`Content-Encoding` 等用途，避免只传正文而丢失必要解释信息 |
| 业务重定向与 WebSocket | 当前不支持，代理拒绝跳转与连接升级 | 属于受控代理的现行能力边界；OAuth、跳转和 WebSocket 须有独立契约与验收，不能直接放行 |

运行控制预算也应明确公布：每行 stdout 控制消息最多 8 KiB，启动握手与健康确认共 10 秒，单次健康请求 3 秒，正常停止宽限 5 秒。业务代理等待回复头最多 120 秒。上述预算用于限制资源占用和保证启停可收尾；本次不修改它们，也不将超时预算本身认定为缺陷。

固定 Node 主版本、完整可运行入口、Git 添加不执行安装脚本、配置与密钥隔离、同源认证和受管进程停止均是现行契约。普通项目可能需要适配这些条件；不能把取消这些边界当作一般兼容性修复。

## 验证计划与实际结果

验证只使用独立、明确可丢弃的夹具，不启动真实 Readio、不读真实 `.env`、密钥、业务数据库或附件。

| 检查 | 计划覆盖 | 实际结果 |
| --- | --- | --- |
| 标准 HTTP/1 回复 | 分块传输、声明长度且保持连接、关闭连接定界 | HTTP 专项共 10 项通过，含分段写入、块扩展、尾部头和 100 中间回复 |
| 健康身份 | 正确三字段及额外元数据通过；错误版本、类型、实例、状态拒绝 | 身份矩阵通过，含整数/字符串/浮点版本区别 |
| 失败与资源预算 | HTTP 非 200、跳转、无效 JSON、截断正文、头部或正文超量、总超时 | 专项通过；完成及超时后均核对模拟服务器实际观察到客户端断开，无后台连接任务 |
| 安全诊断 | 记录阶段、固定码和可用 HTTP 状态；不回显应用原始消息 | 启动控制失败、启动健康 503、运行中健康 503 的日志回归通过；中文原因映射和管理器返回文案断言通过 |
| 启停回归 | 失败后回收本次资源；正常关闭和受管进程归属检查继续通过 | 核心库首轮 756 通过、5 项测试环境失败、12 按原规则忽略；改用随包开发 Node 24 重跑失败的 5 项，全部通过 |
| 真实 Node | 固定私有 Node 的分块健康回复、ping、停止与进程身份 | 显式执行 `pinned_node_runs_disposable_javascript_and_stops` 通过；夹具改为不声明 Content-Length 的标准 Node 回复；只操作临时项目 |
| 编译与静态检查 | 共享核心及全部目标 | `cargo clippy --locked -p platform-core --all-targets -- -D warnings`、`cargo fmt --all -- --check` 和 `git diff --check` 通过；没有新增依赖或界面类型变更 |
| 双平台 CI 与安装包 | macOS/Windows CI、已安装平台及 Readio 实际功能 | 本地为 macOS；双平台 CI 尚待核对，未运行 Windows 实机检查；未重新打包或替换已安装 `.app`，未运行真实 Readio |

首轮 5 项环境失败均为 `web_build::tests::invocation` 在 PATH 上发现本机 Node 26，而现行开发环境只支持 Node 22.12+/24；使用随包 Node 24 后通过。没有修改宿主 Node、测试断言或支持版本来绕过失败。其余 756 项无需重复执行。核心默认组的 12 项 opt-in 测试仍按原规则忽略，真实私有 Node 分块回归为其中显式单独执行的一项，不能把这些数量当作 Windows 或完整产品 GUI 验收。

夹具通过只证明所覆盖的协议和资源行为；不等于已安装平台更新、不等于 Readio 实际业务已验证，也不代替 Windows 运行验收。发布或安装验证需另记使用的包版本、检查及限制。
