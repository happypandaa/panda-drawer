# 停止并删除：第二阶段协调器与锁设计

2026-10-28 用户确认总体设计，并补充“任何目标改名前可放弃”、复杂已接纳操作可等待自然结束、网页范围说明及第 1 批后打包要求。本说明记录确认后的实施约定，具体已完成能力与验证按各批报告记录，不能将设计当作已实现。第一阶段结果及 Git 导入目录关系见[第一阶段报告](stop-and-delete-phase1.md)。

## 实际结构与必须改变的地方

当前有两层全局异步锁：

| 位置 | 当前职责和等待范围 | 本阶段调整 |
| --- | --- | --- |
| `apps/desktop/src-tauri/src/node_windows.rs::NodeWindows.operations` | 管理窗口打开、关闭、重启、删除和更新；开发／Git／源码发布入口也会持有它等待 | 保留短暂的准入、窗口登记与提交协调；停止、窗口销毁回执、任务退场、复制或递归删除期间不持有它 |
| `crates/platform-core/src/node_apps.rs::NodeApps.inner` | 保存全部实例的运行 owner、标记 owner、错误与退出门禁；启动、停止、monitor、stop_all 均可能持锁等待 | 保留全局表查找与短提交；资源 owner 移入稳定的每实例控制对象，等待在该实例范围内进行 |

当前 `node_app_delete.rs::delete` 还把 `OwnedMutexGuard<Inner>` 交给整个递归删除线程，因此慢删除会占住内层全局锁。第二阶段改为后台任务持有实例操作归属和资源 owner，不携带全局锁。

删除不能直接调用公开 `close()`：二者都会获取同一把 `operations` 锁。窗口 `Destroyed` 回调的后续 session 清理也会取该锁，不能持锁等待 session 消失。

本阶段不重写为完整 actor 系统，也不保证所有实例间完全没有短暂等待。共享源码、安装提交、恢复事务、全平台退出和工作区迁移仍按原有共享协调执行；只涉及独立实例的耗时收尾不能占住全局锁。

## 每实例操作归属

全局表按实例 ID 保存稳定的 `Arc` 控制对象。实例对象保存运行／proxy／标记 owner、当前操作和删除任务引用。请求取消、前端超时或关闭管理弹窗都不能移走最后一份 owner。

实例对外状态为：空闲、运行中、停止中、删除中、已删除、删除失败。删除期间另有阶段：正在结束当前操作、正在关闭窗口、正在停止、正在暂存、正在删除、正在清理登记。删除阶段不能被普通状态刷新覆盖成可启动。

公开的停止和删除入口分别取得该实例操作归属，然后调用同一个“不再获取操作锁”的内部停止函数。内部函数只做窗口／运行资源收尾，不调用会再次取得锁的公开关闭、删除或配置读取入口。删除已经持有归属时，关闭请求合并到该次收尾；不会等待一项反过来等自己的操作。

锁顺序固定为：短暂获取全局表并克隆实例引用 → 释放全局锁 → 取得实例操作归属 → 必要时短暂提交元数据。不得持任何全局锁等待实例操作归属、窗口回执、进程、reader、proxy、文件复制或递归删除。元数据提交不得回调等待实例操作的接口。

窗口按现有 `WindowLifetimes` 的精确 generation 等待 `Destroyed` 回执。销毁事件先记录回执，session 清理用短锁完成；等待者不能以 session 是否消失作为唯一凭据，也不能在删除中重建旧窗口。

## 操作准入规则

删除受理必须先持久化任务和删除门禁，成功后才返回任务 ID、执行关闭。仅写实例目录内的 `registration.json.removalPending` 不够：目录改名或登记移除后，该 ID 仍须被删除任务封住。

| 操作 | 删除中／删除失败且尚未收尾时 |
| --- | --- |
| 启动、打开新窗口、重启 | 立即拒绝，返回原删除任务与当前阶段；不排队自动启动 |
| 构建、更新准备／应用、Git 读写命令、源码绑定／取回／发布、配置写入 | 新请求立即拒绝；不在删除后补执行 |
| 同实例安装提交、内部可重建配置／目录的入口 | 同样检查持久任务门禁，包括登记已不在原路径时 |
| 列表、已有诊断、删除进度和失败原因 | 允许读取安全快照，不等待资源停止锁；不为展示重建配置目录 |
| 关闭、停止、窗口销毁后的清理 | 合并到已有收尾，复用同一 owner 和回执 |
| 再次点击删除 | 返回原任务，不创建第二份删除，也不重复发送信号 |
| 删除失败后明确重试 | 恢复同一任务，重新核对身份；保持启动门禁 |
| 放弃删除 | 仅在从未改名任何目标、且已排除正在发生的改名时允许；结束删除 runner、持久化已放弃后撤销删除门禁，不自动启动 |
| 其他实例操作 | 正常准入，仅真正共享来源或短元数据临界区仍需协调 |

原有 `require_not_removing`、开发操作 guard、安装最终指针检查和桌面窗口入口都须使用同一门禁。不能只在按钮处或只在 `NodeApps::start` 检查。

## 删除前已接纳的操作

删除先封住新操作，再收尾已有 owner，不能直接报告“有任务，不能删”就结束：

1. 已接纳的启动请求不再创建窗口；在可安全取消的阶段取消，否则接回返回的 owner 后停止。
2. 构建和安装准备可通过现有取消入口停止，等待其真实进程、reader、任务 owner 完成收尾。取消请求发出不等于已停止；若对应任务的安全取消交接复杂，第 1 批可先等待其自然结束并展示具体操作。
3. 已进入短安装提交的 apply 不硬中断，等待提交结束；已接纳的 Git 写入／恢复、源码发布和共享来源恢复先等待自然结束，显示“等待 Git 操作完成”“等待源码发布完成”或“等待应用更新提交完成”。仍沿用现有事务和恢复协调，不在写盘临界点强杀或删除恢复证据。
4. 已接纳操作只能凭原 token 完成当前事务的安全收尾，不得因删除门禁而在半次写盘中失去归属；该 token 不允许继续开启新工作。
5. 收尾后重新核对用户确认的实例身份和范围。若已有提交令目标身份被替换、范围变化或留下未解决恢复材料，删除任务明确失败并报告原因；不能自动重新绑定到替换对象或扩大删除范围。

等待上述退场不持两层全局锁。平台受理后的删除由后台 owner 执行，前端请求结束或观察超时均不释放归属。只读预览可直接取消；受理后的“放弃删除”是显式任务操作，适用下节条件，不能用请求取消或关闭弹窗代替。

第 1 批入口范围与规模：

| 入口组 | 具体入口／实现位置 | 已接纳请求的处理 |
| --- | --- | --- |
| 窗口与运行 | `node_windows` 的 open／close／restart／delete／apply_install、Destroyed 与 reconcile；`NodeApps` 的 start／stop／restart／monitor／stop_all | 共享实例归属；阻止迟到窗口；接回实际 owner 后停止，销毁按精确 generation 回执收尾 |
| 配置和实例登记 | `node_app_configuration_save`、Node 配置存储、安装最终指针提交、目录登记与开发绑定 | 新写入须先过同一准入；短提交完成后交接，不能在提交中间撤销归属 |
| 构建和安装准备 | `node_development_build`、`NodeDevelopmentTasks`、`node_install_prepare`／`NodeInstallTasks` | 优先复用真实任务取消与排空；不能安全取消时等待自然结束，不能仅丢弃等待 future |
| Git 与源码 | `node_development_git` 的 status／versions／restore-preview／restore-apply／restore-status／restore-recover，开发绑定、源码 lease、`source_import_publish`／`source_import_recover` | 现有 owner 完成当前事务；新请求拒绝。发布和恢复保留共享来源协调，不新增全局强制取消 |
| 全平台协调 | `stop_all`、正常退出、工作区迁移的 task／lease | 短锁取得实例引用，实际等待在锁外；保留共享协调 |

第 1 批预计修改十余个实现和测试文件，分布在原生桌面入口、core Node 运行／删除及开发／安装协调，实际数量以提交为准。风险最高的是“封住新请求”和“接回旧 owner”的原子交接：如果只有先检查再设置门禁，可能漏入启动；如果旧 token 因新门禁突然失效，可能在复制或恢复半途丢掉真实工作。其次是窗口 Destroyed 清理与调用者互等、等待者取消后资源归属丢失。这些边界优先用临时项目与实际子进程覆盖。

## 改名前放弃删除

任务记录增加持久的“已放弃”结果和单调的“曾改名目标”证据。只要任一目录曾成功进入该任务的暂存位置，即使它随后已被递归删除，也永远不再提供放弃，不能因为当前暂存为空而重新放行。

“放弃”与进入改名阶段必须由同一实例协调器裁定。改名意图已写入但结果尚不明确时，先核对原位置和独占暂存位置，不能把“尚未写入改名完成”当作“从未改名”。放弃受理后先确保该删除 runner 不会继续进入下一阶段，持久化已放弃，再撤销删除门禁；任务历史保留，旧任务不能因平台重启再次续删。已有普通操作仍保留自己的 owner 和事务规则。

放弃不恢复已关闭窗口、不自动启动应用，也不把尚存活或无法核实的运行假报为已停止。能确认资源已停的实例显示停止；停止失败时，删除门禁可以撤销，但独立的运行／恢复门禁及真实状态继续存在，不能因此启动第二实例。

删除失败界面同时提供“重试”和条件允许时的“放弃删除”，靠近失败原因说明当前是否仍可放弃。任一目标已改名后仅提供重试／继续及实际剩余结果。等待旧操作自然退场而尚未改名时也允许主动放弃，不要求用户先等它结束才退出删除任务。

## 持久任务和分卷暂存

持久任务存放在固定开发数据根 `D/node-deletion-tasks/<任务UUID>/`，独立于 `D/node-apps/<实例UUID>/`。记录实例身份、确认修订、操作阶段、每个目标的路径／目录身份／卷身份、改名意图、暂存位置、曾改名证据、清理结果、已放弃结果和明确保留原因。使用已有受限写盘／原子提交方式，不添加任意根覆盖入口。

每个目标在其实际父目录所在卷创建专属待清理位置，不能假设工作区与固定数据根同卷。第二阶段白名单是实例内的配置、数据、缓存和受管代次，实际暂存位置为 `D/node-apps/<实例UUID>/.pending-deletions/<任务UUID>/`；完整计划发布前核对所有目标同卷且不是已知挂载点。若后续确认删除整个实例目录，暂存必须上移到实例之外，例如 `D/node-apps/.pending-deletions/<任务UUID>/`；独立受管源码则在其所在卷另建专属位置。外部用户源码目录不进入目标计划，不改名、不删除。挂载点、卷不可用、目录身份变化或无法原子改名时报告失败，不降级为跨卷复制后删除。

每个目标逐项执行：持久化该项改名意图 → 精确身份核对 → 同卷不覆盖原子改名 → 持久化暂存完成 → 后台递归删除 → 持久化该项完成。不同卷、多个目录不能伪称为一次原子删除。

若崩溃发生在改名与任务更新之间，重启后根据原位置和该任务独占暂存位置的目录身份核对，不凭同名猜测。身份不明、路径被替换或卷不可用时保留现场并报告；不追踪或清理其他目录。登记、引用和平台生成数据的每项清理也需有实际结果，全部完成后才报告成功。

第二阶段先沿用当前已确认的实际删除目标。完整实例槽、独立受管源码、共享来源和安装库的最终范围按第一阶段目录表另行确认后在第三阶段接入；不能以暂存改造顺便扩大范围。无法证明独占的受管源码须列入“以下目录未删除”及原因，共享来源／安装库仅清引用。

## 退出、重启和失败

- 删除任务注册到现有共享 task／lease 协调，迁移能看见它；迁移不能在删除后台仍写盘时移动工作区。
- 平台启动先加载删除任务门禁，再核对运行标记和恢复已确认任务。未完成任务显示“删除未完成”，不回到可运行列表，也不打开应用窗口。
- 停止使用第一阶段身份规则：关闭目标窗口，SIGTERM 等 5 秒，必要时重核身份后 SIGKILL 等 2 秒。仍有活进程或身份不足则任务失败，明确提示重启电脑；不无限等待，也不因超时准许再开一个删除任务。
- 正常退出先封住新操作；`stop_all` 用短锁取得实例引用，在实例范围内等待收尾。已有删除和共享源码事务继续受退出协调约束，不能让失去 owner 的后台写盘继续运行。
- 已停止但只删掉一部分时列出完成、未完成和保留部分，不显示成功，不重新启动。下次启动可继续清理已确认、归属可核实的暂存目录；用户无需再次确认原范围。
- 删除失败是本次执行的明确结果；未明确放弃时删除授权和门禁仍保留，再次删除复用该任务。满足改名前条件且明确放弃后，旧任务保持已放弃，不再续删。若需要新的范围或替换对象，必须重新展示范围并由用户确认，不能静默改变原授权。

## 网页项目的处理范围

本轮第二阶段三批实现针对 Node 应用。网页项目当前由 `service.rs::project_delete` 提交到 `LifecycleManager::submit_project("delete")`，已经使用 `TaskRegistry`／项目 lease、`W/.platform/operations/<任务ID>/` 持久 journal 和 `W/.platform/project-state/deleting/<项目ID>.json` 删除门禁；确认身份绑定为 `expectedDocumentEpoch`。`lifecycle.rs::delete` 冻结业务写入、取得项目独占 gate、关闭数据库并核对恢复门禁后，直接递归删除已确认的项目根目录，**没有先改名到暂存位置**。

网页项目重启时的 `reconcile_direct_delete` 在原目录已消失且任务身份仍匹配时完成登记收尾；原目录仍存在则报告 `delete_incomplete`／剩余路径，要求明确重试，当前不自动继续递归删除。删除门禁仍阻止重开、同 ID 登记及迁移。它没有 Node 的进程身份、PGID、运行标记或原生业务窗口收尾步骤，也没有新增的“改名前可放弃”接口。

| 行为 | 本轮 Node 目标 | 网页当前实现 |
| --- | --- | --- |
| 持久记录与身份 | 固定数据根的 Node 删除任务，绑定实例修订及目录／卷身份 | 工作区 lifecycle journal 与 project-state 删除标记，绑定文档 epoch 和项目根身份 |
| 停止 | 关闭目标原生窗口、停止独立进程组、排空平台 proxy／reader | 冻结项目写入、独占项目 gate、关闭数据库及业务会话 |
| 文件阶段 | 同卷逐目录原子改名、后台删除、逐项记账 | 原项目目录直接递归删除，可能在原位置部分完成 |
| 崩溃后 | 核对归属后续删已确认暂存，已放弃任务不续删 | 目录已不存在时收尾；仍存在时报告结果并等明确重试 |
| 放弃 | 从未改名任何目标、且改名不在进行中时可明确放弃 | 尚无本次新增能力，不能借“从未改名”认定仍安全可放弃，因为可能已原地删过文件 |

不把现有网页 journal 直接交给 Node 删除 runner：网页已有项目 epoch、维护／数据库恢复协议和原地部分删除历史，与 Node 实例槽及进程 owner 不同，直接共用会误判历史任务是否还能放弃、是否已进入不可逆阶段。本轮复用现有底层 task／lease、目录身份和安全文件操作能力，不强行共用同一个任务 schema 或恢复器。

建议在本轮 Node 三批验收后，把网页接入同卷暂存、逐项目标记、放弃条件和续删行为列为单独的后续适配批次，并先确认旧网页中断任务的兼容规则。适配时可以抽取已经验证的暂存／任务状态原语，但网页停止、epoch 核对和旧 journal 恢复仍由网页适配层负责。这项后续范围尚未确认，当前不会修改网页删除行为，也不阻塞 Node 第 1 批。

## 分批实现与验收安排

1. 实例准入与 owner／锁拆分：覆盖关闭和删除互等、窗口销毁回执、monitor／stop_all、前端等待者丢失、删除中启动／构建／更新／Git 被拒及另一应用仍可运行。检查后提交推送并重新打包，供用户安装后重启电脑验证 Radio Bob 的遗留标记清理。
2. 外部任务与同卷多目录暂存：覆盖各持久化点崩溃、重启续删、目录替换、卷不可用、部分失败、重复点击复用原任务，以及改名前放弃／改名后永久禁用放弃的持久判定。
3. 对接删除阶段快照与结果展示，包括“等待 X 完成”、失败时重试和条件放弃；第三阶段再按确认范围调整最终按钮和确认文案。

每个实现步骤完成相关检查后提交并推送。测试只用明确命名的临时项目；外部源码设置哨兵，另一实例独立运行。崩溃测试只杀测试平台进程，不删除用户现有项目、不用真实源码验证永久删除。
