# 熊猫抽屉最终目标

确认日期：2026-10-21。

状态：用户已明确确认下述最终目标、四类场景的目标结果，以及先解决技术能力、再完善设计交互与使用提示的推进顺序。最新取舍是仅保留 Git 版本管理，去掉独立本地备份体系。支持范围、详细验收标准和实施计划应由此推导；目标确认不表示相关功能已经交付，也不将此前的具体实现建议自动升级为实施契约。

## 已确认的最终目标

把熊猫抽屉做成普通用户管理个人小应用的平台：用户可以借助外部 AI 制作应用，也可以通过链接或应用包获取别人制作的应用，在本机方便地运行、保存数据、定制和分享。平台负责处理受支持应用的获取、运行、配置、版本与数据保护，减少用户复制代码、操作终端和配置环境的负担。

这里的数据保护按最新取舍收敛为正常持久化、操作失败不损坏当前实例，以及用户主动保存的 Git 版本；不再包含独立本地备份产品或另一套私有 Git 恢复仓库。已有资料与未完成现场继续保全。

## 四类场景的目标结果

| 使用场景 | 最终应达到的结果 |
| --- | --- |
| 自己制作、自用 | 从想法出发，交给 AI 制作，完成检查后能长期稳定使用。 |
| 获取别人项目 | 粘贴链接或选择应用包，完成必要配置后使用；需要适配的源码有清楚的后续路径。 |
| 分享自己的项目 | 生成别人能接收、安装和使用的交付物，清楚控制是否附源码、示例资料和个人数据。 |
| 修改与定制 | 能改配置或交给 AI 改功能，验证后应用新版；失败保留当前可用程序，能取回已保存的 Git 版本，普通更新保留业务数据。 |

这四条完整路径是后续制定验收标准的依据。单独下载成功、构建通过或应用能打开，不能代替对应路径的完整验收。

## 已确认的推进顺序

用户进一步明确：为了最终目标，优先解决技术问题，包括 Git 所涉及的项目获取能力，随后再解决设计、交互和使用方法提示。此前以界面整理起步的候选批次，应据此重新排列。

技术计划需要覆盖工具环境、获取、Git 版本、开发构建、安装、运行、定制更新与分享之间的依赖。Git 版本管理方向已确认；其实现、分发方式和操作范围仍需明确。

技术步骤仍需保障正常数据保存、必要停写、候选验证和失败保留当前实例，不再要求先补齐完整备份、恢复、复制与回收体系才能开放新类型安装。技术步骤提供验证该能力所需的最小入口、状态及必要配置与错误说明，完整视觉和交互优化随后推进。用户说明与 AI 开发说明继续随实际交付维护。

## 确认范围与待细化事项

内置 Git 是服务源码获取和定制的候选技术手段；是否打包、采用何种实现及开放哪些版本操作，仍需由目标和支持范围推导。此次确认没有批准安装 Git、修改运行代码或执行项目迁移。

此前讨论的入口、详情和状态整理，Node 数据持久化与运行协调，标准应用包、本地安装、干净分享和使用说明，继续作为候选工作内容；原第一、第二批的顺序不再作为执行依据。数据库纳入 Git 的方向保留，`dist` 是否提交仍待评估。独立备份及其强制前置按本次选择退出，旧资料不删除。

## 后续计划的制定顺序

按“最终目标 → 支持范围 → 验收标准 → 能力缺口 → 整体计划 → 分批实施”的顺序推进。

在上述规划顺序下，实施优先打通技术能力与完整使用路径，再完善设计、交互和使用提示。每个实施步骤应说明它服务哪条使用路径、依赖哪些已确认条件、交付什么结果，以及怎样验证。具体计划继续映射到现有 M0–M6、AP、NR 和 Windows 工作线，不因重新梳理目标而改写其编号或完成状态。

当前整理结果见[技术实施计划](technical-implementation-plan.md)，含现状、Git/开发工具建议、10 项修改、依赖和验收矩阵，替代原 32 步。取舍已确认，具体推荐实现仍需在对应步骤细化，既有功能完成状态不因重排而改变。
