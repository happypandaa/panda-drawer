# 网页应用包安装与分享设计

状态：v0.2，设计讨论稿；专用清单和目录分工已按用户要求汇总到[格式 v1](project-and-app-format-v1.md)；安装尚未实现，初始化、更新、预算等细则仍为候选

更新日期：2026-10-19

本文件保留安装与分享的完整设计背景；开发者和 AI 从[《项目与应用包格式 v1》](project-and-app-format-v1.md)读取当前格式入口、Schema、示例及实现状态。`local-app.json` 是外部包的目标清单，不是当前受管项目 `project.json` 的替代文件，也不是现有 ZIP 导入入口。2026-10-19 本轮只整理文档和规范文件，不实现安装功能，不将下述候选方案自动升级为已确认运行契约。

用户可以安装在外部开发、已经构建好的网页应用。用户选择应用包目录，平台先读取专用说明文件，再检测内容和兼容要求；通过检查并确认后，把程序复制到当前工作区。应用可以不带源码，安装后不依赖原目录、开发者电脑或 GitHub 在线状态。

本文面向平台开发者、应用开发者及协助打包的 AI，规定应用包、目录检测、错误说明、GitHub 分发、环境和初始数据的拟议规则。它不授权实施代码，也不修改已有项目的源码、SDK、数据库、附件、维护和恢复记录。

## 1 已确认方向与本次设计范围

已确认的方向是：安装对象为 HTML、JavaScript、CSS 等网页构建产物；复制到受管目录；源码可选；必须先找到专用说明文件；检测发现问题时给出具体原因和处理办法；支持开发者通过 GitHub 分享应用，并说明接收者的环境要求。

文件名 `local-app.json` 与两类目录角色已作为格式 v1 的目标文档整理；严格字段、错误码、初始数据库快照、相同数据版本的更新规则和检测预算仍须按新规范的状态列理解，其中初始化/更新/预算细则继续保留为候选。文档和 Schema 示例不代表已经存在的安装接口或正式发行版本。

| 项目 | 本次设计 |
| --- | --- |
| 用户入口 | 添加应用 → 选择目录 → 检测 → 确认安装 |
| 首版输入 | 本机目录；下载的 ZIP 由用户解压后选择包根目录 |
| 运行方式 | 平台提供本地网页服务、独立项目窗口及已有浏览器入口 |
| 存储归属 | 安装后的程序和用户数据均在当前工作区；原包只读 |
| 首版不提供 | 自动克隆 GitHub、从源码安装依赖或构建、直接输入仓库链接安装、ZIP 内置解包、应用市场或后台自动更新 |
| 不支持的运行类型 | 需要本机独立 Node/Python 服务、SSR 服务、Docker、原生可执行程序或额外数据库服务的应用 |

公开 HTTPS 接口仍按[运行能力约定](project-capabilities-and-secrets.md)使用。应用自行运行的本地后端与声明的远程公开接口是两类依赖，不能混为一谈。

“安装应用包”与现有“导入完整项目备份”分开。后者包含某个项目实例的数据库和附件，适用于迁移与恢复；应用分享包默认不含开发者的个人业务数据。[现有生命周期约定](project-lifecycle-and-workspace.md)中没有源码的分发包仍属后续范围，不能直接套用完整项目校验。

## 2 用户操作与安装结果

1. 用户点击“添加应用”，选择目录并在系统目录选择框确认。这里的确认只选定检查对象，不立即安装。
2. 检查所选目录根部的 `local-app.json`。缺失时停止，提示选择包含该文件的应用包目录，并提供打包规范入口；不递归搜索、不猜测 `dist/` 或 `build/`，也不因为找到 `index.html` 就开始安装。
3. 文件存在时解析清单，检查声明范围，生成受管暂存副本，在该副本上完成静态和初始数据检查。原目录始终只读；不打开应用网页、不执行包内脚本。
4. 展示应用名称、作者声明的版本、实际将安装的内容、是否包含源码、初始数据摘要、所需平台能力、联网和设备需求，以及检测问题。
5. 检查通过后启用“安装”。用户确认所展示的具体包；后台任务完成并持久登记成功后，应用才进入可打开列表。首次打开由用户主动触发。

目录格式、文件路径、平台版本等由程序读取，普通用户无需填写。原包无效时不让用户临时猜字段、关闭检查或手动修改数据库来完成安装。

检测结果与任务状态分别表达：

| 检测结果 | 含义 | 操作 |
| --- | --- | --- |
| `passed` 基础兼容检查通过 | 必需检查完成，没有已知阻断问题；运行行为尚未验证 | 可以确认安装；同时显示未验证事项 |
| `blocked` 暂不能安装 | 缺少清单、格式错误、必需文件缺失或确定不兼容 | 显示具体问题；修复或重新选择后检测 |
| `incomplete` 检测未完成 | 读取失败、超过检查预算、文件变化或任务中断 | 原因消除后重试；不能解释为应用不兼容 |

候选目录不明确的问题通过“必须选择说明文件所在根目录”解决。多个 HTML 文件可以是同一个多页面应用，入口由清单决定。缺少必需运行声明属于阻断，不让用户确认后跳过；只能运行时判断的事项属于提示，不能伪装成已通过。

安装使用现有持久任务状态 `queued → running → succeeded | failed | interrupted`。检测通过不等于安装完成，安装完成也不等于所有业务功能已经测试通过。

## 3 应用包目录

建议的完整包布局如下；目录名通过清单声明，只有根部 `local-app.json` 固定：

```text
wordbook-1.0.0/
├── local-app.json
├── dist/
│   ├── index.html
│   └── assets/                  JS、CSS、图片、字体等运行资源
├── meta/
│   └── icon.png                可选
├── docs/
│   ├── README.md               可选使用说明
│   ├── data.md                 使用初始数据库时必需
│   └── development.md          附带源码时的可选说明
├── initial-data/               仅 seed 模式需要
│   ├── main.sqlite
│   └── attachments/            可选初始附件
└── source/                     可选源码资料，不参与安装执行
```

只复制说明文件，以及它声明的网页根、图标、文档、初始数据和可选源码范围。其他文件显示为“未纳入安装”，不整仓库盲拷；排除范围内的变化不影响包摘要。声明范围内不静默忽略文件，未知文件也必须计入体积、文件清单和内容摘要。

各声明目录不能互相包含；独立声明文件不能落在另一声明目录内，`web.entry` 作为网页根内入口除外。种子附件目录与种子数据库文件可以共用 `initial-data/` 父目录，但前者不能包含后者。网页入口只能引用网页根内的运行资源，不能把源码、初始数据库或文档根作为资源补齐来源。

包内声明路径使用 `/`，相对包根；`web.entry` 唯一例外，相对 `web.root`。拒绝空路径、绝对路径、`.`、`..`、反斜杠、控制字符和路径别名冲突。文件名必须可按 UTF-8 处理；按目标文件系统规则检查大小写及 Unicode 名称碰撞。应用包路径规则与 HTML 中合法的相对资源解析分开：网页中的 `../` 可以指向网页根内文件，不能越出网页根。

声明范围及其祖先路径不接受软链接；文件必须为普通文件或目录，拒绝设备、套接字、FIFO、嵌套挂载和有多个硬链接的文件。可选源码不得带 `.git`、`node_modules` 或开发缓存；需要源码的接收者通过资料入口取得，不在安装时自动拉取、安装依赖或执行代码。

禁止在安装内容中携带平台控制目录、项目会话、管理凭据、开发环境 `.env` 文件、数据库伴随文件或现有实例的受管 `project.json`。种子数据只能通过专门字段引入。检查可以阻止这些明确的文件类别，不能证明网页或种子数据已经脱敏。

## 4 说明文件规范

### 4.1 编码与版本

`local-app.json` 是 UTF-8 JSON 对象，不接受注释、尾逗号、重复键或非有限数字。拒绝未知字段和未知枚举值，避免把拼错的兼容要求静默忽略。唯一扩展区为可选 `extensions` 对象，只存额外描述信息；不能改变权限、路径、初始化或更新行为，忽略其内容时给出提示。

`packageFormat` 必须为 `local-web-app`，`formatVersion` 首版为整数 `1`，`runtime` 必须为 `static-web`。不支持的格式主版本返回专门错误，不降级为普通目录安装。

### 4.2 最小完整示例

以下是无预建业务表、无平台数据接口依赖的示例：

```json
{
  "packageFormat": "local-web-app",
  "formatVersion": 1,
  "runtime": "static-web",
  "app": {
    "id": "org.example.simple-notes",
    "name": "便签示例",
    "version": "1.0.0",
    "description": "展示本地网页界面的示例应用"
  },
  "web": {
    "root": "dist",
    "entry": "index.html",
    "routing": "hash"
  },
  "requires": {
    "capabilities": []
  },
  "runtimeRequirements": {},
  "data": {
    "formatVersion": 0,
    "initialization": {
      "mode": "empty"
    }
  }
}
```

示例名称和版本不对应已发布应用；空的能力列表也不代表平台替应用提供了业务数据保存。要保存到 SQLite 或附件，应用需接入对应平台接口，并按下一节准备所需表结构。

### 4.3 字段定义

| 字段 | 必需 | 规则 |
| --- | --- | --- |
| `packageFormat`、`formatVersion`、`runtime` | 是 | 按 4.1 节的固定值校验 |
| `app.id` | 是 | 跨版本稳定的应用标识，建议反向域名；3 至 128 个 ASCII 字符，点分段非空，各段以小写字母开头，其余为小写字母、数字或连字符 |
| `app.name` | 是 | 去除首尾空白后非空，最多 200 个字符；名称不作为身份 |
| `app.version` | 是 | 首版采用 `主版本.次版本.修订号`，每段为无前导零的非负整数，单段不超过 2147483647；不接受 `v` 前缀、版本范围或预发行后缀 |
| `app.description` | 否 | 最多 2000 个字符，默认空字符串 |
| `app.icon` | 否 | 相对包根的 PNG 文件路径；声明后缺失或无效则阻断，省略则使用平台默认图标 |
| `web.root` | 是 | 相对包根的网页产物目录 |
| `web.entry` | 是 | 相对网页根的 HTML 文件，支持 `.html`、`.htm`，大小写按实际文件匹配 |
| `web.routing` | 是 | `hash` 或 `files`；前者用片段导航，后者的页面导航对应实际 HTML 文件。依赖服务器回退的 history 路由不在 v1 内 |
| `requires.apiVersion` | 条件必需 | 使用平台 SDK/API 时为正整数，当前接口主版本为 `1`；不用业务 API 可省略 |
| `requires.capabilities` | 是 | 不重复的必需接口能力字符串数组；未知或缺失的必需能力阻断。非空时必须声明 `apiVersion` |
| `requires.minPlatformVersion` | 否 | 最低平台版本，格式同 `app.version`；按数值逐段比较。不得用 SDK 包版本代替平台版本 |
| `runtimeRequirements` | 是 | 复用既有网络、设备结构；无需求为 `{}`。错误声明阻断，不能默认为全部开放 |
| `data` | 是 | 数据格式版本与初始化方式，见第 7 节 |
| `documentation` | 否 | 对象，可含 `readme`、`data`、`development`，值为相对包根的文件路径；seed 模式必须有 `data` |
| `source` | 否 | 对象，唯一字段 `root` 指向可选源码目录；不验证其与产物一致，也不据此自动开放构建 |
| `distribution` | 否 | 对象，可含 `repository`、`releaseUrl`、`releaseTag`；前两者为不含凭据的 HTTPS URL，后一项是非空显示文本；安装不自动联网访问 |
| `extensions` | 否 | 仅供展示的自定义元数据；不影响安装语义 |

所有必需对象均须出现，不能用 `null` 代替省略或空对象。可选字段一旦出现也必须有效。`requires.capabilities` 复用正式能力名称，例如 `db.schema`、`db.execute`、`db.transaction`、`files`、`events`；不从 npm 依赖名称猜 API 版本或能力。

`runtimeRequirements` 沿用[现有网络与设备字段](project-capabilities-and-secrets.md)：网络按 `connect`、`images`、`media` 分组，每项包含准确 HTTPS origin、用途和发送数据说明；设备按 `camera`、`microphone` 声明用途。接口依赖、浏览器策略与系统授权分别检查。能力列表不是权限隔离；没声明使用 SDK 不等于服务端自动禁止数据库访问。

### 4.4 身份与版本的含义

| 标识 | 用途 |
| --- | --- |
| `formatVersion` | 平台怎样读取应用包格式 |
| `app.id` 与 `app.version` | 哪个应用、作者发布的哪个版本 |
| API 与最低平台版本 | 安装环境是否满足声明的接口要求 |
| `data.formatVersion` | 该应用的数据结构与业务存储约定版本 |
| 平台生成的 `projectId` | 本机一个安装实例及其独立数据库、附件 |
| 平台生成的安装代与 `packageDigest` | 本次实际安装的内容及其发布记录 |

包不能指定本机 `projectId`、安装目录、服务端口或会话。应用运行时从平台上下文获取实例身份。相同应用可以另装多份；相同 `app.id` 只表示更新候选，不证明作者身份或包来源可信。

同一实例的同版本、同摘要更新显示“已安装此版本”，不重复初始化；同版本但不同摘要拒绝覆盖，要求作者发布新版本。首次安装同版本的独立实例仍是合法操作。版本较低的包不走普通更新，v1 不提供一键降级。

## 5 目录检测与兼容边界

### 5.1 检查顺序

| 阶段 | 必须完成的检查 |
| --- | --- |
| 目录与清单 | 目录身份和可读性、根清单存在、严格 JSON、格式与运行类型 |
| 声明范围 | 路径边界、范围重叠、普通文件、名称冲突、声明内容存在、排除项与检查预算 |
| 当前环境 | 平台版本、API 主版本、必需接口能力、网络与设备声明是否受支持 |
| 暂存复制 | 对声明范围生成有序文件清单，读取内容摘要，安全复制并复核源变化与副本一致性 |
| 网页静态校验 | HTML 入口、文本编码、静态可解析资源、子路径兼容、当前 CSP 冲突和路由声明 |
| 初始数据 | 按初始化模式验证空库约定或种子快照、附件、数据说明 |
| 结果 | 汇总阻断、警告、运行未验证项及实际要安装的内容；绑定报告与暂存副本 |

报告中的“通过”必须附检查时间、当前平台/策略版本、文件数、逻辑字节和范围。读取不完整、超预算、诊断失败不能标记通过或显示零字节。可继续的独立问题尽量一起报告；清单无法解析时不猜路径继续扫描。

### 5.2 网页检查

使用 HTML/CSS/JavaScript 的实际语法解析，区分脚本、样式、图片、模块、导航、JSON 数据脚本、注释及模板内容。不能把所有 `href` 当成资源，不能把字符串或注释中的 `<base>`、`eval` 等关键字直接当成运行行为。HTML 按浏览器容错规则解析，不要求 XML 式良构。

安装检测必须复用运行时实际执行的 MIME、文本大小和资源路径限制，不能只检查整个包的预算。目前服务对每个 HTML 文件限制为 8000000 字节，资源逻辑路径限制为 2048 字节、单段 255 字节，均属于现有内部测试参数。入口和多页面 HTML 都要按当次真实限值检查；不能让包总量合格但文件必然无法提供的内容通过。

确定违反 v1 发布约定的内容阻断安装：

- 入口不是有效可读取的 HTML；HTML、CSS、JS 文本不是 UTF-8；入口仍直接引用需编译的 TS/TSX 或开发服务器模块。
- 实际资源引用指向不存在的文件、越出网页根，或使用与平台子路径不兼容的根路径。URL 按浏览器语义处理查询参数、片段、编码及 HTML 实体，不能仅按字符串拼接文件路径。
- HTML 语法树中含 `<base>` 元素，包括模板中的该元素；平台负责注入发布代资源基址。注释或脚本文本中的字样不算元素。
- 页面声明外部可执行脚本、远程样式或字体，或包含会生效的内联可执行脚本、内联事件处理器，违反当前 CSP。JSON 数据块不作为可执行脚本报错；不能通过自行开放 `unsafe-inline` 绕过平台规则。
- 清单要求 history 回退、本机后台进程或其他未支持的运行类型。导航链接与资源加载分开检查；仅在可确定的导航规则冲突时阻断，不能把客户端路由误报为缺失 JS。
- 种子、源码或数据目录被引用为网页资源；硬编码另一安装实例或开发服务的必需入口。

静态分析不能完整判定变量拼接的 `import()`、`fetch()`、条件分支、懒加载、第三方接口返回、CORS、设备授权和业务数据读写。明确可解析的调用按实际规则校验，其余标为“运行尚未验证”；不根据源码中未找到网址就声称离线可用，也不根据找到 `eval` 字符串断言必然执行。

现有 [validate_artifact](../crates/platform-core/src/builds.rs) 使用有限正则扫描，存在把导航当资源、漏过动态加载及远程脚本的边界，不能原样充当新安装检测器。[静态服务](../crates/platform-core/src/service.rs)目前按实际文件提供资源、没有通用 history 回退；[运行策略](../crates/platform-core/src/runtime_policy.rs)限制脚本、连接和设备来源。新检测规则必须与真正的运行策略共用依据，避免检查与运行各维护一套不一致的规则。

`hash` 支持要验证平台注入基址后的行为：普通 `href="#/page"` 或 `href="#section"` 必须仍指向当前 HTML 文档，不能跳到没有入口映射的发布代目录。现有目录式 `<base>` 不能直接保证这一点；建议安装应用的基址指向当前发布代中的当前 HTML 文件，相对资源仍从其父目录解析。实施须同步验证普通锚点、JavaScript 路由、多页面与旧代资源，不能仅依据 `routing: "hash"` 宣布导航兼容，也不为任意缺失路径添加首页回退。

### 5.3 运行验证

目录检测不执行网页或安装脚本。用户安装后主动打开应用，才能观察启动、资源请求、路由、接口和具体功能的实际结果。将来若增加“试运行”，需单独设计临时数据与浏览器环境，不能借正式项目验证，也不能把当前共享 origin 架构描述为恶意第三方代码沙箱。

运行记录应区分“首页打开”“指定操作成功”“未覆盖功能”，不把无控制台错误等同于业务正确。系统权限、真实摄像头/麦克风、普通浏览器及最低系统版本仍按原有实测要求验收。

### 5.4 检测结果绑定与预算

只对声明范围建立内容清单，排序后记录相对路径和节点类型，普通文件另记录字节数与 SHA-256，目录包含空目录也须登记；说明文件原始字节参与摘要。`packageDigest` 对规范编码的清单计算，编码包含字段长度与类型，避免拼接歧义；内部摘要规则单独版本化，不依赖 mtime，也不把包自报的摘要当成来源认证。

复制使用文件身份及不跟随链接的操作；复制前后对声明范围重新核对，发现新增、删除、内容变化或路径替换即报 `PACKAGE_SOURCE_CHANGED`，丢弃本次确认资格。最后校验的对象是平台自己的暂存副本。

检测报告生成单次 `planId`，绑定服务实例、工作区身份、暂存摘要、平台策略和目标操作。建议有效期十分钟；关闭流程、重新选择、更新目标变化、工作区迁移或平台重启均使未提交计划失效。确认安装提交该计划，不重新盲读原目录；提交前核对暂存内容。确认后的源目录变化不影响已经固定的副本，但不能把新变化混入本次安装。

同一计划一旦提交，持久绑定唯一操作 ID 和任务 ID；重复提交只返回原任务，不能再创建实例。计划过期或服务重启不撤销已接受操作，按持久任务与日志恢复；响应丢失后查询原任务。废弃暂存副本只在确认没有活动操作或恢复引用后清理，不按目录名盲删现场。

建议初始检查预算：清单 256 KiB，声明范围最多 2 GiB 逻辑字节、50000 个文件与目录、相对目录深度 32。以上仅为待确认的安装检查预算，不改变[资源限额讨论稿](resource-limits-proposal.md)中的既有状态，也不是已有项目配额。实际报告必须返回本轮采用的限制与观测值；超限为 `incomplete`，不截断安装。磁盘空间预检计入暂存、安装内容、数据库转换及更新前备份，不把预检通过当作后续写入必成功。

## 6 错误与提示规范

用户提示采用“位置与检测事实 → 对安装的影响 → 处理办法”。内部保持稳定错误码，界面显示中文；路径相对包根，行列仅在真实解析得到时提供。不回显数据库记录、凭据或完整源码。发现多个问题时先显示阻断项，支持复制诊断摘要给开发者或 AI。

```json
{
  "code": "PACKAGE_RESOURCE_MISSING",
  "stage": "staticValidation",
  "severity": "error",
  "path": "dist/index.html",
  "line": 8,
  "column": 5,
  "message": "入口引用的网页资源不存在，当前不能安装。",
  "details": {
    "reference": "./assets/app.js",
    "resolvedPath": "dist/assets/app.js"
  },
  "suggestion": "请重新导出包含完整网页资源的应用包，再次检测。"
}
```

`severity` 为 `error` 或 `warning`；警告不能绕过阻断。动态行为没有可确定错误时使用警告，不伪造错误位置。任务级 `operationOutcome` 仍按实际情况报告 `not_started`、`not_committed`、`committed` 或 `unknown`，不能从网络超时推断未安装。

| 错误码或提示码 | 检测事实及用户处理 |
| --- | --- |
| `PACKAGE_MANIFEST_MISSING` | 根部没有 `local-app.json`；请选择包含说明文件的目录，或让开发者按规范打包 |
| `PACKAGE_READ_FAILED` | 指定目录/文件不可读；显示具体路径，检查访问权限或磁盘连接；结果为未完成 |
| `PACKAGE_MANIFEST_INVALID` | JSON 或字段无效；给出字段路径和预期类型，修复说明文件 |
| `PACKAGE_FORMAT_UNSUPPORTED` | 包格式版本不受支持；提供兼容包或使用支持该格式的平台版本 |
| `PACKAGE_RUNTIME_UNSUPPORTED` | 明确要求本机后端、SSR 等；平台不能只靠复制网页满足该依赖 |
| `PACKAGE_PLATFORM_INCOMPATIBLE` | 最低平台/API/必需能力不匹配；列出要求与当前实际值 |
| `PACKAGE_RUNTIME_REQUIREMENTS_INVALID` | 网络或设备声明无效/不支持；指出字段及平台规则，不提示授予不存在的权限 |
| `PACKAGE_PATH_INVALID` | 越界、链接、特殊文件、名称冲突或范围重叠；指出路径，重新整理完整包 |
| `PACKAGE_CONTENT_FORBIDDEN` | 声明内容含控制资料、依赖目录或禁止分发的文件类别；说明类别并要求重新打包 |
| `PACKAGE_ENTRY_MISSING` | 清单入口不存在；显示声明入口与检查路径 |
| `PACKAGE_SOURCE_ONLY` | 入口明确引用未编译 TS/TSX 等；先构建，再提供发布包；仅存在 package.json 不构成此错误 |
| `PACKAGE_RESOURCE_MISSING` | 明确资源引用缺失；同时显示引用文件、引用值和解析目标 |
| `PACKAGE_WEB_POLICY_CONFLICT` | 真实可执行内容、资源地址或路由与当前策略冲突；给出规则和修复办法 |
| `PACKAGE_SEED_INVALID` | 初始库损坏、伴随文件依赖、外键错误或格式不受支持；重新导出干净快照 |
| `PACKAGE_DATA_VERSION_MISMATCH` | 声明版本与种子/实例实际版本不一致；禁止自行改数字跳过检查 |
| `PACKAGE_DATA_MIGRATION_REQUIRED` | 更新包需要另一数据格式；v1 不自动迁移，可另装独立实例 |
| `PACKAGE_SOURCE_CHANGED` | 检测复制期间声明范围发生变化；停止外部修改后重新检测 |
| `PACKAGE_CHECK_LIMIT` | 检查超预算；列出限制和实际计数，结果为未完成 |
| `PACKAGE_SPACE_INSUFFICIENT` | 目标空间不足以完成暂存/备份/安装；保留原数据，整理空间后重试 |
| `PACKAGE_PLAN_EXPIRED` | 计划失效或目标状态已变化；重新检测，不复用旧确认 |
| `PACKAGE_VERSION_CONFLICT` | 已装同版本而内容不同，或使用旧版走更新；发布新版本或另装实例 |
| `PACKAGE_RUNTIME_UNVERIFIED` | 基础检查通过，动态加载、外网或具体功能尚未验证；显示已知范围 |
| `PACKAGE_SOURCE_UNVERIFIED` | 附带源码但未证明与产物匹配；保存为资料，不开放本机构建 |

安装执行失败另带任务 ID、阶段、已提交与否及可恢复状态。普通用户无需理解错误码；开发者可以依靠代码和位置复现。正式错误码在实现前与 CLI/API 一次性定稿，本文不新增可调用路由。

## 7 数据初始化

### 7.1 模式与版本

v1 建议只支持 `empty` 和 `seed`。安装器不执行包内 SQL、JS、shell、npm 或数据库迁移脚本；首次打开网页不作为安装初始化步骤。

| 模式 | 包内容 | 新实例的结果 |
| --- | --- | --- |
| `empty` | 无初始数据库或附件；`data.formatVersion` 必须为 0 | 创建独立空 SQLite 和空附件目录，没有任何业务表 |
| `seed` | 已准备好的 SQLite 独立快照、可选初始附件及数据说明；版本为正整数 | 复制为新实例自己的可写数据库与附件，不执行建表脚本 |

需要业务表但没有示例记录的应用也使用 `seed`，提供“有表结构、没有个人记录”的库。纯静态应用可以使用 `empty`；缺少必须的业务表时不能以空库冒充初始化成功。

数据应用示例使用以下字段替换最小示例中的 `requires`、`data`，并增加 `documentation`：

```json
{
  "requires": {
    "apiVersion": 1,
    "capabilities": ["db.schema", "db.execute", "db.transaction", "files"]
  },
  "data": {
    "formatVersion": 1,
    "initialization": {
      "mode": "seed",
      "database": "initial-data/main.sqlite",
      "attachments": "initial-data/attachments"
    }
  },
  "documentation": {
    "readme": "docs/README.md",
    "data": "docs/data.md"
  }
}
```

`data.formatVersion` 为 0 至 2147483647 的整数，含义由作者在数据说明中定义。`empty` 禁止提供 `database`、`attachments`；`seed` 必须提供 `database`，`attachments` 可省略，省略即空附件目录。声明目录不存在则报错，明确存在的空目录可以接受。

种子库的 `PRAGMA user_version` 必须等于 `data.formatVersion`；平台安装记录也保存该版本。它是兼容声明和一致性检查点，不是数据库物理完整性或业务兼容的证明。禁止用修改版本号代替实际数据迁移。

### 7.2 发布者准备初始数据

发布者在独立、可丢弃的打包项目中准备业务表、索引和允许分发的初始资料，不从日常业务库直接复制一份当作默认种子。数据说明列出业务表、初始记录用途、附件逻辑路径和数据版本。

种子库必须通过 SQLite Backup API 等一致性快照方式生成，并关闭为独立的 `journal_mode=DELETE` 文件；不依赖原机的 `-wal`、`-shm`、`-journal`。出现这些伴随文件时要求重新导出，不以删掉文件后继续安装作为修复。正确导出是发布者职责：单独复制主文件造成的缺失提交，扫描器不一定能识别。

应用数据中的附件引用应为相对附件根的逻辑路径，不含开发者机器绝对路径、项目 ID、服务端口或会话 URL。安装保留业务主键和业务 UUID，不全库搜索替换字符串。

### 7.3 平台校验与首次提交

对受管暂存副本检查：数据库可由内置 SQLite 打开，页和 schema 可读取，`integrity_check` 与 `foreign_key_check` 通过，`user_version` 与清单一致，不依赖未提供的扩展或外部数据库。禁用扩展加载并沿用数据库访问约束；不为验证而执行应用查询、触发业务写入或调用包内代码。无法完成诊断就停止，不能把检查异常解释成通过。

初始应用包的种子要求外键检查通过；这不同于[恢复用户备份](backup-and-maintenance.md)时可以保留问题并进入维护的抢救规则。检查只验证可检查的结构与约束，不证明附件业务引用正确、不自动脱敏，也不能证明所有潜在函数或查询都与运行环境兼容。

接受安装任务时预留新实例 ID，完整候选准备成功后才提交为可用身份并发布；失败和重启按日志保留或释放预留，不使半成品出现在可运行列表。空库模式调用空库创建流程；种子模式先复制独立文件，再作为已有库打开，不使用会重置版本的空库初始化流程。当前 [initialize_database](../crates/platform-core/src/database.rs)会设置 `user_version=0`，实现时必须区分这两条路径。

平台可以在新实例副本上启用正常 WAL 模式，原始种子保持只读。每次安装分别复制数据库和附件，不用硬链接或软链接共享可写数据。初始附件复制后成为该实例的业务数据，后续新增、删除由该实例负责。

同一安装操作在响应丢失或重启后通过持久操作 ID 核对，不再次生成实例或重复播种。再次明确点击“另装一份”才是新的安装操作。不能因为正式目录已有文件，就盲目重跑初始化覆盖它。

### 7.4 初始化承诺的边界

应用包应保证首次打开已有必要表结构，并遵守“不在更新后偷偷进行 schema 迁移”的开发约定。现有 SDK 的 SQL 能力并非全面禁止 DDL，静态检测不能保证网页运行后绝不自行改表。若将来要求强制阻止这种行为，需要另行设计服务端权限，不能只写在说明文件里。

每个安装实例独立保存数据；分享同一个包不产生多人共享数据库或跨设备同步。浏览器 `localStorage`、IndexedDB 不自动进入平台备份；需要受管持久化的业务数据应使用平台数据库和附件接口。

## 8 更新与现有生命周期

安装应用保留独立的类型与来源，例如“安装应用／仅含运行产物”；不生成假源码目录、不要求 Node、不伪造构建成功或源码匹配记录。附带源码也只作为资料，转为可开发项目需要单独流程。详情提供版本、来源、更新、备份、恢复、复制和删除，源码缺席不是损坏。

### 8.1 安装记录与备份格式

包说明文件与受管项目清单是不同文件。平台按安装类型生成自己的项目清单和登记记录；原始 `local-app.json` 作为发行来源资料保存，不直接作为已安装项目的路径解析依据。运行网页、图标、文档和源码资料建立明确的包内路径到受管路径映射；网页树内相对结构保持不变，种子库/附件映射到实例的数据库/附件位置，原种子不作为额外运行数据长期保存。

文档和可选源码可以保留在安装资料目录下的原相对层级，避免改写其中的相对引用；它们不成为静态网页服务根。内部目录名称及项目清单格式升级在实施前定稿，但必须满足上述角色分离，不能把包内路径直接拼成任意目标路径。

来源资料保存原包摘要、原始清单、应用版本、初始数据说明和映射。另记录当前已安装程序的文件清单及摘要；业务数据库和附件会持续变化，不属于不可变程序摘要。原 `packageDigest` 包含一次性种子，只表示安装时来源，不能作为当前运行目录内容摘要。

备份必须携带安装类型、当前程序、必要资料、可移植来源、当前数据库/附件及归档逐文件摘要。恢复按“已安装实例”模式核对当前程序摘要和归档数据，不再次检查原包 seed 路径、不重算原始包摘要、不运行初始化。包格式、内部项目格式和备份格式分别版本化；旧平台不理解新类型时明确拒绝，不把它当成损坏的源码项目。

已使用实例的数据版本不一致时，阻止更新或恢复后直接开放，但仍按既有备份与坏库保全规则保存可保存内容、记录诊断并保持维护；不修改版本号、不重置数据库、不用种子替换。种子的严格准入条件不能成为拒绝保全用户已有数据的理由。

### 8.2 操作与更新

| 操作 | 拟议规则 |
| --- | --- |
| 安装新实例 | 新 `projectId`，按 empty/seed 初始化；默认不覆盖任何现有项目 |
| 更新当前实例 | 用户在目标实例中明确选择包；`app.id` 相同、应用版本更高、数据格式版本相同、兼容检查通过 |
| 复制实例 | 复制当前程序和当前业务数据，生成新实例 ID；不重新播种 |
| 备份与完整恢复 | 包含当前程序、实际数据、附件、安装声明及可移植来源；源码可无；恢复不依赖原包或 GitHub |
| 删除与迁移 | 沿用受管项目的回收站、永久清除和公开工作区迁移规则 |

更新前取得项目操作互斥，核对预检时的实例版本、数据版本及当前数据库，进入已有维护流程并完成受保护的整项目基线备份。存在未解决恢复现场、初始化或其他冲突任务时拒绝开始更新。维护中的操作携带当前维护身份，不能自动解除既有维护。

如果实例原本就在维护中，沿用当前 `maintenanceId` 并保留原基线引用，同时创建反映本次更新开始前实际内容的受保护快照。维护期间可能已有改动，不能用较早基线冒充本次更新前备份。中断或提交结果未明确前，该快照继续受保护。

新程序及其声明作为一个发布代暂存和校验，再持久提交；不覆盖数据库、附件或实例 ID，不重新复制种子，也不重置用户改过的名称和图标。新包的默认元数据仅记录为发行资料；采用新版显示信息是明确的用户操作。新增联网或设备需求在更新预检中突出展示。

更新包仍须通过完整包校验，其种子属于将来新安装实例的初始内容，不能作为当前实例的修复或升级依据。安装后不长期另存一份未使用种子；当前数据、声明和来源足以完成该实例的备份恢复，重新分发安装包由作者重新打包。

提交前失败保留旧程序和原数据；提交点之后的异常按操作日志核对真实代次，不谎报“完全未更新”，也不盲目回退或重播。成功后继续显示维护状态，用户明确结束维护才开放；推进文档代次，旧页面要求处理草稿后重新进入。维护结束使用安装产物、来源和数据检查，不要求没有源码的应用进行构建。

v1 更新要求包、安装记录和当前库的 `user_version` 对同一数据格式版本达成一致；不自动执行迁移，也不接受作者仅通过版本范围声称任意升级可用。不同数据版本提示需迁移，可以另装独立实例，不能借此把旧数据静默搬过去。

程序回退与完整恢复分开：旧程序未必理解现在的数据，v1 不提供一键程序回退。完整恢复把程序和数据一起回到快照时点，保留恢复前现场、维护门禁和旧页面代次；它会撤回备份之后的业务变化，界面须明确告知。旧有开发项目的清单、SDK、锁文件、备份和维护行为保持原有契约。

## 9 GitHub 分享流程

### 9.1 作者发布

1. 在源码仓库保存业务代码、固定构建依赖和生成包说明文件的配置。开发可以由 AI 完成，但分享包必须符合相同规范。
2. 在开发机或 GitHub Actions 中安装锁定依赖，构建本地 HTML/JS/CSS 和资源，不把 `node_modules` 当运行包交付。SDK 所需代码在构建时打入产物，接收者不再安装 SDK。
3. 在独立打包目录准备 `local-app.json`、产物、可选资料及干净初始数据。先检查格式，再在新建可丢弃实例验证首次安装、必要功能、重新启动和无源码运行。
4. 将完整包目录压缩为带版本的文件，例如 `wordbook-1.0.0.local-app.zip`。压缩包内只有一个包根目录，说明文件位于该目录根部；Release 说明写清解压后应选哪个目录。
5. 在 GitHub Release 附加该 ZIP、下载文件的 SHA-256 及安装说明。说明应用版本、最低平台要求、网络/设备需求、初始数据内容、实际测试环境和已知限制，再分享 Release 链接。

GitHub Releases 可以附加构建后的发行文件；其自动生成的 `Source code.zip` 是仓库在 tag 时点的快照，未必包含构建产物。接收者应下载作者发布的应用 ZIP。[GitHub Releases 说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)、[上传发行文件](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)。

GitHub Actions 可以固定 Node 环境、按锁文件安装依赖并执行构建测试；自动产出包的工作流属于后续实现，不在本次文档中新增配置。[GitHub Node.js 构建文档](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)。

### 9.2 接收者安装与后续更新

接收者先安装兼容平台，再下载应用 ZIP、解压、在“添加应用”中选择说明文件所在目录，完成检测和安装。无需克隆仓库、安装 Git 或使用作者的 AI 客户端。私有仓库的下载仍需接收者具有访问权限；平台 v1 不代办 GitHub 登录或获取私有仓库凭据。

作者发布新版后，接收者下载解压，在已有实例中选择“更新应用”并选择新版目录。普通“添加应用”始终创建新实例，不凭应用 ID 或同名目录自动覆盖原实例。说明文件中的 Release URL 只是资料，不授权后台自动下载更新。

GitHub、应用 ID 和校验摘要不是发布者身份签名。摘要可用于核对下载/复制内容一致，不能证明应用安全；本版面向用户信任的应用来源，不宣称具有任意第三方应用市场的隔离能力。

源码是否公开与应用包能否安装分别决定。分享包不默认包含个人数据库、附件、访问令牌或本机路径；初始资料由作者明确选择可分发内容。平台整项目备份不是默认的公开分享包。

## 10 接收者与开发者的环境要求

| 环境项 | 只安装和运行应用包 | 开发或重新构建 |
| --- | --- | --- |
| 平台 | 安装满足说明文件要求的版本，运行时平台服务必须开启 | 使用对应平台文档及 SDK，构建工具自行准备 |
| 系统与 CPU | 实际可用性以对应平台发行支持矩阵为准；现有内部运行线为 macOS 15+、Apple Silicon | 前端构建环境可以另选，但须在目标平台验证产物 |
| Node/npm | 不需要 | 当前受管构建约定支持 Node 22.12+ 的 22 分支及 24 分支；外部工程另按锁定工具链执行 |
| Git、Rust、Xcode、Docker | 不需要 | Git/Node 等视开发流程需要；Rust/Xcode 只在开发平台本体等情况下需要 |
| 数据库服务 | 不需要另装，平台提供 SQLite | 初始库必须与平台内置 SQLite 能力兼容 |
| 磁盘 | 当前工作区可写，空间满足安装、数据、备份需求；沿用工作区文件系统规则 | 额外容纳源码、依赖和构建中间文件 |
| 网络 | 获取包时需要下载渠道；运行时按应用需求，本地功能可离线 | 首次依赖下载或在线构建通常需要网络 |
| 摄像头/麦克风 | 只有相关功能需要设备和明确授权 | 必须分别做真实设备与拒绝权限测试 |
| AI 客户端 | 开发该应用的 AI 不需要继续运行 | 可作为开发工具，不成为应用运行依赖 |

平台本体仍是内部开发版，正式签名、公证、普通用户下载首次启动和最低系统等发行验收尚未完成。系统支持目标与交付状态以[发行约定](release-and-updates.md)及[M6 计划](development-milestones.md)为准；Windows 等工作线须独立交付和验收，不能由网页产物可移植或 Mac 验证推导已经可用。本方案不扩大或否定其他已确认的平台规划。

说明文件不保证系统已经授予设备权限，不保证外部接口可用，也不保证网络连接成功。可选设备不可用时应用应给出相应提示，不能把整包判成无法安装。运行时需要在线模型的功能仍需适当服务和接入方式；把秘密 API key 打进网页不属于受支持的凭据方案，沿用[现有能力边界](project-capabilities-and-secrets.md)。

不写死开发者电脑路径、localhost 开发端口、旧项目 ID 或旧会话入口。能打包成网页不代表可脱离所依赖的服务；应用明确需要本机后端时必须拒绝，而不是指导普通用户额外搭一套不受管运行环境。

## 11 实现边界与验收计划

实施时需要独立的包解析/检测、初始化和安装发布流程，并复用持久任务、受管目录、会话、不可变网页代、备份和维护机制。现有清单强制源码及构建字段，来源记录含本机构建信息，维护结束也依赖源码摘要；这些地方必须显式理解“安装应用”类型，不能用空源码或伪造构建记录兼容。

以下为未来验收要求，不是本次已通过测试：

| 范围 | 最少覆盖场景 |
| --- | --- |
| 清单入口 | 根清单缺失/不可读/JSON 错误/重复键/未知字段或版本；选错上一层目录；有 index.html 但无清单 |
| 包边界 | 越界、软/硬链接、特殊文件、名称碰撞、目录重叠、明确排除内容；未声明文件不被复制 |
| 网页检测 | 缺 JS/CSS/图片、根路径资源、编码 URL、注释/字符串中的假标签、导航与资源区别、JSON 数据脚本与可执行脚本区别、多页面、懒加载未知项；包总量合格但 HTML/路径超运行限值；原生片段链接、JS 设置 hash 与子目录入口 |
| 环境 | 不支持 API/能力、无 Node/源码/AI 客户端运行、离线本地功能、实际 WebView 及指定浏览器 |
| 初始数据 | 真空库、有表无记录的种子、有公开资料和附件的种子、WAL 伴随、损坏库、外键错误、数据版本不一致、旧版 SQLite 不支持的结构 |
| 数据保留 | 同包多实例互不影响、更新不播种/不覆盖数据、同版本不同摘要阻断、不同数据格式阻断、复制与备份恢复无需原包 |
| 中断 | 复制时改文件、取消/超预算/磁盘不足、计划失效、安装响应丢失、提交前后重启、初始化不重复、提交结果不明保留现场 |
| 生命周期兼容 | 已有开发项目、SDK、数据库、附件、备份、维护及恢复现场均保持；无源码项目恢复后不被迫构建 |
| 真实交接 | 作者在 GitHub 分享包，另一台符合支持线的电脑下载、解压、选择目录、检查、安装、重启，并记录真实操作结果 |

测试只使用明确命名的可丢弃项目。数据库结构检测、静态扫描和模拟 UI 不能代替真实功能、设备权限、最低系统或跨机器验证。
