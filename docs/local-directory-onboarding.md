## 三条路径

| 检查状态 | 页面动作 | 文件和执行范围 |
| --- | --- | --- |
| `empty`：普通空目录 | 显示目录、名称与生成范围，点击“生成并添加项目”一次完成初始化与添加 | 只在刚核对的空目录生成起始文件并登记外部引用，不安装依赖或启动服务 |
| `ready`：声明及必要文件满足当前 Node 入口 | 展示名称、应用声明、入口、配置说明和接入范围，再明确添加 | 登记为外部目录引用，不复制或改写作者目录，不自动启动 |
| `needs-review`：其余目录 | 展示问题，可复制完整“给 AI 检查”的说明；评估／适配后可重新检查 | 检查和复制说明均不写目录、不执行项目、不自动发送给 AI |

空目录按实际目录项判断，隐藏文件也算内容；平台不为初始化自动清空文件夹。路径不安全、无读取权限或超出检查预算时明确停止，不能把检查失败当作空目录。

空目录的起始项目是零第三方依赖的 Node 服务应用：`local-app.json` v2 声明 `web/index.html` 静态入口及 `backend/server.mjs` 协议服务，网页脚本为 `web/app.js`。模板源为 `templates/local-node/`，不是让用户先安装前端工具链。点击按钮本身即明确确认生成与添加，不再要求额外勾选、二次生成确认或生成后再点添加。若确认前目录已变化，不覆盖新内容，重新检查后再决定。

提交后页面显示“正在生成并添加项目”，由一个原生命令完成文件生成与持久登记，不由界面串联两次写操作。成功后项目立即进入列表，在同一弹窗显示“添加成功”，由用户明确选择“打开应用”“去配置”或“完成”。“去配置”只进入配置，不因重新读取后配置完整而启动应用。外部目录接入没有临时下载材料，不添加清理阶段。只有持久登记与返回结果确认成功后才更新列表；生成或添加失败、结果未知时保留错误、目录与已生成文件，不回滚删除，也不自动重试写入。

若旧版本已生成文件但尚未添加，或新流程在生成后未能完成添加，重新选择或检查同一个目录即可进入预览并确认添加，无需重新初始化。先核对列表和登记；同一目录已有登记时沿用已有实例，不因重试而创建重复项目。已添加项目的登记保存在平台自己的数据目录，刷新列表或重新启动管理器后仍应出现；外部源码目录本身不承担登记作用。

初始化还生成 `README.md`、`DEVELOPMENT.md`、无第三方依赖的 `package.json` 与 npm v3 锁文件，并在 `local-app.json` 中声明独立的 `dataContract`。检查技能全文仅随这个新建起始项目放入 `.agents/skills/local-folder-review/SKILL.md`；不安装到 AI 的全局技能目录，也不把其他仓库的 skill 路径当作必需条件。

只有空目录初始化会写入这些新文件。已有目录检查不会塞入 skill、清单或其他资料；不因少一个声明就“帮用户补齐”或搬走原文件。目录仍属于用户，初始化后的直接接入也使用外部引用语义。

## 给 AI 的完整检查说明

复制内容包含本次目录、当前接入要求和独立 [`local-folder-review` skill 全文](../skills/local-folder-review/SKILL.md)。这是完整可用的检查请求，不要求外部 AI 已安装技能、拥有平台仓库或能访问某个文档链接。用户自行选择 AI、提供目录访问权限并发送；平台不自动开任务、上传目录或读取其账号凭据。

本轮请求只授权读取公开项目材料作评估，不修改文件、不运行安装／构建／服务、不登录、不读取 `.env`、凭据或业务数据库内容。AI 根据用户目标给出“可接入、需适配、当前不适合、信息不足”及具体依据。它无法访问目录时须明确说明；Java、Python、未声明运行方式和空目录不能一律宣称可自动适配。用户以后明确要求适配，再按其目标与已有授权实施，不能由一次复制检查说明暗中开始改造。

## 当前能直接添加的类型

此本地目录入口直接添加 Node 应用：`local-app.json` 使用 `packageFormat: "local-web-app"`、`formatVersion: 2`、`runtime: "node-service"`；已有完整静态网页，后端为 Node 24 可直接执行的 JavaScript，并实现平台 initialize／ready、健康检查、ping／pong 及 shutdown／stopping 协议。业务文件通过 `APP_DATA_DIR` 等平台位置保存，配置和秘密通过实例私有配置注入。平台不通过“检查目录”安装依赖或启动代码来证明兼容。

project-v1 网页项目、静态应用包与普通 Node/Web 仓库不能混套此入口。发现 `project.json` 可说明原类型并提示已有完整项目 ZIP 流程，不自动收养外部目录、造平台 ID 或改变结构。额外 Java／Python／Docker 运行时不因目录被选中而获得支持；声明检查通过仍不证明真实运行、在线服务、权限或数据格式兼容。

平台登记、配置、业务数据与原目录分开。外部引用删除时只移除平台登记及私有配置／秘密、数据和缓存，外部源码文件夹完整保留；删除不可撤销范围继续按[直接删除契约](application-deletion.md)执行。独立源码副本安装仍走[来源安装流程](node-managed-installation.md)，不借此接入原目录的数据或凭据。

## 原生入口与确认绑定

- `node_app_directory_inspect({sourcePath})` 返回规范目录、`state`、`expectedRevision`、可选 Node `inspection`、问题列表和完整 `reviewPrompt`；检查不初始化、不登记。
- `node_app_directory_initialize_and_register({sourcePath,input:{expectedRevision,name}})` 用于空目录的“生成并添加项目”。核对空目录确认，完成起始文件生成、验证和持久登记后返回 Node 应用详情；单次确认与原生操作覆盖整个过程，不安装或启动应用。创建时逐项核对目录／文件身份，不跟随链接、不覆盖现有内容；失败保留已创建路径和部分文件，不自动删除或再次初始化。
- 兼容保留的底层 `node_app_directory_initialize({sourcePath,input:{expectedRevision,name}})` 仍只生成文件并返回检查结果，不登记。桌面新入口不调用此命令，不再把它作为用户操作中途的成功状态。
- 添加时 `node_app_directory_register({sourcePath,expectedRevision})` 重新核对已检查的目录。检查与确认之间的变化不能沿用旧确认；失败或结果未知先核对现场，不自动覆盖或重复初始化。原有 `node_app_register` 不作为新目录确认流程的替代入口。

确认绑定核对目录身份、顶层条目、声明内容及已声明文件的元数据，不是整棵工程的内容快照，也不提供系统级写锁。核对和添加期间应暂停外部编辑，修改后重新检查；不以递归读取源码、凭据或业务数据来补造兼容结论。

空目录的合并操作额外保留本次生成文件的身份与内容摘要，在生成后的检查及登记前逐次复核。外部工具即使把文件改成另一个有效 Node 项目，也不能沿用本次生成确认自动登记。生成完成后的错误区分“尚未登记”“登记尝试后结果未确认”“已登记但详情需处理”，均保留目录和登记证据，要求重新检查；登记文件及父目录同步完成后才报告添加成功。

正常退出时停止接受新的初始化／生成并添加操作，并等待已经接受的操作结束。失败保留已创建内容和诊断，不自动回滚或删除；硬崩溃、断电和强制结束不保证完成，也不承诺自动恢复或继续写入。
