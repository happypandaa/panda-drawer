# 项目统一清单修改方案

日期：2026-11-01。

状态：待用户审阅和修改。文件名、字段、切换规则及实施批次均为提案；本轮只保存方案，不修改运行代码，不改写已有项目。

建议把项目根目录的清单统一为 `panda.json`，通过 `runtime` 区分网页项目和 Node 服务项目。项目作者维护一份清单，平台另外维护本机实例登记、用户配置和运行状态。

## 1 统一的原因和范围

当前 `project.json` 描述平台管理的网页项目实例，包含实例 ID、源码与构建、数据库、附件和文档位置。`local-app.json` 最初描述作者交付的应用程序，后来被 Node 应用接入采用，包含作者应用 ID、版本及前后端入口。两份文件来自不同阶段的对象划分，运行类型本身不要求两个文件名。

本次统一文件名、字段含义、解析校验和各流程中的清单读取。网页继续使用现有平台 SDK、SQLite、附件和构建机制；Node 继续直接运行登记文件夹，由自己的后端管理业务数据。统一清单不自动开放任意外部静态目录接入、SSR、多服务、额外运行时或 Node 自有数据库恢复。

现有受支持入口保持各自能力边界：平台创建网页项目，平台完整 ZIP 处理对应网页项目；本机目录和 Git 添加处理已适配的 Node 应用。入口内部使用同一份清单定义，是否扩展网页目录接入另行确定。

## 2 文件名称

| 候选名称 | 判断 |
| --- | --- |
| `panda.json` | 推荐。简短、有平台辨识度，可同时描述开发和运行材料 |
| `panda.config.json` | 可选，但名称较长，更像开发工具设置 |
| `app.json` | 过于通用，容易与已有工程配置混淆 |
| `project.json` | 沿用旧名称容易混淆新旧字段及身份语义 |

建议固定使用根目录 `panda.json`，不支持自定义清单文件名，不递归搜索子目录，不同时维护其他权威项目清单。

## 3 字段结构和必填规则

| 字段 | 要求 | 含义 |
| --- | --- | --- |
| `manifestVersion` | 必填，首版固定为 `1` | 新清单格式版本，与旧 `project.json` v1 分开定义 |
| `app.id` | 必填 | 作者应用标识，随源码保存，与本机实例 UUID 分开 |
| `app.name` | 必填 | 应用名称 |
| `app.version` | 必填 | 作者声明的应用版本，建议使用如 `0.1.0` 的形式 |
| `app.description` | 可选 | 纯文本简介 |
| `app.icon` | 可选 | 项目内静态 PNG 的相对路径，建议 `meta/icon.png` |
| `runtime` | 必填 | `static-web` 或 `node-service` |
| `web` | 必填 | `root`、`entry`、`routing` |
| `backend` | Node 必填，网页禁用 | `root`、`entry`、`nodeMajor`、`protocolVersion` |
| `platform` | 当前平台网页项目必填，Node 禁用 | `sdkApiVersion`、`database`、`attachmentsDir` |
| `development` | 当前平台网页项目必填，Node 可选 | `sourceDir` 和 `build`；网页继续要求有效构建脚本 |
| `configuration` | 有需用户填写的启动配置时声明 | 沿用当前配置声明 v1，仅供 Node 使用 |
| `documentation` | 按运行类型要求 | 用户、开发、数据库和平台接入说明的路径 |
| `window` | 可选 | 沿用现有初始窗口尺寸和尺寸记忆声明 |
| `runtimeRequirements` | 网页项目可选 | 沿用现有网页联网与设备策略，不因此新增 Node 能力 |

`packageFormat` 和 `formatVersion` 不在新清单中保留。文件名和 `manifestVersion` 共同识别新格式。

清单格式版本、应用版本、SDK API 版本、后端协议版本和 `configuration.version` 各自独立，不用同一个版本号控制全部变化。

### 网页项目示例

下面是平台新建网页项目的清单示例。数据库、附件、SDK 和文档仍按现有机制准备；JSON 本身不构成可运行项目。

```json
{
  "manifestVersion": 1,
  "app": {
    "id": "com.example.notes",
    "name": "示例笔记",
    "version": "0.1.0"
  },
  "runtime": "static-web",
  "web": {
    "root": "dist",
    "entry": "index.html",
    "routing": "files"
  },
  "platform": {
    "sdkApiVersion": 1,
    "database": "data/main.sqlite",
    "attachmentsDir": "data/attachments"
  },
  "development": {
    "sourceDir": "app",
    "build": {
      "kind": "npm",
      "script": "build"
    }
  },
  "documentation": {
    "development": "README.md",
    "database": "docs/database.md",
    "platform": "docs/platform.md"
  }
}
```

### Node 应用示例

下面是无需构建、零第三方依赖的 Node 应用最小声明。网页、后端文件和平台运行协议仍须实际满足要求。

```json
{
  "manifestVersion": 1,
  "app": {
    "id": "com.example.notes",
    "name": "示例笔记",
    "version": "0.1.0"
  },
  "runtime": "node-service",
  "web": {
    "root": "web",
    "entry": "index.html",
    "routing": "files"
  },
  "backend": {
    "root": "backend",
    "entry": "server.mjs",
    "nodeMajor": 24,
    "protocolVersion": 1
  }
}
```

## 4 路径和构建规则

`web.root` 相对项目根，`web.entry` 相对 `web.root`；`backend.root` 相对项目根，`backend.entry` 相对 `backend.root`。例如网页目录为 `dist` 时，入口写 `index.html`，不再重复写 `dist/index.html`。

路径使用 `/` 分隔，不允许绝对路径、越界或依靠链接绕过现有边界检查。数据库和附件继续受限于网页项目的 `data/`，源码、产物、数据库、附件和平台控制范围保持现有分离规则。

两类项目的首版 `web.routing` 均使用 `files`。网页原有片段导航可继续使用，不增加服务器 history 回退能力。

构建声明只放在 `development.build`。首版平台网页项目必须提供 `development.sourceDir`，并使用 `kind: "npm"` 和有效 `script`，保留现有源码及构建契约。Node 可以省略 `development`，也可以用 `kind: "none"` 描述无需构建的源码；声明 `kind: "npm"` 时同样必须有 `script`。最终入口位置以 `web`、`backend` 为准，不再另设与它们重复的 `outputDir`。无源码或无构建声明的外部静态应用接入另行确定。

平台网页的 npm 构建继续接入现有暂存、输出目录参数、发布代和输入摘要机制。原生平台差异通过适配层处理。Node 的源码目录沿用当前仓库根约束；Git 添加只用构建声明判断材料是否齐备，仍不执行仓库构建脚本，启动不安装依赖。

本机开发依赖安装继续遵守使用 pnpm 的机器偏好；应用的受管 npm 依赖准备契约保持不变。Git 添加有 npm 材料时仍要求一组有效 `package.json` 与 npm v2/v3 `package-lock.json`。本地目录由作者或 AI 提前准备依赖；零第三方依赖项目可以没有这些文件。

## 5 用户配置和说明文件

`configuration` 沿用当前 `version: 1`、`fields` 的结构。每项声明变量名、显示名称、类型、是否必填、是否秘密、用途和获取步骤；支持普通默认值，秘密值不能有默认值。缺少必填值时可以添加应用，但启动前进入配置引导，保存配置不自动启动。

实际值继续由平台实例私有配置保存，秘密值按现有私有文件机制保存并仅注入目标后端。清单只声明配置结构，不包含真实 Key，不要求用户新建 `.env`。平台登记、配置存储和运行状态文件由平台管理，不属于作者必须交付的文件。

说明路径统一放在 `documentation`：

| 字段 | 阅读者和内容 | 必填规则 |
| --- | --- | --- |
| `readme` | 普通用户的使用与配置说明 | Node 的可选说明组之一；网页可选 |
| `development` | AI 和开发者的架构与接手说明 | 网页必填；Node 的可选说明组之一 |
| `database` | 表、字段、单位、关系和删除规则 | 网页必填 |
| `platform` | 平台 SDK、数据和运行接入说明 | 网页必填 |

Node 保持现有可选规则：可以省略整个 `documentation`；如果声明，必须提供 `readme` 和 `development` 两个独立且存在的文件。新建模板默认生成这两份资料，但不因此把它们升级为所有 Node 应用的准入条件。任何已声明文档路径均须指向实际存在的文件。

网页原 `docs.readme` 主要是开发交接资料，在新结构中对应 `documentation.development`；不能只改字段名称就把其内容当作用户指南。是否进一步统一两类项目的文档必需要求，保留为待确认项。

## 6 应用标识和本机实例身份

`app.id` 表示作者应用标识，建议使用反向域名形式。平台新建项目时生成一次独立的作者应用标识并保存到源码；它不取自本机实例 UUID。新模板明确提供初始应用版本，不为旧项目补造作者版本。

本机实例 UUID、目录及文件身份、数据归属、用户配置、密钥、日志、窗口状态和删除归属由平台内部登记维护。网页运行上下文也要从登记取得实例 ID，再与作者清单组合，不能继续依赖作者 JSON 中的本机 `id`。

同一份应用添加为多个实例时，作者应用标识可以相同，本机实例和数据必须独立。普通复制和完整 ZIP 导入继续分配新实例 UUID；修改已有实例的名称、作者 ID、版本、入口或有效配置声明，不创建新实例，也不重新分配数据。

已经登记的运行类型，以及网页数据库、附件的归属变化，不通过普通清单编辑自动切换。类型转换和数据迁移不在本轮开放。Node 继续使用 `APP_DATA_DIR`、`APP_CACHE_DIR`、`APP_TEMP_DIR`，不会因新清单获得网页项目 SQL 或附件接口。

## 7 旧字段的整理方向

下表用于审阅新字段的职责，不表示提供自动转换工具。

| 当前字段 | 新结构或处理方式 |
| --- | --- |
| 网页 `id` | 本机实例身份留在内部登记，不转成 `app.id` |
| 网页 `name`、`description`、`icon` | `app` 内对应字段 |
| 网页 `sdkApiVersion`、`database`、`attachmentsDir` | `platform` 内对应字段 |
| 网页 `sourceDir`、`build.script` | `development.sourceDir`、`development.build` |
| 网页 `outputDir` 和根相对 `entry` | `web.root` 和相对该目录的 `web.entry` |
| 网页 `docs` | 按文档实际角色放入 `documentation` |
| Node `app`、`web`、`backend`、`configuration` | 保留主要结构，采用统一校验 |
| Node `development.outputDir` | 不作为另一份产物位置；最终入口由 `web`、`backend` 声明 |
| `packageFormat`、`formatVersion` | 新清单不保留，改由文件名及 `manifestVersion` 识别 |
| Node 已停止参与运行判断的 `dataContract` | 不作为新清单的平台契约字段，不提供数据兼容或迁移保证 |

## 8 校验和格式切换

所有入口共用清单定义和语义校验，再按运行类型检查条件字段。拒绝重复键、未知字段、不支持的版本或类型、字段矛盾、路径越界和缺失运行入口；保留现有图标无效时的默认图标回退。

目录检查只读，不自动补字段、改文件、登记或启动。配置缺失、依赖准备提示与清单格式错误分开表达，检查通过不表示实际运行已经通过。

按[项目完整删除约定](project-complete-deletion.md)，建议本次切换只支持新清单，不新增旧项目兼容、旧残留清理或自动迁移工具。

| 目录情况 | 切换后的行为 |
| --- | --- |
| 只有有效 `panda.json` | 按对应入口的现有能力检查和接入 |
| 只有旧 `project.json` 或 `local-app.json` | 明确提示旧格式需要适配，不静默回退读取 |
| 同时有新旧清单 | 提示声明冲突，不猜优先级，不自动删除文件 |
| 没有清单 | 沿用空目录生成或非空目录评估流程 |

本次切换不批量改写已有目录，不删除旧项目和用户原始文件，不修改固定开发应用身份或数据根。现有开发残留仍由用户自行处理；格式不支持不能触发空库重建或数据归属重绑。

新导出的完整项目 ZIP 使用 `project/panda.json`，归档格式由当前版本 `1` 提升为 `2`。作者清单中的 `manifestVersion: 1` 与 ZIP 版本独立。旧归档和旧 Git 历史不提供自动转换或清单别名读取；读取不支持格式时明确说明原因。

## 9 需要一起调整的流程

| 范围 | 必须处理的事项 |
| --- | --- |
| 模板和新建 | 网页和 Node 都生成唯一新清单、独立作者应用标识和正确说明资料 |
| 本地与 Git 添加 | 统一识别与诊断，保持依赖准备和非执行检查的边界 |
| 登记和运行 | 分离作者清单与本机实例身份，保持后端协议、配置快照及关窗收尾 |
| 网页构建 | 更新清单输入、构建摘要和产物来源，保持旧窗口对当前实际产物的占用保护 |
| 元数据与详情 | 名称、简介、图标、类型、入口和配置说明读取同一清单 |
| Git 保存与取回 | 更新清单路径和身份核对，不通过放宽校验绕过不支持的历史 |
| ZIP、复制和导入 | 更新归档版本、路径、摘要和实例分配规则，不更改业务主键 |
| 删除和工作区操作 | 沿用既有独占归属与平台能力边界，保留外部原始目录和已完成外部交付 |
| SDK、CLI、AI 说明 | 更新清单名称、路径语义及示例，不自动升级项目 SDK |
| macOS 和 Windows | 业务定义共用，原生文件处理经过平台适配层，两套 CI 都通过 |

这项变更不能只替换文件名。尤其需要清除把作者清单 ID 当作本机身份的依赖，并同步构建摘要、Git 核对及完整 ZIP 的格式契约。

## 10 实施批次

| 批次 | 内容 | 完成标准 |
| --- | --- | --- |
| 1 规范定稿 | 确认名称、字段、条件必填和切换范围，补 Schema、两类完整示例与错误用例 | 规范内部一致，示例与校验规则一致 |
| 2 公共解析和登记 | 建立统一读取与校验，从内部登记组成运行上下文 | 两类新项目的身份和路径来源正确；尚不切换默认入口 |
| 3 创建和日常运行 | 接入模板、新建、本地、Git、详情、配置、启动停止和网页构建 | 一次性测试项目可以完整创建和运行 |
| 4 生命周期对齐 | 更新 Git、构建摘要、ZIP、复制、删除和既有工作区流程 | 对外流程不再依赖旧作者清单，不丢失数据和归属保护 |
| 5 切换和交付 | 关闭旧格式入口，更新文档、CLI、SDK 说明与 AI 提示词，完成两平台检查 | 新流程只交付一份作者清单，相关回归和实际验收通过 |

正式切换默认入口前，批次 2 至 4 的完整链路需要同时满足要求。每个完整批次通过相关检查后提交并推送；不提交未完成的并行改动或本地测试证据。

## 11 验收要求

- 网页和 Node 项目均只有一份 `panda.json`，必填、可选与禁止字段按类型正确校验。
- 两类模板生成的文件和文档真实存在；平台网页可以使用 SDK、SQLite 和附件，并通过原有构建流程更新产物。
- Node 可以打开、健康检查、配置和正常关窗停止；配置保存不自动启动，控制协议和秘密处理保持现有规则。
- 同一作者应用的多个实例独立保存数据、配置和网页存储；改名称、版本或作者 ID 不改变实例归属。
- 缺配置、缺依赖、入口缺失、清单错误和未知版本分别给出准确提示；只读检查不修改作者目录。
- 构建或添加失败不清空业务数据；已有窗口的产物占用和实际后台收尾仍受保护。
- 新格式 Git 操作、ZIP 导出导入和复制符合各平台现有支持范围；旧格式被明确拒绝，不隐式转换。
- 删除仍覆盖平台管理内容，并保留用户选定的外部原始目录、原始导入 ZIP 和已完成外部交付。
- macOS 与 Windows CI 均通过；需要实际原生验证的项目单独记录，不能用模拟界面或单元测试代替。

所有验证使用明确命名、可丢弃的项目，不使用现有业务项目做删除或格式切换实验。
