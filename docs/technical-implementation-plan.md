## 1. 最终目标与本次取舍

让普通用户借助外部 AI 制作自己的小应用，也能通过仓库链接或应用包获取别人制作的应用，在本机稳定使用、保存业务数据、定制和分享，减少复制代码、操作终端和配置环境的负担。

长期保留四条路径：自己制作自用、获取他人项目、定制修改、分享自己的项目。本轮只补齐前三条，修改定制须包含真实 Codex 接手和更新后的使用验证；分享暂缓，不删除历史目标或改写此前记录。独立备份产品不再是目标，也不再作为安装、更新和分享的完整前置工作。

用户此前提出数据库应纳入 Git，`dist` 是否提交仍待评估，这两点继续保留。Git 不可用时，版本保存能力明确不可用，不另外生成 ZIP 备份；成品的普通安装和运行不因此要求用户配置 Git。

## 2. 从计划中移除的内容

- 新建手动/自动 ZIP 备份、备份历史列表、保留份数、独立恢复中心和备份任务体系。
- 上轮提出的“每项目私有 Git 恢复仓库”。不以 Git 为存储继续建设另一套备份管理系统。
- 为新 Node 类型补建完整 ZIP 备份、带数据复制和复杂回收管理，并将其列为安装前置。
- 每次更新先做全量项目备份的强制要求，以及依赖 ZIP 基线的独立维护工作流。
- 以完整跨电脑备份恢复作为首个四场景闭环的验收条件。

保留最小运行和写入协调：候选构建、必要校验、操作互斥、替换时停写、成功后切换、失败保留当前可用版本、重启识别未完成操作。这些只保证当前操作正确完成，不产生另一套长期备份历史。

功能退役与删除资料分开：既有项目、旧 ZIP、维护/恢复现场、回收内容及唯一 Git 历史原样保全；旧格式读取可隔离为兼容导入，未完成事务仍需识别处理。改造完成前，旧代码的存在不代表它仍属于未来产品范围。

## 4. 工具和数据的建议规则

以下规则按步骤落实，不等于全部已交付。Git-only 取舍已由用户确认；Node/npm 与 Git 工具默认来源已按下文第2项独立子步实现。SSH 目前仅检查系统工具版本，SSH／HTTPS 认证、仓库目录与操作支持范围仍在后续步骤落实，不把工具可用当作认证已通过。

| 对象 | 建议规则 |
| --- | --- |
| 应用运行 Node | 固定使用平台提供且验证过的运行时；不因电脑里有另一个 Node 而自动切换 |
| 构建 Node/npm | 新用户默认受管工具链；有环境的用户可明确选择兼容的本机工具，保留已有显式选择；Node/npm 配套使用 |
| Git | 默认内置私有工具，也允许明确选择兼容的本机 Git；实际路径与版本可查看，失效时不偷偷换来源 |
| SSH/HTTPS 认证 | 工具与认证分别选择；首批支持已有系统 SSH 的复用，随后适配受支持的 HTTPS 凭据助手；无环境用户可先通过 HTTPS 获取公开项目，不强制配置 SSH |
| 外部 AI | 交接真实项目路径和构建入口；AI 使用自己的工具环境，最终产物通过平台目标环境验证；不擅自改用户全局 PATH |
| 源码和版本 | 使用项目标准 Git 仓库；查看改动、提交、分支和取回版本由 Git 完成，避免平台与 AI 同时修改仓库状态 |
| 数据库和附件 | 在用户触发的 Git 保存流程中，生成数据库一致性文件，并包含所需附件；提交后保留仓库内受跟踪的当前快照文件，只清理提交前暂存文件，历史只在 Git 中保存；不对活库直接执行 checkout/reset |
| Git 范围 | 新项目统一明确 Git 根与数据快照目录；已有仓库若只覆盖源码，不暗中搬根或新建备份仓库，先明确是否扩展纳管及兼容方式；不支持时如实提示未包含数据库 |
| dist | 仍待评估。完整源码和依赖可重建时可不进入开发提交；无源码成品必须有运行文件。发布包与 Git 提交是否包含 dist 分别决定 |
| 秘密与远端 | 已知 API Key、SSH 私钥和令牌排除；含数据库的提交按私密内容处理，推送范围明确，不自动推向作者公开仓库；没有通用数据库脱敏承诺 |

Git 是本地版本机制，推送到远端是另外的操作。数据库版本取回必须由用户明确选择，不能因为切换源码分支就覆盖当前业务数据。第一版程序更新优先保持相同数据格式，不引入自动数据迁移和任意跨版本数据回滚。

## 6. 旧代码退役的准确边界

- 初始盘点中 `control.rs` 以 ZIP 文件存在判断旧维护基线，`maintenance.rs` 新建维护和恢复前操作、`lifecycle.rs` 导入／复制会产生 ZIP 基线。2026-10-24 已关闭新建及恢复前 ZIP 生成、解除新实例基线依赖；旧状态读取与收尾仍保留，见[退役实际边界](backup-retirement-admission-step.md)。
- `backups.rs` 的 SQLite 一致性函数、文件校验可供 Git 数据提交复用；ZIP 读取保留兼容，压缩工具若仍用于分享/导出就按实际调用保留。模块名字不决定是否整文件删除。
- 持久“维护中心”退出日常新流程；替换程序或数据时的短暂停写与进程收尾保留为内部操作步骤。普通源码编辑和 Git 提交不要求先生成全量基线。
- 构建/安装的候选目录与提交日志只服务当前操作。确认成功后按规则收尾，不新增长期可浏览的恢复历史；旧的未解决现场不自动清理。
- 已有回收与工作区迁移保护继续识别旧资料，不因取消备份就随便删目录。带数据复制继续按使用价值收敛；2026-10-23 确认新删除直接永久执行，旧回收内容保留兼容，不将复杂回收扩展作为新 Node 的前置。
- Git 操作不能代替应用实例登记、SQLite 停写或同机工作区迁移；固定开发身份、数据根和公开迁移要求继续执行。
