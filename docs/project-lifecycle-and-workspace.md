## 1 首版范围

| 操作 | 用户得到什么 | 身份与数据规则 |
| --- | --- | --- |
| 导出项目 | 一个包含当前源码、网页产物、数据库和附件的 ZIP | 保留项目 ID，不携带本机会话与管理凭据 |
| 导入项目（默认） | 把归档中的内容变成一个独立新项目 | 新项目 ID，允许重复导入；原归档不修改 |
| 复制项目 | 在当前工作区生成独立副本 | 新项目 ID；保留业务数据，不改业务主键 |
| 删除项目／应用 | 确认后直接永久删除所选实例，不进入平台或系统回收站 | 受管源码、数据、备份、恢复、任务及迁移副本一并删除；外部原始目录保留 |
| 迁移工作区 | 把全部项目和平台持久状态移到新位置 | 保留项目 ID；同一台电脑一次只使用一个工作区 |

第一版不增加无数据模板包、只导入某张表、两个工作区合并、跨设备同步或批量冲突合并。迁移入口用于同一台电脑更换目录或磁盘；换电脑先使用项目导出与导入。若以后需要把历史备份、回收站和维护现场完整搬到另一台电脑，再定义整工作区交接格式。

## 2 项目身份与操作协调

### 2.1 新实例永远用新身份

新建、下载、导入和复制均分配新的本机 UUID，名称、业务主键和作者 `app.id` 不决定本机身份。编辑现有实例与正常公开工作区迁移保留其 ID；重新导入归档一律重新分配，不提供 `original` 模式或旧回收站恢复。

项目删除成功后清除登记与文档代次，不留 retired 墓碑；会话绑定真实已登记 epoch，注销时清除 cookie 会话与未使用票据。旧 ID 缺少有效登记即不能认证，不以两个空 epoch 相等作为身份。项目名称、图标与业务 UUID 各自保持原有语义。

### 2.2 沿用现有任务和维护模型

所有长操作复用 `queued → running → succeeded | failed | interrupted`，具体步骤放在 `phase` 和进度信息，不增加项目持久模式。项目仍只有 `ready` 和 `maintenance`；旧回收站属于历史登记位置，不是第三种运行模式，新删除不再产生回收项。

导出、复制、删除与构建、备份、恢复共享项目操作互斥。导入预留目标 ID；迁移持有工作区级互斥。冲突返回明确忙碌原因，不强行中断正在提交的数据操作。CLI 等待超时后按任务 ID 查询，不盲目重试创建副本或迁移。

平台只能协调自己接收的请求。外部 AI、编辑器和 SQLite 工具需要按操作说明暂停直接修改；平台不能把自身互斥描述成系统级文件锁。维护中的导出、复制和删除要求提供当前 `maintenanceId`。导出、复制等操作仍受恢复门禁保护；永久删除可清除静态待恢复材料，但必须先排空真实写入者。

平台提交的项目名称、简介和图标修改同样与上述项目操作互斥；正常模式下可直接修改，维护中则必须携带当前 `maintenanceId` 且 `readyForChanges: true`，恢复待处理时禁止修改。项目概览在维护、未构建或业务数据库损坏时仍可由平台读取元数据并显示诊断，不为展示概览执行项目网页或业务脚本。

### 2.3 未来 Node 类型的生命周期前置条件

Node 应用在开放前必须把受管后端纳入项目/工作区门禁：备份、导出、复制、进入维护、恢复、删除和工作区迁移涉及快照或目录操作时，先停止新业务、排空、停止后端与受管子进程并核实退出。Node 直接写文件不受现有平台 API 冻结约束；无法确认停写时阻止后续操作，不能用强杀后直接移动目录代替数据检查。恢复现场、维护状态、备份和 WAL/SHM 的既有保护继续有效。当前 Node 独立槽的直接删除按[删除契约](application-deletion.md)执行，不因此具备其他 project-v1 生命周期能力。

可运行后端产物及完整依赖须纳入未来版本的归档清单；当前源码 `node_modules` 的缓存排除不能导致恢复后失去唯一运行依赖。导入、恢复和回收站恢复的校验/登记不执行应用代码或安装脚本，也不自动启动后端。进程、端口、实例凭据等本机标识不随 ZIP 或迁移复用；复制实例的数据归属和目标系统依赖须在新格式中另行校验。

普通快照完成后的原服务恢复、维护结束后的启动以及平台异常退出后的残留处理，按新增方案分别验收；后端启动成功不能自动解除维护、处理恢复日志或让旧页面取得新代次。以上为未来类型的准入要求，目前没有新增可调用的 Node 生命周期接口。

### 2.4 Node 配置与凭据的历史候选策略

本节保留早期系统凭据库候选，不作为当前 Node 文件槽的执行规则。当前直接删除会移除选中实例的本机私有配置及秘密文件，外部引用目录和旧 Keychain 条目保留；以[本机配置契约](node-native-configuration.md)和[直接删除契约](application-deletion.md)为准。

用户通过表单填写的普通配置拟作为实例私有持久数据，不默认发往业务网页；新类型私有完整归档明确携带普通值，原实例恢复后恢复快照值并按声明重验，分享默认去掉本机配置值。秘密值拟存入 OS 凭据库，不进入 `.env`、源码、项目数据库或日志；任何项目 ZIP（含完整备份、导出和分享）既不含秘密值，也不含可直接使用的凭据绑定。用户配置、OS 凭据绑定和平台短期控制凭据分别归属，不能互相充当。

| 操作 | 候选处理，不是当前已实现行为 |
| --- | --- |
| 同机恢复原实例 | 保留当前本机凭据绑定，不把 Key 回滚到备份时点；缺失或不兼容时要求重新填写；普通配置按快照恢复并重验 |
| 复制、导入新 ID | 新实例不继承可用秘密绑定，普通配置随新类型快照处理，必需秘密重新填写后才能启动 |
| 工作区迁移 | 仅通过现有公开迁移流程保持项目身份及本机绑定，不用绝对目录复制凭据、不新增换根捷径 |
| 移入/恢复回收站、卸载程序 | 不自动删除 OS 凭据，回收项和本机绑定继续按身份保护；恢复不自动启动 |
| 永久清除或凭据删除 | 不借现有目录清除连带删除凭据；永久删除秘密另行明确设计和授权，未识别/未解决控制现场仍保留 |

同 ID 的陌生归档不能单靠名称或 ID 获得已有凭据。绑定必须核对本机实例身份和已接受的生命周期操作；不能确认时先保留记录并阻止自动使用。具体规则按[配置契约草案](node-app-configuration.md)与新类型格式定稿后验收，不表示已向当前生命周期 API 增加配置功能。

## 3 导出：生成完整、可移植的当前快照

### 3.1 内容与格式

复用 `backup.json + project/` 的完整 ZIP，包含项目持久文件：清单、README、其他文档、`meta/` 图标与项目资料、源码、锁文件、本地 SDK 包、当前完整网页产物、独立 SQLite 副本和附件。排除项沿用备份契约，仅限已识别工程依赖根、构建缓存、平台日志与控制、凭据和会话；用户附件中的同名 `node_modules` 或隐藏目录仍是持久文件，不按名称递归忽略。

浏览器偏好或可丢弃缓存不导出；业务数据原本就必须写入项目数据库或附件，不能依赖某个浏览器的私有存储才能恢复。项目导出只包含一个项目当前快照，不递归包含其历史备份、回收站或平台操作现场。

`workspace/.platform/cache/storage/projects/<projectId>.json` 与工作区汇总 `workspace/.platform/cache/storage/workspace.json` 是可重建统计，不随单项目归档。平台自身名称、图标、版本和安装位置来自当前安装包；固定位置的 `appLocalDataDir/cache/storage/platform.json` 也不进入项目归档，不能随项目导入覆盖当前平台信息。

在既有归档元数据中新增可选的 `snapshotState`，值为 `ready`、`maintenance` 或 `unknown`，仅说明快照生成时的状态，不携带 `maintenanceId`、令牌、旧基线路径等本机控制信息。缺少该字段的旧归档按 `unknown` 处理；该可选字段作为既有格式的兼容扩展。

同时保留平台已知的未完成构建提示；来源缺少记录或外部文件变化无法确认时，标记需要检查，不能把缺少记录解释成“源码已完成构建”。这些提示用于导入后的维护检查，不复制原机器的任务日志。

归档的可选 `buildProvenance` 按主约定第 7.4 节和备份契约携带输入/产物关联及工具版本，导入时重建本机记录并核对，不依赖原任务仍存在。来源缺失显示未知；正常项目仅有“源码已修改、仍运行旧产物”的展示状态，不因导入或复制自动变为维护。维护快照已知的待构建要求则继续保留，两者不能合并为同一个状态。

状态提示既不是业务验收证明，也不是归档可信来源的签名。维护中可能存在源码、数据和产物尚未匹配的中间态，导入时不能因为 ZIP 校验通过就自动解锁。无法生成有效 SQLite 副本的损坏项目不伪装成正常导出；保留和修复原现场仍走已有维护恢复方案。

### 3.2 产品流程

1. 用户选择项目和“导出当前项目”，选择保存位置；默认文件名包含展示名称和时间，身份以归档内容为准。
2. 检查项目状态、空间和目标路径；拒绝把导出目标放进正被快照的项目持久目录，以免自包含。已有同名文件或已登记路径时必须选择新名称。
3. 使用已有备份流程短期冻结业务，生成一致的不可变副本；外部文件修改同步暂停。
4. 副本完成后解除临时冻结，保持原来的持久模式，再压缩与校验。
5. 在目标目录先写有明确临时标识的文件，校验完成后发布最终 ZIP；任务结果给出路径、项目 ID、快照时间、校验信息和当时状态。只有最终文件发布成功才报告导出成功。

目标磁盘掉线、空间不足或应用崩溃时不登记一个看似完整的导出；未完成文件标记为临时，原项目继续保留。导出必须使用新文件名，不覆盖现有文件。2026-10-29 用户明确：保存在用户选定外部文件夹的最终 ZIP 属于外部交付，删除项目时保留；网页下载及附件另存副本遵守同一边界。平台 snapshot／archive、内部 stage 及外部发布 `.partial` 文件仍为本项目独占材料，写入前登记身份，失败或删除项目时清除；成功发布后不保留最终文件归属。原始导入 ZIP 保留，不追溯旧导出。

“另存历史备份”是独立入口：用户选定某份已验证备份后复制到外部位置，展示原快照时间；不把它称为刚导出的当前状态。直接导出不必额外永久保存一份本机手动备份，任务完成后可清理安全的暂存副本；现有备份保留规则不变。

## 4 导入：先验证，再登记，不运行项目脚本

### 4.1 输入与验证

第一版导入入口只接受平台完整 ZIP；任意工程文件夹不等于符合平台约定的项目，目录收养可后置。导入过程中不执行 npm、构建脚本或项目网页，不要求系统安装 Node。

归档先解包到工作区 `.platform/operations/<taskId>/candidate/`，不直接写入 `projects/`。验证包括：

- 归档格式、文件清单和 SHA-256；路径不能越界，不能含重复条目或符号链接。
- 目标文件系统上的大小写与 Unicode 名称冲突、解压大小及文件数量限制；遇到歧义拒绝，不悄悄覆盖同名文件。
- `project.json`、清单与归档的项目 ID 一致，声明路径合法，接口主版本受当前平台支持。
- SQLite 可打开、完整性检查；外键检查单独报告，不能把 `integrity_check` 成功当作外键正确。
- 源码、锁文件、SDK、文档和声明的网页资源是否齐备；允许原本没有 `dist/` 的“尚未构建”项目，不能把声明存在而丢失的产物当正常。

校验失败保留原 ZIP，不登记可用项目；返回具体原因。结构和校验值正确但存在可修复的外键问题时，可登记到维护状态供 AI 修复。无法打开或完整性检查失败的数据库不作为成功导入，损坏数据抢救另行处理。

可选图标未设置时正常使用默认图标；已声明引用的文件原本缺失或图像无法作为静态 PNG 解码时，登记后显示默认图标与警告，不单因此阻断项目使用。若归档文件清单已承诺该文件存在，却在解包后缺失或校验失败，仍属于归档不完整，必须拒绝；非法归档路径同样不豁免。导入名称、简介和图标采用归档内的项目资料，不拿同 ID 的旧列表缓存补回。

### 4.2 每次导入新身份

CLI／管理 API 省略 `mode` 或显式指定 `copy` 时，均生成新的本机实例 UUID，允许重复导入和自定义名称。`original` 模式已移除，不保留归档本机身份；平台不全局改写业务主键、用户文字和附件名称。

验证完成后，为新目标建立独占归属和本机控制状态，提交候选与登记。原始归档不修改；失败不影响其他实例。提交后的构建、维护、恢复和任务材料都归新实例，不由来源项目共享。

### 4.3 导入后的运行状态

| 归档情况 | 登记结果 |
| --- | --- |
| `snapshotState: ready`，机械检查通过，产物完整 | 登记为 `ready`，用户可以打开已带产物 |
| 同上，但明确没有构建产物 | 登记为 `ready`，显示“尚未构建” |
| `maintenance`、`unknown` 或缺少状态字段 | 建立新的本机维护，验证与明确结束后开放 |
| 数据库完整但有外键问题 | 保持维护，展示问题，允许 AI 修复 |
| 格式、路径、校验或数据库完整性不通过 | 导入失败，不登记可运行项目 |

导入维护项目时生成新的 `maintenanceId`，不复用另一台电脑的维护会话。建立可用本机基线后才设置 `readyForChanges: true`。原 ID 导入可将验证后的来源归档存入本机备份区；相同备份 ID 且内容相同可复用，ID 相同而内容不同则报冲突，不覆盖历史文件。

新副本的 ID 已改变，原归档不能直接充当这个新 ID 的恢复基线：应先调整候选项目身份，再生成属于新项目的新基线归档和备份 ID。原归档保持原样，只记录来源关系。基线准备失败时保持维护且不开放管理修改，重试准备步骤。

导入不会升级 SDK、锁文件或文档。正常快照中可复用的产物可以直接使用，不要求为了换位置重新构建。维护或 `unknown` 快照必须继续保留待检查、待构建提示；新建基线只提供回退依据，不证明源码、数据库与产物已经匹配，不能借复制清除原先未完成的构建要求。已知尚未成功构建的源码改动仍须构建；未知情况在结束维护前显式检查，不能确认原产物可复用时先构建。只有确认可复用的原产物才沿用免重建规则。

合法无已发布产物的 `unbuilt` 状态沿用备份维护契约的例外：其他检查通过可结束为 `ready + unbuilt`，保留待构建信息且不开放业务网页。意外缺失或损坏的既有产物不能冒充此状态。

随后编辑源码或上述检查要求构建时，才需要服务选定的配套 Node/npm 和正常构建流程；当前 Mac 内部包默认受管工具，已有显式本机选择保持优先。首次重新构建执行对应锁文件的依赖安装，不能依赖原电脑的 `node_modules`。

首次打开由用户或明确工具调用触发，不在解包验证过程中自动运行。导入范围仍是用户信任的自建项目；结构验证不把任意第三方 JavaScript 变成安全代码。

## 5 复制：独立内容副本，不改业务身份

平台上的“复制项目”相当于“生成一致快照 → 以新 ID 导入”，可复用不可变暂存副本以减少中间压缩，不必让用户手动导出和导入。源项目只短暂冻结；新项目初始化与源项目互不影响。

复制内容包括数据库记录、附件、源码、文档、`meta/` 项目资料、固定 SDK、锁文件和当前产物；数据库、附件与图标文件是独立副本，不以硬链接或指向源项目的路径共享可写内容。默认名称为“原名称 · 副本”，也可指定其他名称；简介和图标默认保留，最终以新 ID 区分，同名并不构成冲突。

平台只更新 `project.json` 中的 ID、可选名称，以及明确归平台管理的交接信息。业务主键、UUID、文件内业务引用和用户编写的文字不批量替换。README 只有带明确平台管理标识的交接区可以定点更新；没有这种标识时另行生成交接说明，不覆盖用户或 AI 的说明。

标准项目应通过 SDK 获取运行时 ID、采用相对资源路径，因此复制后可以直接打开既有产物。平台检查入口与资源声明，但不承诺自动修复任意业务代码中写死的旧 ID、端口、机器路径或外部服务目标；这些问题交给 AI 修改源码并构建。复制成功也不代表任意业务流程已经验收。

构建摘要不包括项目 ID、展示名、简介、图标字段、`meta/` 项目资料、根 README 的交接信息及机器位置，复制或管理修改仅改变这些内容时不重建产物、不要求 Node，也不伪造一次新成功构建；来源保留原完成时间，摘要仍按相同规则核对。业务网页实际打包的 `app/public/` 图标仍属于构建输入。业务源码真有改动时正常显示差异，不能用“复制过项目”或修改元数据消除原有待构建要求、解除维护。

源项目处于维护时，新副本也进入独立维护，并建立新 ID 的基线；不会把源项目的维护 ID 或旧基线引用搬过来。源项目保持原来的维护状态。历史备份、任务日志和恢复现场不随单项目复制；需要完整移动这些内容时使用工作区迁移。

## 6 完整永久删除

删除整个项目根（含 Git、未提交修改、数据库及附件），清除目录外的独占登记、构建、维护、备份、恢复和任务材料，以及公开迁移保留的本项目旧副本。只按本项目受理的归属处理，不扫描是否还有其他项目引用，也不使用共享引用计数。其他项目、外部原始输入和平台全局运行环境／设置不随项目删除。

先阻止新写入，等待实际进程、数据库及 IO 完成，再删磁盘和内存。静态恢复记录不是保留项目的理由。成功不保存删除任务或旧身份注销文件；响应丢失时，只有目标的全部受管范围均已缺失才按成功返回。失败保留当前可重试范围，不报告已完成。

旧回收站流程、旧删除任务和旧网页删除记录兼容已退役，不新增迁移或旧残留清理工具。现有开发残留由用户重置；删除回归只使用临时项目。

## 7 工作区迁移：整体复制，验证后提交位置

### 7.1 范围与目标限制

Mac 首版支持本机内置磁盘及直接连接的外置磁盘，目标使用 APFS，目录可写、为空且独立。APFS 是当前 Mac 的标准文件系统之一，见 [Apple 文件系统说明](https://support.apple.com/en-euro/guide/disk-utility/dsku19ed921c/mac)；把 Mac 首版迁移目标限定为 APFS 是产品支持范围，不是声称 SQLite 无法用于其他文件系统。Windows 起步范围已确认为本机内置 NTFS、固定默认工作区，卷/路径/权限保护仍待实现；这不开放迁移入口。外置盘、网络/映射盘、同步目录和 Windows 迁移目标另行评估，同机迁移实现与验收后置至 W3.7，不把当前 APFS 实现视为已经支持 Windows 迁移。

不将活跃工作区放到 NAS、网络文件系统或由 iCloud Drive、Dropbox 等同步的目录中；已完成的 ZIP 可以另存或转移。SQLite WAL 依赖同一机器的协调机制，不支持跨机器的网络文件系统用法，见 [SQLite WAL](https://www.sqlite.org/wal.html)。平台应说明限制并检测能够识别的位置，不宣称能识别所有第三方同步目录。

目标不能与源相同，不能是源的父目录或子目录，不能放进 `.app` 或固定运行配置目录。默认工作区位于固定应用数据目录下，因此这里禁止的是 `runtime/`、迁移日志等控制目录及其父目录整体作为目标，不禁止选择一个独立的数据子目录。先解析实际路径检查，再进行写入。

### 7.2 搬什么、不搬什么

| 内容 | 迁移处理 |
| --- | --- |
| 所有项目持久文件与当前产物 | 完整搬迁，项目 ID 不变 |
| 本项目的备份与恢复现场 | 完整搬迁，登记新旧副本的独占归属 |
| 当前维护状态、代次及必要基线引用 | 完整保留，不能迁移后自动解锁；不保留已删除项目的注销墓碑 |
| 操作日志、受保护原现场、必要任务记录 | 完整保留，不能把整个 `.platform/` 当缓存忽略 |
| 活跃项目中的源码构建 `node_modules`、明确可重建缓存 | 可排除；现有静态产物仍可用，重建时重新安装依赖；不作为未来 Node 运行产物的排除授权 |
| `workspace/.platform/cache/storage/` 统计缓存 | 可排除并在新位置重建；原统计不能作为新根目录的有效结果 |
| 活跃进程锁、PID、端口、套接字等运行标识 | 不搬迁复用，在新位置重新建立 |
| 本机设置、Node 路径、管理令牌、服务发现 | 留在固定应用数据位置，按切换结果更新 |
| 平台安装包元数据及 `appLocalDataDir/cache/storage/platform.json` | 属于本机平台安装与统计，留在固定位置，不随工作区搬迁 |

上述排除规则仅适用于已识别的活跃项目可重建目录及允许清理的缓存，不进入受保护的 `original/` 等恢复现场内部递归过滤。当前受管恢复目录不能因其内部文件恰好名为缓存目录而被省略。

固定位置采用以下布局：

```text
appLocalDataDir/
├── settings.json                        当前 workspaceRoot
├── runtime/                             服务发现与当前管理凭据
├── cache/storage/platform.json           可重建的平台安装占用统计
├── migrations/<taskId>/
│   ├── journal.json                     源、目标、阶段、验证和提交记录
│   └── task/                            本次迁移任务状态与日志
└── workspace/                           默认数据位置；迁出后是旧副本
```

迁移日志和本次任务记录必须位于迁移树之外，否则复制进度本身会不断修改源文件，且迁移失败时找不到依据。其他任务仍按既有工作区任务目录保存；管理端的任务查询统一处理这项存储位置差别。平台启动时先读取固定迁移日志，再打开当前工作区。

工作区内部的持久引用使用相对路径或稳定 ID，迁移不依赖全局搜索替换绝对路径。平台生成的 AI 交接信息在新位置重新生成；用户业务文档中的任意绝对路径不擅自改写。

`project.json` 和 `meta/` 随项目持久内容搬迁，名称与图标不因换位置改变。空间缓存按工作区与根目录身份校验；提交新位置后，全部项目和汇总统计均需重新生成，即使某份旧缓存随文件复制也不得当作当前有效结果。扫描结果注明统计时间与完整性，尚未扫描不显示为零占用；平台安装包占用仍来自本机安装位置的独立统计。

### 7.3 执行顺序与提交点

1. **预检。** 展示源、目标、预计空间和迁移范围，检查目标支持条件。空间估算包含完整副本；源文件要保留到切换成功以后。
2. **停止新工作。** 建立工作区级入口限制，等待已有构建、备份、恢复和生命周期任务结束，再暂停全部项目业务访问。固定目录中的任务状态保留；真实 I/O 围栏期间查询暂不可用时继续等待，不重复提交迁移，不强杀提交中的事务。
3. **关闭并固定源目录。** 外部 AI、编辑器和 SQLite 工具停止修改与访问。关闭所有平台数据库和文件句柄，停止向源目录写日志；本次迁移记录写到固定位置。仅有已暂停的维护可以迁移；任何未解决的 `recoveryRequired` 先处理再搬迁。
4. **复制到目标暂存。** 搬迁范围覆盖全部持久状态；只排除明确可重建内容和运行期标识。已关闭数据库后仍存在的 WAL/SHM 与所属数据库一并保留，不能只复制 `main.sqlite`；受保护的损坏现场保持原样。复制期间源项目不重新开放写入。
5. **校验。** 核对目录、文件清单和校验值、项目 ID、控制格式及引用完整性，确认目标可用。迁移不会执行项目脚本或为全部项目重建。已知损坏且被阻断的项目/现场不因迁移被删除，也不冒充健康；源数据新增变化则停止提交，返回源位置重新协调。
6. **提交新位置。** 目标完成校验并安置到最终工作区根目录、相关记录持久化后，更新固定设置中的 `workspaceRoot` 并持久保存，作为切换提交点；设置不能指向尚未安置完毕的暂存容器。日志记录提交意图与结果，重启可对照设置核实；不声称设置、标记和多个文件可以跨磁盘一次原子提交。
7. **重新开放。** 只在新位置初始化运行，刷新服务实例和管理凭据及发现文件。保留各项目维护模式与历史代次，在目标位置为活跃登记项目单调推进 `documentEpoch` 并持久保存，再开放业务；此步骤纳入迁移日志，崩溃后先核对补齐。普通页面重新建立会话并加载新文档，同浏览器的新 Cookie 不能使迁移前旧文档恢复写入，已接受的旧实例写入不自动重放。生成指向新位置的 AI 交接说明。
8. **自动收尾原目录。** 2026-10-29 起，新迁移只有在新位置实际重新打开、旧管理器及 HTTP／附件／原生后台真实排空后，才核对原根身份及提交时的复制清单并删除。新位置正常写入不参与旧内容逐字比较。失败保留精确残留路径，当前新位置继续可用，通过设置页或 `workspace cleanup-retry MIGRATION_ID` 重试；旧 journal 不取得新删除权限，也不进入手动历史候选。范围与收据见[收尾及历史资料规则](history-cleanup.md)。

桌面已有项目窗口在迁移中显示暂停，完成后提示重新连接；明确重载时取得新入口，不因复用窗口就继续使用旧实例。普通浏览器端口变化时需重新打开平台地址。构建来源与输入基准随持久状态迁移，路径归一化使位置变化不成为源码修改。

对所有项目的自动数据库修复不属于迁移。校验的目标是完整搬走已有数据与状态，不要求用户先把原本损坏的历史现场修成健康项目；不能为方便迁移删掉保护记录。

### 7.4 中断与失败

| 时点 | 恢复规则 |
| --- | --- |
| 新位置尚未提交 | 源仍是唯一当前工作区；记录失败后可以从源恢复服务，目标残留保持未激活 |
| 提交状态不明 | 启动时核对固定设置、日志和目标标记；不能核实时保持停用，保留两边 |
| 已提交，尚未完成重启服务 | 根据日志继续初始化新位置；失败不删除源或目标，不自动切回源 |
| 已提交，新位置不可用或外置盘断开 | 提示恢复新位置访问，不自动切回旧副本，不以是否观察到业务写入为条件 |
| 新位置已重开，原根清理失败 | 新位置继续可用，保留失败路径与按迁移 ID 重试状态；不能把任务结束当成原根已删除 |

提交成功后，尚未收尾的旧目录只是迁移时点的副本。自动切回可能展示过期数据或形成两套继续变化的数据，因此不自动回退；新位置成功重开后按上述自动收尾处理，不能依赖旧副本作为用户版本备份。已登记外部原始源码若处在旧根内，迁移前拒绝并提示路径；pending 旧根也不能被新登记为外部原件。

外部 AI 先前打开的工作目录不会自动跟随。迁移完成后用户应让 AI 在新项目路径继续工作；平台提供新的路径和 CLI 信息，不在旧目录放一个让 AI 无感继续写入的模糊兼容副本。

## 8 管理入口与 AI 工具

以下命令和管理路由属于已确认接口。`platform` 仍是名称占位符；桌面 UI 和原生 CLI 调用相同 Rust 管理逻辑。普通项目 SDK 不获得跨项目导入、清除或迁移权限。

| 命令 | 主要输入或结果 |
| --- | --- |
| `project export --project ID --input request.json` | 目标 ZIP 路径、可选明确覆盖、维护 ID；返回任务 ID |
| `project import --input request.json` | ZIP 路径、可选名称；省略 `mode` 或显式 `copy` 均使用新身份，`original` 拒绝；返回任务和新目标 ID |
| `project copy --project ID --input request.json` | 可选名称、维护 ID；返回任务和新项目 ID |
| `project delete --project ID` | 直接永久删除，不进入平台或系统回收站；JSON 可显式提供 `expectedDocumentEpoch`，省略则先读取当前项目身份；可携维护 ID，返回任务及实际删除结果 |
| `workspace info` | 当前目录、格式、空间、迁移状态 |
| `workspace migrate --input request.json` | 目标目录；返回任务 ID，沿用任务查询与日志 |

管理路由使用 `/api/v1/projects/{id}/exports`、`/api/v1/projects/imports`、`/api/v1/projects/{id}/copies`、`/api/v1/projects/{id}/deletions`、`/api/v1/workspace` 和 `/api/v1/workspace/migrations`。不提供旧回收站兼容管理路由。变更操作使用 POST，读取列表和详情使用 GET，沿用管理凭据、JSON 错误及任务协议。Node 独立槽仅开放[原生预览／删除](application-deletion.md#管理入口)，没有新增 Node HTTP／CLI 删除入口。

迁移刷新服务实例后，CLI 从固定发现位置重新取得服务信息，按任务 ID 查询提交结果；只恢复查询，不自动重新发起迁移。普通浏览器页面只接收必要状态，不获得磁盘路径、操作现场或管理凭据。
