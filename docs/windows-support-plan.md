建议建立小范围系统适配层，集中处理安全文件操作、进程、工具链发现、系统打开、目录与安装布局。按当前开放操作实现所需能力，整树删除、复杂恢复交换和迁移执行可以后置；未实现的操作必须明确不可用。不能通过关闭现有安全检查、为 Windows 返回假成功或到处补条件分支来达到可编译。

只读审查发现：文件、下载和历史清理使用 Unix 文件描述符与身份；构建发布的非 Mac 路径返回不支持；迁移检查要求 APFS；Node/npm 查找、进程组停止、`/usr/bin/open`、管理页面来源及打包脚本存在 Mac 专用逻辑。具体落点包括 `crates/platform-core/src/{files,paths,projects,maintenance,backups,lifecycle,storage,builds,environment,workspace,history_cleanup}.rs`、`apps/desktop/src-tauri/src/{main,browser_download}.rs` 与构建脚本。项目登记、恢复、回收和迁移等持久记录也保存了文件身份；接口抽取须兼容旧 Mac 记录，不能伪造 Windows inode 或重建历史。`paths.rs` 已使用系统数据目录 API，实际需补齐 Windows 的权限和安全文件行为。这是移植清单，不表示已运行 Windows 证明这些修复有效。

### 2.1 文件、凭据与故障保护

- Windows 使用适合该系统的卷/文件身份和用户私有 ACL；Mac inode、POSIX mode 不直接当作 Windows 身份和权限。涉及控制文件格式演进时明确版本，保留旧状态并提供恢复证据。
- 初期默认位置由系统目录 API 解析，不能以环境变量覆盖或手工设置跳过固定根和公开迁移。目录被重定向到未支持位置时保留诊断，不自行另选根；符号链接、junction/reparse point 不得绕过实际卷与根边界。环境探针只读报告候选目录，不等于已通过平台路径、ACL 或卷安全验收。
- 处理保留名称、尾点/尾空格、大小写与 Unicode 冲突、长路径、ADS、盘符及路径别名；目录链接与 junction/reparse point 不可绕过项目边界。
- 预检后执行仍须核对对象身份，历史清理不能退化成对字符串路径递归删除。部分失败展示实际完成范围，保留重试/恢复所需回执。
- 构建、附件、恢复和迁移在文件被占用、杀进程、磁盘不足及目标失联时保持明确状态；不能丢旧产物、把坏库当空库、自动解除维护或重放未知结果的写入。
- 迁移提交后只认可新根，目标不可用不自动回源；所有历史清理继续使用范围预览、明确确认及既有保护规则。

Windows 的命名与文件替换规则以[微软命名说明](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)和[文件替换说明](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files)为依据。进程树管理可评估 [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)，实际退出与子进程残留必须验证。

### 2.2 运行环境与浏览器

成品运行、新建预编译初始项目及已有产物读写无需用户另装 Node、Rust 或 Visual Studio 开发工具。开发构建目标默认使用配套受管 Node/npm，并保留兼容的显式本机选择；当前只有 Mac arm64 实现，Windows 工具资源与运行门禁尚未验收。沿用本机选择最低 Node 22.12.0、支持 22/24、推荐 24 LTS 的约定，W1 核对实际依赖组合及两版 Windows 的最低系统要求，不借移植擅自提高支持线。

应用业务运行的固定 `node-runtime/` 与开发构建的 `development-node/` 是两套资源。Windows 已有官方 Node 24.22.0 x64 的固定资源、私有配置 ACL、完整 ID128/保留 HANDLE、Job 进程树和静态代理实现及测试；真实桌面仍受上述 ACL 准入阻塞，范围见 [Windows Node 记录](windows-node-verification.md)。主线新增的完整开发 Node/npm 与受管 Git 仅有 Mac arm64 载荷及 Unix 校验，不能以现有 Windows `node.exe` 代替 npm/Git 开发工具，也不能以系统 PATH 的 Node 替代应用私有运行时。Windows W2.4/W2.5 用户构建、来源获取和安装更新继续按实际前置门禁，详见 [新功能兼容审查](windows-new-features-compatibility.md)。

WebView2 是桌面网页运行环境，不能用安装了 Edge 浏览器来代替运行环境检测。建议使用 Evergreen，并在缺失、版本不足、安装失败或被策略限制时提供可理解诊断；在线安装、离线运行环境安装、首次 npm 依赖下载是三个不同场景。依据为[微软分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)。

媒体格式运行时探测；用途声明、网页许可和 Windows 系统隐私开关分别生效。桌面 WebView2、普通 Edge 与 Chrome 分别验证，不因都使用 Chromium 就合并结论。关闭窗口、隐藏页面、维护、拒绝、许可等待和晚到许可均核对设备释放与写入门槛。

### 2.3 分阶段开放与启动门禁

现有 `service.rs` 启动会调用工作区恢复，并初始化构建、维护、生命周期、空间和历史清理管理器；其中一些初始化会对账或修改任务、操作日志和回执。因此后置功能不能只隐藏按钮，还须处理启动和读取入口的依赖。

- Windows 按已验收能力开放；桌面命令、CLI 和 HTTP 共用后端门禁，UI 展示同一结果。未开放操作在创建任务、预留 ID、写控制状态或修改文件前拒绝，并说明“此 Windows 阶段尚未开放”。不把未实现状态伪装成空列表、成功或正常状态。
- 未开放管理器不得进入执行、自动恢复或会改写现场的对账路径；启动仍须只读识别已有维护、迁移、恢复和清理证据。发现未支持格式或未解决状态时保留现场，阻止受影响的项目或工作区写入，并给出原因；不能跳过记录后按正常项目开放。
- 普通读取也要核对其依赖，例如工作区信息、概览、维护和空间状态。界面不应为了显示未开放模块而触发其初始化或后台任务。系统适配和门禁本身需测试，不能整块禁用原有安全测试。
- 固定身份与默认根、私有凭据、真实对象身份、路径边界、SQLite 事务、页面代次、未知写入结果不重放，以及当前操作的原子发布、失败保留和重启核对，必须随对应写入能力一起完成。用户可见的备份功能后置，不表示这些基础也后置。
- W1/W2 只使用本轮明确命名的可丢弃新项目，不接管真实用户历史数据。维护尚未开放时，不允许绕过已有维护或成功基线要求修改真实项目；AI 流程验证只面向这些新样本。Mac 继续使用原有完整路径，不能受 Windows 门禁影响而丢失功能。

2026-10-19 首片实现整体运行时门禁：共享策略按编译目标判断，当前 Windows 返回 `PLATFORM_STAGE_UNAVAILABLE`，没有环境变量或参数解锁。桌面在 Tauri/WebView 创建前退出；固定根初始化、服务发现、锁、服务启动及项目仓库构造在各自副作用前检查同一策略。CLI 保留明确的阶段错误及 `operationOutcome: not_started`，不当作普通离线成功。独立编译同一生产策略模块的 Windows 原生测试 5 项通过；入口顺序目前经源码审查，真实桌面/CLI 拒绝行为和 Mac 回归仍未验证。

同日下一片新增独立 `platform-preflight` 库，先分类传入内存的维护控制和恢复日志字节；不复用会把缺失/空对象补成正常状态的既有控制加载器。缺失、不可读、损坏、不认识的格式和未解决记录分别保留，已解决日志仅表示识别到历史记录；任何结果都不是运行许可。迁移、生命周期、快照、清理等其余记录解码与实际安全文件读取继续后置，不因个别记录能解析就开放 Windows。

## 3 项目交换与工作区迁移

本节能力整体后置到 W3；不阻塞 W1/W2 的可丢弃新项目内部验证。具体步骤通过前，完整项目导入导出、复制、回收站、迁移和清理均不开放，不用手工复制工作区或改控制文件替代。

跨系统先验证完整单项目 ZIP：Mac 导出 → Windows 导入 → 使用及修改 → Windows 导出 → Mac 导入。已有归档结构继续携带源码、固定 SDK 原字节、锁文件、清单/图标、当前产物、SQLite 一致性副本和附件；业务主键保持，原 ID 导入冲突时不覆盖，副本使用新项目 ID。

依赖在目标系统重新安装，不搬运行机器的 `node_modules`、构建缓存、管理令牌或绝对 CLI 路径。允许符合现有维护与来源规则的完整产物免 Node 打开，不能要求为了换系统一律重建；包含平台专用脚本的用户项目仍须实际构建验证。导入不运行脚本，不自动升级固定 SDK 或重写用户 README；重新生成的交接信息优先给当前机器实际路径与命令。

导入前预检目标系统不兼容名称和碰撞，失败保留原 ZIP 和现有项目，报告具体文件；不静默改名、覆盖或丢弃内容。

整工作区迁移仍指同一台电脑上的公开迁移流程。Mac 的 APFS 支持条件继续有效，Windows 对应文件系统和路径规则待 W1 确定、W3 验收。跨电脑整工作区格式、控制记录移植、实时同步和工作区合并不在现有契约中，不能用直接复制工作区控制树代替项目导入。

W2.3 通过后可以交付“Windows x64 基础数据内部验证版”；W2.5 通过后可以交付“Windows x64 新项目与构建内部验证版”。两者都只覆盖已通过的系统和本轮可丢弃项目，明确列出未开放功能，不作为真实数据接管或正式发行依据。完整支持仍需 W3/W4 和两个目标系统各自通过。

平台边界设计、测试设备准备和不依赖 Mac 未完成设备项的工作可独立推进；涉及共享数据格式或接口的修改统一协调。媒体在 W2 做小范围可行性探测，完整采集与保存能力后置到 W4.2；探测失败可以保留门禁继续基础链路，不降低基础写入门槛，也不伪称完整支持。

W1.1 的本机准备和探针结果不表示 W1 全阶段或平台运行通过；不设置未实测的工期、完成比例或发行日期。任何 Windows 阶段都不授权使用现有 Mac 用户项目做破坏性测试。

W2.4 的内部执行器检查不改变公开任务协议。CLI `project build`、桌面和 HTTP 构建入口须等 W2.5 完整发布链路通过才开放；`succeeded` 仍表示产物及来源记录完整提交，不能把暂存编译通过记为构建成功。

正常业务写入与 AI 修改是不同操作：旧维护、基线和恢复现场继续识别并保护，不因入口退出而跳过未解决状态。新 AI 流程按 Git-only 的候选、提交及重启核对规则落实，不再要求新增 ZIP 成功基线；Windows 在相关保护通过前只验证上述可丢弃新样本，不推广到带真实历史数据的项目。

W2 的附加探测只做真实 WebView2 的原生文件保存、媒体回调支持、用途声明、许可允许/拒绝、等待取消及短录音拍照，使用临时素材并核对设备释放。不要求本轮一次解决完整设备矩阵；未通过的能力保持关闭，具体错误和未完成项进入 W4.1/W4.2，不以模拟设备填补结论。

### 4.3 W3：数据与生命周期

这些功能后置，不参与基础内部版的通过条件。原编号保留，W3.1–W3.3 的新独立备份／维护基线／完整恢复产品建设按 Git-only 退出，旧资料兼容和未解决现场保护仍有效。其他操作到达对应步骤才补齐实现及故障测试，迁移、直接删除与旧回收兼容分别验收。

| 小步 | 本步范围及相对难度 | 退出条件 |
| --- | --- | --- |
| W3.1 手动完整备份（原编号） | 新独立备份建设取消；保留旧资料兼容范围 | 不新建备份产品入口或自动清理；旧 ZIP、索引与恢复依据不删除、不冒称损坏／缺失为新空状态 |
| W3.2 维护与成功基线（原编号） | 新 ZIP 基线耦合取消；旧维护现场继续保护 | 不以新归档成功作为 Node 安装前置；旧维护和未解决状态不能自动解除，后续源码修改使用现行候选与提交保护 |
| W3.3 完整恢复（原编号） | 新独立恢复产品建设取消；旧恢复兼容单列评估 | 旧候选、原件、提交日志及中断证据保留，未知状态不自动重放或覆盖；不以取消产品为理由删除旧恢复资料 |

| W3.5 项目复制 | 中；按现行复制范围与候选提交链路落实，不新建独立备份前置 | 新平台 ID、业务主键保留、内容独立、旧控制状态按契约保留；复制失败不登记半成品，也不影响源项目 |
| W3.6 直接删除与旧回收兼容 | 高；分别验收新删除与旧回收恢复，Windows 未验收前保持关闭 | 新删除确认后直接永久执行，不进入平台或系统回收站；旧回收项恢复保留原 ID，旧页面失效；中断和占用时记录真实范围；备份、恢复依据和其他项目不受影响 |
| W3.7 同机工作区迁移 | 高；依赖此前持久状态和生命周期均可识别 | 只走公开迁移；复制、校验、提交前后中断及目标失联逐项通过；固定发现位置不变，提交后不自动回旧根，源和恢复证据保留 |
| W3.8 永久清除与历史清理 | 高；最后开放，回收项清除和历史目录清理分开提交验收 | 按对象身份预检和执行；GUI 范围、字节预览、保护原因、取消、确认、部分失败及回执通过；只清理本轮可丢弃样本的已审计对象，不连带删除备份或未解决现场 |

每步覆盖其实际操作涉及的占用文件、重解析点/对象替换、磁盘不足、拒绝访问及进程中断，逐项核对原项目、备份、回收项和恢复证据。无需等所有 W3 功能完成才核对前一小步，旧记录的归档成功也不能代替恢复或新永久删除验收。受控中断不标作硬件断电实测。

## 5 验收证据、开发数据与提交规则

每个阶段记录代码版本、系统构建号、CPU、文件系统、WebView2/浏览器/Node 版本、安装包身份与摘要、可丢弃项目 ID、操作步骤、预期/实际结果及未完成项。区分源码测试、CI、真实服务、GUI 和真实硬件；未执行、失败或工具不可达均不标通过。

Windows 使用独立测试数据与目标实例；保留现有 Mac 开发标识 `dev.localprojects.platform.m0`、固定数据根及当前工作区指向。不重建现有开发环境、不直接改迁移日志、不升级旧项目的源码、固定 SDK、锁文件或文档，不清除备份、维护、回收站及恢复证据。测试前后核对受保护范围，清理只用已确认的公共流程。

进入实施后，每个完整步骤通过相关检查即 commit、push；不混入未完成并行工作、凭据、生成的安装包或本地验证证据。上一小步失败时先定位并修复，不叠加下一项功能掩盖问题；延期功能继续受门禁保护。2026-10-18 的规划提交与当前 W1.1 开发辅助脚本、环境准备分别记录；本轮不生成或重新交付平台 `.app`、DMG 或 Windows 安装包。

### 5.1 分支与主线关系

2026-10-19 用户要求明确 Windows 分支与主线关系，并再次确认每一小步 commit、push 后继续。后续 Windows 适配使用 `codex/windows-compatibility`，从当时已同步的 `main` / `origin/main` 提交 `81bd817` 创建。

| 分支 | 职责与历史关系 |
| --- | --- |
| `main` | 共用集成基线；现有 Windows 环境准备、启动门禁和前两种记录分类已经在其中。保留这些提交，不回滚、不改写历史；在本轮功能组达到合入条件前，不再直接追加 Windows 小步 |
| `codex/windows-compatibility` | 包含 `81bd817` 之前的全部主线历史；后续 Windows 小步在此验证、逐步提交并推送至同名远程分支。它是同一产品的适配工作线，不维护另一套项目格式或长期产品分叉 |

每一小步完成相关检查后立即 commit、push 到该工作分支，不能把“暂不合主线”当作积攒本地改动的理由。若主线出现新的独立修复，先 fetch，再将 `origin/main` 合入工作分支并在合并后的版本重跑受影响检查；不对已发布的分支做 rebase 或强制推送。不要把未完成的并行改动混入提交。

合回 `main` 按可独立审查的功能组进行，通过 PR 展示最终改动、实际验证和未完成项。共享核心改动需完成相关 Mac 回归；开放 Windows 能力还需其对应阶段检查通过。单个纯模块测试或 push 成功不等于可以合主线，更不等于正式发行。本轮只建立工作分支并继续小步，不执行主线合并。

分支只管理源码历史，不改变固定开发应用身份、数据根、工作区指向或用户项目；也不把 `main` 上尚未完成的 Mac/Windows 验收改称已通过。分支创建前后的实际提交和验证继续记入 [W1 记录](windows-w1-verification.md)。
