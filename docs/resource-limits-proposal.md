# 首版资源限额建议

状态：v0.2，讨论稿；M1 部分限额已按内部测试参数实现，正式默认值与扩展仍待确认  
更新日期：2026-10-15

本文展开[技术决策与实施清单](remaining-technical-decisions.md)中的资源参数。它不覆盖已确认的主约定；确认后再同步 SDK、HTTP、README 模板与验收标准。数值是面向个人 Mac、本地学习及资料项目的首版建议，不是 SQLite、Tauri 或电脑的技术极限，也不是性能测试结论。

2026-10-15 用户明确选择“先保留为内部测试参数”。M1 的 SQL、JSON、上传和队列保护用于开发验证，接口标为 `internalTest`；构建、归档、媒体与保留参数尚未实现。本文没有因此升级为正式限额契约。

## 1 建议原则

- 不设项目数量、数据库总大小或用户素材总容量的产品配额；空间页如实展示增长，不自动驱逐数据。
- 限制一次请求、一次任务和同时进行的工作，避免误写的查询、上传或构建拖住整个平台。
- 平台执行的硬限制与项目组件协作的提示分开。外部 AI 直接写文件不受 HTTP 上传上限限制，但仍遵守维护与文件协作约定。
- 所有字节使用十进制：`1 MB = 1,000,000 bytes`，`1 GB = 1,000,000,000 bytes`；JSON 时间使用毫秒，界面显示秒或分钟。
- 第一版不做几十个全局设置旋钮。普通网页使用默认值，可主动降低自己的请求预算；少数管理操作允许明确申请较高预算。不能用 `0` 或缺省表示无限制。

已经确认的数值继续保留：数据库 `busy_timeout=5000`、CLI 单次等待最多 30 秒、launch ticket 60 秒、管理附件列表默认 100／最大 500、普通自动备份最近 10 份且保护项除外。下面不重新选择这些规则。

## 2 建议默认值

| 范围 | 建议值 | 调整与超限行为 |
| --- | --- | --- |
| 普通 JSON 请求体 | 2 MB | 含 SQL 和参数；按实际接收字节限制，超限不执行业务。二进制附件单独计算 |
| SQL 返回行数 | 默认一个请求合计 1,000 行 | 管理调用可明确提高，最多 10,000 行；网页只能降低。多语句事务共享预算 |
| SQL 返回大小 | 编码后 `data` 合计最多 8 MB | 含列描述、行、Base64 字节编码等；不提供无限回包或静默截断成功 |
| 单次事务 | 最多 100 条语句 | 大批量工作由 AI 分批；明确分批不再拥有跨批原子性 |
| SQL 等待队列 | 每项目最多 32 个等待项，最多等 5 秒 | 超限或排队过期时明确尚未执行；全局最多 128 项且待执行载荷合计不超过 32 MB |
| SQL 执行预算 | 默认 30 秒 | 管理调用可提高至最多 120 秒；从真正执行起算，不含排队，锁等待包含在执行预算内 |
| 单附件上传 | 最多 256 MB | 服务流式暂存并计数；首版固定该上限，无断点续传。大文件已在本地存在不因此失效 |
| 上传并发 | 全局 2 个，同项目 1 个 | 超额直接返回忙碌，不在内存排队保存整个上传体 |
| 上传期限 | 连续无接收进展 30 秒，整个上传最多 10 分钟 | 结束暂存并清理；不能先破坏原文件。结果不明时先查询，不自动重试 |
| 标准录音组件 | 默认 3 分钟，可配置至最多 10 分钟；累计数据目标 32 MB | 先达到时间或大小目标就停止。组件协作限制，不冒充服务端音频时长检测 |
| 构建并发 | 全局运行 1 个，最多等待 8 个 | 每项目仍只允许一个未完成构建；同项目重复请求返回 `PROJECT_BUSY` |
| 构建期限 | 默认 10 分钟，管理调用可提高至 30 分钟 | 从开始运行计时，包含依赖准备、摘要和构建；不包含排队，超时在安全点停止 |
| 大型文件任务 | 全局运行 1 个，最多等待 8 个 | 备份、导出、复制、导入、恢复、历史归档另存／删除校验及旧根清理共享重 IO 槽位；内部子阶段不重复申请 |
| 空间扫描 | 全局 1 个低优先级扫描 | 同项目重复扫描复用现有任务；大型文件任务开始后在安全点让出磁盘工作 |
| 数据库空闲回收 | 无运行或等待请求 5 分钟 | 安全关闭连接和线程；打开项目窗口不等于必须永久持有数据库连接 |
| 单任务普通日志 | 最多 10 MB，保留开头 2 MB 与末尾 8 MB | 明确标注中间截断，不因输出日志太多把任务本身判失败 |
| 普通日志总量 | 最多保留 30 天，且总量目标 500 MB | 达到任一条件时清理最旧的可清终结日志；活动和受保护材料不强行删除 |
| 普通任务摘要 | 最多保留 30 天且最多 1,000 条终结记录 | 活动任务、维护／恢复／迁移仍引用的记录除外；构建来源与归档登记独立持久保存 |
| 旧网页资源 | 切换后至少提供 30 分钟宽限 | 当前产物、切换中的文件和未结束读取始终保护；宽限结束后旧页面可能需明确重载 |
| 磁盘低空间提示 | 所在卷可用空间低于 5 GB | 提示空间页与可清对象；不自动进入持久维护，不删除素材或基线 |
| 大任务空间预检 | 预计额外峰值占用 + 至少 1 GB 余量 | 每个涉及的卷分别检查；不足则拒绝新任务，不以检查通过保证之后不会满盘 |

数据库工作线程暂不额外设项目数量上限；先在最低支持设备上测试队列、连接缓存和多项目内存，再判断是否需要连接池调度。上述限额不承诺整个平台、SQLite 或任意项目 JavaScript 的内存绝不会超过某个 RSS 数值。

构建槽位与大型文件槽位可以各运行一个不同项目任务；同项目任务互斥优先。队列项只记录请求与身份，不先冻结业务、打开归档或创建巨大暂存副本。等待中的项目变更任务预留项目操作位置，避免后来请求插队；取得全局槽位后重做状态与空间预检。迁移先关闭新任务入口，排空已经接受的工作，再独占切换，不能拿着全局槽位等待需要同一槽位的任务。

大型文件任务按进度运行，不套用 SQL 的 30 秒或构建的 10 分钟期限；超过 60 秒没有可观测进展时显示阶段与诊断，不强杀目录提交。清理计划的预检也低优先级执行；具体进度心跳不是业务成功证明。

构建期限到达时停止继续构建并结束受管子进程，正式切换前检查是否已超时。若已经进入不可中断的产物／来源提交阶段，先完成日志核对与安全收尾，再按真实结果报告；新产物已经提交时不能只报“超时失败、旧产物未变”。不因编译器暂时没有日志输出就推断任务卡死。

## 3 SQL 限额的准确含义

### 3.1 查询与事务结果

建议只读查询超出行数或字节预算时返回 `SQL_RESULT_LIMIT_EXCEEDED`，不返回一份貌似完整的成功结果。错误说明触发哪项限制、预算及应使用稳定排序、`LIMIT` 或业务分页；平台不直接改写任意 SQL，也不承诺自动生成分页游标。这里建议把既有“不得无提示截断”细化成首版明确失败，而非开放不完整成功结果。

带 `RETURNING` 的写入必须特别处理：适合事务包装的写入在平台短事务中收集并校验结果，预算通过后才提交；超限时确认回滚后报告失败。多语句事务共用总行数、总字节及整事务时间预算，不能每一条重新获得全额预算。不适合事务包装的维护语句按其真实执行结果单独处理，不能虚称已回滚。

SQLite 的 `RETURNING` 可能在把结果交给调用方前缓存返回内容，所以 8 MB 是平台结果预算，不是数据库引擎内存上限；大批量写入应避免返回全部大字段。参见 [SQLite RETURNING](https://www.sqlite.org/lang_returning.html)。

### 3.2 三种超时不混用

| 情况 | 能向调用方保证什么 |
| --- | --- |
| 排队超时或队列满 | 本次请求尚未执行，可在重新核对状态后明确重试 |
| 服务端执行期限到达 | 发起中断，等操作停止与事务清理后再归还连接；结果按实际情况报告 |
| 浏览器、HTTP 或 CLI 不再等待 | 不能推断数据库已经停止或尚未提交；先查询状态或数据，不自动重放写入 |

`busy_timeout` 仅针对锁争用，不代表查询总期限。SQLite 中断接近完成时可能来不及阻止提交；实现应使用执行进度和中断机制，并避免迟到的取消误伤同连接的下一条请求。参见 [busy timeout](https://www.sqlite.org/c3ref/busy_timeout.html)、[interrupt](https://www.sqlite.org/c3ref/interrupt.html)和 [progress handler](https://www.sqlite.org/c3ref/progress_handler.html)。

建议 SQL 错误的 `details` 增加 `operationOutcome`：`not_started`、`no_change`、`rolled_back`、`committed` 或 `unknown`。成功完整提交仍按正常成功返回；仅在超时、错误或结果交付异常需要解释时使用该字段。不能把未收到响应等同于 `rolled_back`，也不把字段变成跨重启幂等保证。

## 4 附件与录音

普通 JSON 与二进制上传必须配置不同路由限制，实际流式接收时持续计数，不能只相信 `Content-Length`。Axum 默认的 body limit 只应用于遵守它的提取器，直接读取流需要另外执行限制；参见 [Axum DefaultBodyLimit](https://docs.rs/axum/latest/axum/extract/struct.DefaultBodyLimit.html)。

上传使用已确认的“暂存 → 校验 → 发布”；超限、取消或明确失败保留同路径原文件，暂存不出现在附件列表。只清理平台记录且已结束的上传残留，不按文件名猜用户附件。备份、恢复、迁移及删除等待活动上传和读取安全排空。

256 MB 限制的是单次平台上传，不是附件目录文件的有效性规则。AI 已经直接放入的更大文件仍可计数、备份并通过流式下载读取；普通页面不应对大文件一律 `files.get()` 成一个内存 Blob，媒体播放和下载优先使用 `files.url()`。读取支持适用的 Range 行为，不把下载、媒体播放或 SSE 统一套进上传总时限。导入 ZIP 走本机管理路径，也不受上传 256 MB 的限制。

录音组件默认 3 分钟，项目确有需要时可设到 10 分钟。组件在累计数据接近 32 MB 时停止，保留预听与显式保存机会；这只是尽力控制，浏览器可能迟发一个更大的数据块，不能切断 Blob 就声称仍是完整录音。最终超过上传上限时拒绝上传并提供可行的本地下载处理，不显示为已存入项目。`timeslice` 不是精确时钟，须独立计时并核对实际字节；参见 [MediaRecorder dataavailable](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event)。

录音时长／32 MB 目标属于模板和辅助组件协作要求；任意 AI 页面可能自己调用录音 API。首版服务端只保证附件上传字节限制，不新增音频解码或转码服务来鉴定时长。运行时把这些字段放在 `mediaHints`，不要混入服务硬执行的 `limits`。

## 5 归档预算与磁盘空间

建议完整 ZIP 操作默认预算为：压缩归档最多 100 GB，实际展开内容最多 100 GB，文件与目录条目合计最多 200,000 个。管理请求可显式提高，首版接受到 1 TB／1,000,000 条；这是每次归档操作的保护预算，不是项目容量配额。

导入与恢复先检查清单，再在解包过程中按实际字节和条目累计核对；不能只信 ZIP 头或仅按压缩比例拒绝。备份与导出超过预算时必须失败并解释，不能漏掉部分文件仍发布“完整备份”。归档条目路径、链接、大小写及 Unicode 冲突继续沿用既定检查。

创建、导入与恢复采用同一预算结构。平台登记的已验证大归档保存其实际尺寸和所用预算；明确恢复该归档时可沿用已登记且在首版上限内的预算，不被默认 100 GB 意外卡住。外来 ZIP 不能凭自己声明的高预算绕过管理请求设置。普通文件直接保存、浏览和工作区迁移不受 ZIP 预算约束。

预检计算的是每个卷的额外峰值，包括暂存副本、候选目录、压缩包、待覆盖文件与原现场保留需要；不能只看最终 ZIP 大小。文件系统共享块、压缩率和依赖下载量不总能事先确定，按保守估计并在任务中持续检查。调度器避免把已接纳任务的预留空间重复许给另一任务，但这不是操作系统磁盘预留。

低于 1 GB 余量时不接收新的大型写文件任务；状态查看和明确清理仍可用。普通 SQL 写入不凭“磁盘告警”自动改成维护，真实写入失败则保持正确事务清理并报告。已有恢复或迁移进入提交阶段时，以一致性和可恢复日志为先，不能因低空间硬杀或删保护文件腾地方。

## 6 日志、任务和旧资源

普通日志的容量与时间规则不适用于唯一的恢复证据。以下记录不能按 30 天／500 MB／1,000 条直接淘汰：未完成任务、维护基线引用、恢复操作日志、未清理迁移旧根的登记与删除进度、身份代次、当前构建来源和备份目录索引。保护内容超过软目标时如实展示，不为达标破坏恢复链。

自动淘汰也沿用空间清理的互斥与保护检查：取得对应项目操作位置，在没有相关活动任务或读取引用的安全时点执行；项目处于维护、维护准备或恢复未决时延后，不由后台绕过维护 ID 和恢复门禁。无法取得安全清理条件时允许普通日志暂时超过软目标。

普通任务日志超过 10 MB 时保留头尾并记录缺口；日志游标指向已淘汰区段时返回缺口说明和可用游标，不悄悄跳过。任务摘要被清理后，有淘汰记录时返回 `TASK_EXPIRED`，无法确认历史时返回 `TASK_NOT_FOUND`，不伪造成功或凭任意 ID 猜历史；已知来源、备份和未完成清理不能只依赖该摘要存在。

旧网页资源的 30 分钟是运行宽限，不是用户可选版本历史。已经加载的旧文档不获得无限期保留承诺；宽限结束、没有活动读取及切换引用后可以清理，旧页面懒加载失败时提示明确重载。不能为达到容量目标删除当前产物或仍在发送的文件，不静默刷新以丢弃表单。

这也是本轮待确认的保护细化：将既有空间契约中“仍被旧页面使用的保留产物”明确为宽限期内、活动读取或切换仍引用的资源，单纯窗口仍打开不表示无限保留。确认后须同步该原文，不能只改清理器数值。

## 7 建议接口增补

这些字段尚未并入正式接口表；建议确认时作为首版 API v1 的初始内容一起定稿。

| 入口 | 建议增加内容 |
| --- | --- |
| `context.get()`／网页 context | 实际 `limits`，包含 JSON、SQL、事务、附件上限；`mediaHints` 单列组件时长与大小建议 |
| `GET /api/v1/runtime`、`env doctor --json` | 完整生效预算、管理可申请上限及诊断，不暴露管理密钥 |
| `db.execute`、`db.transaction` | 可选 `options.maxRows`、`options.timeoutMs`；省略采用默认，越过调用身份上限直接拒绝，不静默裁剪 |
| `project build` | 可选 `timeoutMs`，600,000 默认、最大 1,800,000；最终结果记录实际预算 |
| 创建、导出、导入及恢复归档的管理请求 | 可选 `archiveBudget`：`maxArchiveBytes`、`maxExpandedBytes`、`maxEntries`；历史另存只校验复制已有归档，不重新展开 |
| 任务查询 | `phase`、进度、实际预算；日志是否截断、实际操作结果与清理残留 |

“创建归档”指备份创建，不是新建空项目。含内部基线的维护、复制与导入操作也必须传递相同预算，不能外层允许大项目，内部基线却固定用较小默认值。

网页可见字段示例，数字均是本次待确认建议：

```json
{
  "limits": {
    "jsonBodyMaxBytes": 2000000,
    "sqlDefaultMaxRows": 1000,
    "sqlMaxRows": 1000,
    "sqlResultMaxBytes": 8000000,
    "sqlTimeoutMs": 30000,
    "sqlMaxTimeoutMs": 30000,
    "transactionMaxStatements": 100,
    "fileUploadMaxBytes": 256000000
  },
  "mediaHints": {
    "recordingDefaultMaxDurationMs": 180000,
    "recordingSupportedMaxDurationMs": 600000,
    "recordingStopTargetBytes": 32000000
  }
}
```

建议错误包括 `REQUEST_TOO_LARGE`、`SQL_RESULT_LIMIT_EXCEEDED`、`SQL_QUEUE_FULL`、`SQL_QUEUE_TIMEOUT`、`SQL_TIMEOUT`、`UPLOAD_LIMIT_EXCEEDED`、`UPLOAD_TIMEOUT`、`RESOURCE_BUSY`、`BUILD_TIMEOUT` 和 `ARCHIVE_LIMIT_EXCEEDED`。沿用既有 `code/message/details/retryable`，附实际限制及操作结果。任务被接受不等于完成；`retryable` 仍不是重放写入许可。

## 8 建议确认与验证顺序

建议先确认本稿默认组合，允许在首轮真实设备测试后按明确版本调整；不要把未经测试的数值写成性能保证。第一版不提供任意网页提高硬限制的入口，也不新加资源调度后台或任意进程沙箱。

验收至少覆盖：超大查询、带 `RETURNING` 超限回滚、忙等待与执行期限、迟到取消、队列满、上传失败保留旧文件、大文件流式下载、录音迟发数据块、构建超时、归档预算上下界、磁盘中途满、日志缺口与受保护记录保留。该清单是未来测试要求，本轮未运行这些场景。
